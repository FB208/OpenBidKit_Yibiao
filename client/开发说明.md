# 易标投标工具箱开发说明

本文面向参与 `client/` 开发的成员。具体功能行为以当前代码为准；本文只保留能帮助定位代码、跨进程协作、复用 UI、维护持久状态和完成验证的稳定规则。

## 快速开始

仓库根目录没有客户端 `package.json`，所有客户端命令先进入 `client/`：

```powershell
cd client
npm ci             # 安装依赖；postinstall 会按当前 Electron 重建 native 模块
npm run dev        # Vite 127.0.0.1:5173 启动后打开 Electron
npm run build      # tsc --noEmit && vite build
```

- CI 使用 Node 22，排查本地与发布构建差异时优先对齐该版本。
- `better-sqlite3` 是 Electron native 依赖。出现 `NODE_MODULE_VERSION` 不匹配时运行 `npm run postinstall`；验证 ABI 用 `npm run smoke:electron-native`，不要用普通 Node 进程加载 Store 代替。
- 项目没有统一 lint 脚本，也没有覆盖全项目的 test 脚本；现有 `*.test.cjs` 需按改动范围用 `node --test <file>` 定向执行。

## 运行结构

```text
src/main.tsx
├─ 开发者独立窗口（由 ?window=... 选择）
└─ AppProviders
   └─ WorkspaceDatabaseGate
      └─ App
         └─ AppShell + AppRouter

Renderer
  └─ window.yibiao
      └─ electron/preload.cjs
          └─ electron/ipc/*.cjs
              └─ electron/services/*.cjs
                  ├─ SQLite Store / 配置
                  ├─ 文件与导出
                  └─ AI / Agent / 后台任务
```

- Renderer 是 Vite + React + TypeScript ESM；Electron Main、preload、IPC 和 Main 服务是 CommonJS，保持 `.cjs`。
- 主窗口启用 `contextIsolation`、关闭 `nodeIntegration`。Renderer 不导入 `electron`、`fs`、`path`，也不直接使用 `ipcRenderer`，本地能力统一通过 `window.yibiao`。
- Renderer 负责页面状态和交互编排；Main 负责配置、SQLite、文件解析、AI、Agent、后台任务、导出、插件和更新。
- `WorkspaceDatabaseGate` 在数据库检查、迁移和历史清理完成前阻止业务页面挂载；数据库相关 IPC 也会先注册为 pending/unavailable handler。
- `AppRouter` 是基于 `SectionId` 的组件分发，不是 URL 路由。不要按 React Router 的约定添加页面。

## 代码放在哪里

| 位置 | 职责 |
|---|---|
| `src/app/` | 应用级路由、菜单、全局 Provider、数据库 Gate、启动提示与状态条 |
| `src/components/` | 应用壳层组件，目前主要是 `AppShell`、`Sidebar` |
| `src/features/<feature>/` | 功能页面及其专用组件、Hook、类型和 Renderer 轻量编排；目录按实际复杂度创建，不补空层级 |
| `src/shared/ui/` | 跨功能 UI 组件和全局交互 Provider |
| `src/shared/types/` | 跨功能类型、导航类型和 `window.yibiao` bridge 类型 |
| `src/shared/prompts/` | 仍在 Renderer 使用的 Prompt builder |
| `src/shared/utils/`、`src/shared/markdown/` | 跨功能纯工具和 Markdown 渲染辅助 |
| `src/styles/` | token、壳层、共享组件和各 feature 样式；`src/styles.css` 是唯一总入口 |
| `electron/main.cjs` | 窗口、协议、应用生命周期和 Main 入口 |
| `electron/preload.cjs` | 主窗口 bridge；拖拽文件路径也在这里通过 `webUtils` 暴露；插件配置窗另用 `preload-plugin-config.cjs` |
| `electron/ipc/` | IPC 注册与参数转发；`index.cjs` 负责服务装配和数据库生命周期 |
| `electron/services/` | Main 业务服务、Store、任务实现；`agent/`、`pi/`、`doc2markdown/` 是专用子层 |
| `electron/utils/` | Main 纯工具、路径、日志、队列、文本编辑和导入图片清理 |
| `electron/resources/` | 打包进入客户端的 Agent 指令、许可证公钥和构建证明 |
| `vendor/agent-tools/`、`scripts/` | 随包 Agent 命令工具及构建/校验脚本 |

放置原则：

- 只被一个功能使用的代码留在该 feature；出现真实跨功能复用后再上移 `shared/`。
- `shared/` 的运行时代码不要依赖 feature。现有 `shared/types/ipc.ts`、`shared/types/index.ts` 会组合或转出部分 feature 类型，这是 bridge/type 边界的现状，不应扩展成 shared 引用 feature 组件或服务。
- Renderer 的 `services/` 只做 bridge 调用或轻量编排；耗时流程和权威持久化放 Main。
- 新业务 IPC 默认保持薄。`ipc/index.cjs` 的生命周期装配以及 `pluginIpc.cjs` 的现有插件市场/配置编排是例外，不要把它们复制成普通功能模板。
- Prompt 不写进组件：Renderer Prompt 放 `src/shared/prompts/`，Main 后台任务的 Prompt 与对应任务服务放在一起。

### 新增菜单页面

至少同步检查以下位置：

1. `src/shared/types/navigation.ts`：增加 `SectionId`。
2. `src/app/menuConfig.ts`：配置一级或二级菜单。
3. `src/app/AppRouter.tsx`：注册页面分发。
4. `src/components/Sidebar.tsx`：为 `navigationIcons` 补齐图标映射。
5. `analytics/dashboard/public/src/pages/traffic.js`：为新增埋点路由补中文显示名。

一级菜单有 `children` 时，`AppRouter` 会使用 `shared/ui/SecondaryMenuPage.tsx` 显示二级入口，不在侧边栏实现展开菜单。设置页是侧边栏底部的独立入口。

## Renderer 与 Main 协作

新增或修改 bridge API 时按完整链路更新：

1. 在 `electron/services/` 实现业务能力或 Store 操作。
2. 在对应 `electron/ipc/*Ipc.cjs` 注册通道，并在 `electron/ipc/index.cjs` 装配依赖。
3. 若通道依赖工作区数据库，同时加入 `index.cjs` 的 `workspaceDatabaseChannels`，确保数据库就绪前不会漏注册或重复注册。
4. 在 `electron/preload.cjs` 暴露方法或事件。
5. 在 `src/shared/types/ipc.ts` 同步参数、返回值和事件类型；全局声明由 `src/vite-env.d.ts` 引用该类型。

其他约定：

- `onXxx` 事件 API 必须返回取消订阅函数，React effect 卸载时调用。
- 受管任务页面先读取 Store 快照，再订阅 `tasks.onTaskEvent()`，随后调用 `tasks.getActiveTasks()`；后一步会再次订阅并回放活动任务，避免首次事件早于 listener 注册。
- IPC patch 以“字段是否存在”为语义：字段缺失表示保留，字段出现表示应用该值；`undefined`、`null` 或空集合通常用于显式清理，具体由对应 Store 定义。Renderer 合并 patch 时使用 `hasOwnProperty`，不要用 truthy 判断。
- 命令接口可能返回 `void`、实体或局部 patch，不假定每次写入都会返回完整工作区；需要全量状态时显式调用 `load*` / `get*` / `list*`。
- 拖拽得到的浏览器 `File` 通过 `window.yibiao.file.getPathForFile(file)` 转为本地路径，不读取非标准 `file.path`。
- 外部链接通过 `window.yibiao.openExternal()`；本地导入图和生成图使用 Main 注册的 `yibiao-asset://imported-images/...`、`yibiao-asset://generated-images/...`，不要向 Renderer 暴露 `file://` 路径。
- 只在用户输入和外部响应边界做必要校验；Renderer、preload、IPC、service 之间不重复堆叠同一套内部参数校验。

## 数据与后台任务

### 持久化位置

| 数据 | 位置 / 权威实现 |
|---|---|
| 用户配置与 API Key | `userData/user_config.json`，由 `configStore.cjs` 管理 |
| 结构化业务状态 | `userData/workspace/yibiao.sqlite` |
| 导入/解析源 Markdown、图片及文件型产物 | `userData/workspace/<feature>/`、`imported-images/`、`generated-images/` |
| Pi 运行环境和持久任务 | `userData/agent-runtime/pi/` |
| 开发诊断日志 | `userData/logs/` |
| 插件与插件配置 | `userData/plugins/`、`userData/plugin-configs/`、`userData/plugin-states.json` |

- 核心工作区、配置、日志和 Agent 路径集中在 `electron/utils/paths.cjs`；新增核心路径优先补在这里。插件自身路径目前由插件服务管理。
- Main 文件读写显式使用 UTF-8，并以 Windows 中文路径为常规场景。
- SQLite 建表、升级、健康检查和备份逻辑以 `electron/services/sqliteDatabase.cjs` 为运行时权威。改表时增加 migration，并同步仓库根目录 `sql/workspace_schema.sql` 的目标结构。
- 数据放 SQLite 还是文件系统由对应 Store 定义：导入源 Markdown 和图片通常是文件，技术方案正文则以 `technical_plan_outline_nodes.content` 为权威。不要按文本大小另建平行 JSON 缓存；删除文件型资源时同步清理其导入图片 scope。
- 不在 Renderer 保存业务状态、草稿或密钥。当前 `localStorage` 只用于远程公告已读标记，以及旧 analytics client id 向配置文件迁移。

### 单小节重新生成

正文页单节重新生成由 `contentSectionRegenerationTask.cjs` 续接原正文持久 Session，复用现有 `content-generation` 任务类型和入口，不删除会话或工作区。提示词只提供目标小节当前标题、编号、稳定 ID、HTML 路径和用户修改要求，不主动加入其他小节内容或参考指令。Agent 使用 Pi 原生 edit 和原有三类图片工具（图片任务文件位于 `任务/单节修改/`，替换已有图片时对应项加 `regenerate: true`），不重新编排、还原、检查全文字数或执行一致性审计，也不改写全文结果清单；原审计状态保留。本次只修改目标正文，未要求调整的图片与内容保留，原方案表格和图片继续保留。

程序读取目标 HTML，复用格式、图片引用检查及字数统计，然后按会话中的模板配置仅转换该小节正文，不插入目录标题，覆盖业务目录中同一稳定 ID 的 Word。其他小节文件及转换记录不变，目标转换成功后，再次点击小节即可预览最新正文。运行时沿用 target_item_id、regenerate_requirement、phase 和 html_output，不新增表或字段；修改阶段暂停/失败继续原 Session（修改要求已发出时只发送“继续之前的任务”，新一次修改先清除上次的 `prompted_stage`），转换阶段失败只重试转换。提交中、运行中、正在暂停及已暂停期间禁用全部小节重新生成入口，Main 沿用任务互斥。会话或目标 HTML 不存在时明确报错，不自动重建。运行 `node scripts/check-content-section-regeneration.cjs --real-word` 检查真实 Pi 原生编辑、会话续接、互斥、暂停重试及单节 Word 更新。

### 长任务模型

正文任务启动入口在准备运行态、任务落库和清理旧会话前，读取 Step02 已保存的配图设置。有图模式且开启 AI 配图时，仅读取 `user_config.json` 中当前渠道的 `image_model.status`；不是 `available` 就阻止启动并提示“去设置-生图模型中点击测试，并配置可用渠道”，不发起模型测试请求。无图或关闭 AI 配图不检查；普通生成无待办时仍直接返回已有结果。运行 `node scripts/check-content-generation-output.cjs` 检查该启动规则。

正文生成已移除“忽略失败小节，继续后续流程”：不再提供忽略按钮、确认弹窗和后台请求，不再使用 ignored 小节状态、等待用户选择或忽略数量字段。只有 success 表示小节完成，失败与未完成小节不从生成范围或字数统计中排除。正文生成、单节修改、一致性审计、去表格失败均使用现有原会话重试，Word 转换失败只重试转换；整本导出仍按当前目录读取全部 AI 小节 HTML。此次仅删除功能及其点击上报，其他埋点和服务端历史统计保留，不迁移、清理或重置历史数据。

正文首次生成、新增小节生成及全文重新生成在任务首次落库前统一准备运行时，清除上一轮单节目标、修改要求及执行阶段，从编排阶段开始。新增小节生成保留已有小节状态、字数和 Word 登记；全文重新生成按原规则删除旧正文 Session，并在首次落库时清空旧正文、编排、字数及转换记录，重建待生成状态。继续和失败重试保留当前运行时及 Session，不执行新任务初始化；即使首次落库后、runner 第一次 checkpoint 前退出，重启也按本轮任务恢复。启动恢复检查包含在 `node scripts/check-outline-content-state.cjs` 和 `node scripts/check-content-generation-output.cjs` 中。

正文流程中执行到一半的任务续跑时只发送“继续之前的任务”（`contentGenerationAgent.cjs` 的 `CONTINUE_PROMPT`），由 Agent 依据原会话历史和工作区继续，不重发整段阶段要求。判断依据是 Pi Runtime 在每次向会话发送阶段提示词前写入持久任务状态的 `prompted_stage`（`wasStagePrompted()`）：暂停继续或失败重试时，当前阶段（编排、生成、审计、去表格、格式补写、原方案还原、单节修改）的要求已发出才只发继续语；要求尚未发出（例如暂停发生在审计核对或交接压缩期间）仍发送完整阶段要求；审计或去表格已完成时沿用程序的收尾短提示。新一轮任务（局部生成、全文重新生成）和新一次单节修改先把 `prompted_stage`、`compaction_pending` 清为 null，避免误判为续跑。同一次运行中 Agent 未完成当前阶段就结束回合（审计未提交结论、去表格未完成、格式补写未提交）时同样只发继续语；执行失败（模型或服务中断）的自动重试发继续语，提交校验不通过仍完整退回问题清单，基础编排的执行失败仍不自动重试。改造前已发出要求的旧会话没有该记录，首次续跑仍发完整要求。页面重试日志按真实进度描述：生成阶段按上次扫描到的非空 HTML 写“已有正文 A 节保留，不重新生成；本次补齐 B 节”，审计、去表格、格式自检续跑写“从{阶段名}阶段继续”，不再显示“开始重试 N 个失败或未完成正文小节”。检查由 `piRuntimeService.test.cjs`、`check-content-generation-agent.cjs`、`check-content-generation-output.cjs` 和 `check-content-section-regeneration.cjs` 覆盖。

`taskService.cjs` 统一管理技术方案、标书查重和废标检查任务；三个业务组当前均为组内互斥。知识库是明确例外：`knowledgeBaseService.cjs` 按文档维护 preparation/matching 活动集合，并通过 `knowledge-base:event` 推送。Word 导出也有独立的进度事件。

知识库全局检索使用 `knowledgeBase.search({ keyword, page })`，页码从 1 开始，返回 `{ items, total, page, pageSize }`，每页 100 条。`total` 与当前页在同一 SQLite 读事务中查询；数据减少导致页码越界时返回最后一个有效页。Renderer 使用返回页码和总数展示，翻页沿用已提交关键字，失败保留上次成功页，清空搜索使未完成请求失效。检索仍是 Main 同步子串扫描，分页不代表全文索引或后台线程查询。

受管任务遵循以下流程：

1. Main 创建 running 任务并持久化初始状态。
2. 无恢复价值的高频进度调用 `updateTask()`，只更新 Main 内存并推送事件。
3. 阶段结果调用 `checkpointTask(taskPatch, workspacePatch, eventPatch)`，在 Store 事务中一次提交任务和业务 patch，成功后再推送同一份局部事件。
4. 页面卸载不取消任务；重新挂载从 Store 和活动任务回放恢复展示。
5. 应用重启后的恢复策略由 `taskService.cjs` 按任务类型决定：正文任务可转为 paused，目录等待选择仅在持久 Session 完整时恢复，其余中断任务通常转为 error。Renderer 不自行把残留 running 状态改成 idle。

会清空任务或下游结果的 Main 命令，必须先取消相关活动任务并等待 runner settled，再提交 Store；取消后的 runner 不得继续 checkpoint。技术方案和废标检查的导入、删除、重置已经通过 `taskService` 的 `beforeCommit` 链路处理，新入口应复用该模式。

## 技术方案关键不变量

原方案覆盖审计、旧全文图片编排及后置配图流程已移除，包括重新配图入口、专用进度、计划与图片项目存储；原方案还原、生成时保留原文表格和图片、新版 Agent 配图工具与图片保护继续保留。一致性审计及去表格在正文持久主会话中完成。新建数据库不再创建旧配图计划/项目表及三类图片上限列，启动修复也不要求它们存在；已有表、列和数据不迁移、不主动删除，历史迁移编号保持不变。

全流程“重置”先复用 `taskService` 取消并等待后台任务退出、关闭 OpenXmlHelper，再由 Store 整体删除 `workspace/technical-plan/` 和该流程专属的生成图片、导入图片、持久 Agent 会话，按业务表清空流程记录并恢复初始配置。该入口不按小节 ID 暂存或删除 Word，未登记的 Word、暂存文件和提取的投标模板均随专属目录清除；用户原始上传文件、共享知识库、公共模板库、全局配置及其他业务数据不清理。正文阶段重置、全局事实保存、目录修改仍遵循原有局部失效范围。Renderer 对全流程重置、正文阶段重置、全局事实保存和目录保存统一在 `finally` 中重新读取完整状态并替换页面快照，操作失败也刷新 Word 预览上下文；原操作错误继续提示，刷新失败单独说明且不提示重置成功。

技术方案统一使用 `technical-plan` 入口；Step02 可选上传已有方案，目录、全局事实和正文阶段以 `originalPlanFile` 是否存在决定是否启用原方案扩写能力，不再维护独立扩写入口或工作流开关。

项目级生成配置统一保存在 `technical_plan_generation_config`、`technical_plan_generation_bid_tasks` 和 `technical_plan_generation_reference_docs`，Main 通过 `technicalPlanStore.loadGenerationConfig()` / `saveGenerationConfig()` 读写，Renderer 使用同名 `window.yibiao.technicalPlan` API。Step02“长嘛样”在配置初始化或全流程重置后默认选择系统模板“标准投标简版”（`tpl-system-standard-bid`），不自动改写已有配置。Step02 的“写嘛”复用 `outlineMode`：`response-file`、`standalone-technical`、`standalone-business` 分别表示完整投标文件、技术文件独立成册和商务标独立成册；配置初始化或全流程重置后默认选择技术文件独立成册；三种生成范围均可选择，沿用现有配置保存和 Main 目录生成链路；“我有方案”保存 `outlineExpansionMode`，“知识库”保存 `referenceKnowledgeDocumentIds`，“写多少”保存 `outlineWordControlOptions` 和 `contentGenerationOptions.tableRequirement`，“插图吗”保存 AI、Mermaid、HTML 配图字段，“怎么写”保存 `globalFactsMode`。选择、开关和下拉框改变后立即保存，数字或文本输入在失焦或按回车后保存；每次成功均提示“保存成功”。目录生成页、全局事实设定页和正文生成页不再维护这些生成设置，点击生成或重新生成时直接使用 Step02 已保存配置。一致性审计在正文持久主会话内完成；选择“不要表格”时，审计结束后在同一会话中将数据表格转换为普通文字，再转换 Word。正文生成页不再提供配置弹窗。开发者模式下，正文页操作区提供“重置正文阶段”。正文任务启动前修改生成配置只更新存储，不清空已有结果；正文任务一旦启动（含编排、还原阶段），Step02 除“长嘛样”中的导出模板和模板样式范围外统一锁定（“长嘛样”中的“格式自检及修复”同样锁定）。暂停、失败、完成及重启后保持锁定，目录增删改不解锁；明确重置正文或确认修改全局事实并清空正文后解锁。锁定状态复用正文运行时保存，不另建配置表。模型、API、文件解析器和 Word 导出样式仍属于全局 `user_config.json`；目录字数生效快照、任务运行时和业务结果不属于可编辑生成配置。

基础编排、正文生成、可选字数校正、一致性审计、可选去表格及格式自检补写使用一次主 `agentService.runTask()`，通过现有 `continueTask` 在同一个运行中的 Pi Session 内连续执行，任务标识为 `technical-plan-content-generation`。正常连续执行只创建一个主 Runtime/Session，不以多次打开同一持久 Session 代替阶段续跑。内部 `planning` 阶段及进度范围保留：主 Agent 先提交基础编排，程序校验、校正目标字数、选取表格和配图并保存后，再在同一会话续接生成；原方案还原仍沿用独立任务，在两者之间按需执行。基础编排的 `正文编排目录.json` 是只读参考，包含完整目录及已有编排；本轮目标 ID 写入只读的 `正文编排目标.json`，提示词只给数量；Agent 单独将本轮目标写入 `正文编排结果.json`，格式为 `{ "plans": [{ "id": "目标小节稳定 ID", "content_plan": { ... } }] }`，内容较多时可分多次写入。每项只返回写作重点、目标字数、知识条目、表格安排和配图适配评分，不复制标题、编号、描述或父子结构，也不输出程序计算的 `image_needed`。程序在模型输出边界校验结构、目标完整性、重复及非目标 ID、知识引用和表格用途，按当前目录顺序建立 ID 映射后沿用字数校正与局部保存。新一轮编排清空结果，同一轮在编排阶段暂停或失败后继续时保留草稿；输入参考按当前目录刷新。不接受旧版整目录结果，不新增兼容解析或数据迁移；已保存编排的数据结构及版本不变。基础编排关闭结束总结，成功提交时使用 `task_complete=true`，结束后程序按 Schema 和业务规则校验编排结果，不通过按提交校验规则退回修复。该阶段开放读取、命令与结果编辑工具，写入不在工具层限制；新一轮开始时工作区已有的小节正文登记为受保护文件，被改动的在提交校验前还原，避免影响已有正文和图片。编排结果通过校验后，由任务入口完成字数校正、表格/配图选择及保存，再按需等待原方案还原；随后写入最终正文输入、复制底稿图片、初始化正文工具的数据与保护范围，并在原 Session 发送生成提示词。工具只注册一次，依赖最终编排的数据在执行时读取。新一轮任务清除上一轮图片保护、审计、去表格和格式自检状态，真正的暂停恢复沿用已保存状态。开发者模式不再在编排或原方案还原完成后自动暂停，阶段保存后直接继续；用户手动暂停及继续保留，继续时不重复已保存的编排处理。正文页工作空间指向这一主会话并保持只读；局部目录修改保留会话及非目标产物，全文重置沿用原有正文会话清理，不迁移独立编排旧会话。主会话以 `fixed_tool_list: true` 运行：首次创建即启用本任务全部工具，阶段切换只更新工具门禁，system prompt 与 tools 全程不变，便于复用模型请求前缀缓存；禁用工具由门禁在执行前拒绝。进入一致性审计前，阶段交接通过 `compact_before_prompt` 压缩历史，摘要只保留目标范围、阶段结论、统一口径和未解决问题，正文以工作区文件为准；该压缩为 `compaction_optional`，失败时记录活动并按原上下文继续，取消仍正常中止；与程序步骤并行（`await_before_prompt`）的交接压缩失败时，Runtime 在程序步骤结束、发出阶段要求前补做一次，仍失败才按原上下文继续。编排交接正文、字数校正、去表格、格式补写这三个单工具阶段及同阶段收尾不压缩：单工具阶段只有一两轮对话，压缩开销大于收益。Runtime 在交接压缩开始前把 `compaction_pending`（目标阶段及压缩参数）写入持久任务状态，成功或无需压缩时清除；可选压缩失败或被暂停中断时保留，续跑时若该阶段要求尚未发出（`prompted_stage` 不是该阶段），先按原参数补做压缩再发送阶段要求；阶段要求一旦发出即清除记录，已开始执行的阶段不中途补压缩，超限时由 Pi 自动压缩兜底。运行 `node scripts/check-content-planning.cjs` 和 `node scripts/check-content-generation-output.cjs` 检查精简结果、局部保存、字数传递及继续任务。

正文主 Agent 在基础编排时为每个 AI 生成叶子在 `content_plan.image_suitability_score` 中记录 0-10 的整数评分，0 表示不适合配图，10 表示非常适合配图。评分按图片对理解小节内容的帮助程度判断，仅编排适配性，不安排数量、类型、位置或生图提示词。评分随编排 JSON 保存和复用。编排结束后，程序读取任务启动时 Step02 的配图比例，为所有 AI 生成叶子计算 `content_plan.image_needed`：0% 全部 false；其他比例按全文 AI 生成叶子小节总数乘以用户百分比后向下取整，再按评分降序选取，同分按原目录顺序。0 分始终 false，正分候选不足时不补足。配图标记计算属于编排步骤，保存本次目标编排及配图标记后才检查暂停。首次全文编排按全文保存；局部编排以完整目录为上下文，只编排并覆盖本次目标节点。配图选取参考全文小节数和已有评分，但只写入目标节点的标记，其他节点的编排、配图标记和保存时间保持不变。未编排节点不参与评分排序，不要求 Agent 为非目标节点补齐编排；已有结果不批量迁移。该布尔值由程序计算，不要求 Agent 输出，重新提供目录给 Agent 时不携带此字段。image_needed 和评分提供给正文 HTML 生成 Agent 作为配图依据；图片类型开关另外通过用户配图要求传入，不参与编排评分和小节选取。正文及图片统一由正文生成 Agent 在同一持久会话内完成。缺少评分的旧编排不复用、不补默认分，下次执行编排时由 Agent 重新评分。

正文新增配图按布局组数分配：`contentGenerationAgent.cjs` 以本轮 targets 中 `image_needed=true` 的小节数 N 作为总组数，写入现有 `正文编排决策.json` 的 `image_layout_quota`（`total_groups`、`single`、`imageText`、`threeImages`、`fourImages`）。配图比例为 10% 时四类布局比例为 100%/0%/0%/0%，20%～30% 时为 80%/20%/0%/0%，40%～50% 时为 50%/30%/20%/0%，60%～100% 时为 40%/30%/20%/10%；先向下取整，剩余名额按小数余数降序补齐，同分按上述布局顺序处理。无图、三类生图方式均关闭或 N=0 时名额全为零。主 Agent 在并发写作前依据内容和评分统一分配到本轮允许配图的小节，通过 `generate-sections` 既有 `instructions` 传入本节布局、组数及表达目的；没有新增配图和补充要求时填空字符串，由程序说明未分配新增配图，已有原图仍按底稿要求保留。并发模型不承担全局名额。不要求每个入选小节一组，不设每节张数上限。单张图片本身表达意图；图片表格为左图右文，仅一张图，四类布局分别按分配组数执行，不互换名额。布局不规定 AI/HTML/Mermaid 生成方式，仍遵守现有开关与对照表。原方案图片及布局不占新增名额；暂停重试沿用本轮快照，已有布局计入完成数量，只补未完成部分；局部生成只计算本轮目标，单节修改不重新分配全文名额。主 Agent 在字数检查、图片保护启用前核对布局完成情况，不新增程序硬校验、自动补图或独立布局规划请求。运行 `node scripts/check-content-generation-agent.cjs` 检查名额、取整、零名额、局部目标及本节分配传递。

有图模式且 AI 生图开启时，`image_requirements` 提供本轮新增 AI 图片目标占比 60%；关闭 AI 或无图时明确不应用该目标。主 Agent 在并发写作前优先规划适合实物、场景、效果、物理结构、工艺、操作等表达的主题，结合对照表确定生成方式，通过既有 `generate-sections.instructions` 逐图传入表达目的、图片类型及 aiImage/htmlImage/mermaid。并发模型只执行本节安排，不自行改变生成方式或独立承担全局比例。占比按本轮实际新增图片张数计算：单张、图片表格各 1 张，三列 3 张，四宫格 4 张；原方案图片不计入分子或分母，原图 aiImage 属性只是格式标记。60% 是整体规划目标而非上限，不要求精确命中；保持布局名额，不额外加图凑比例，不将流程、逻辑、统计图强行改为 AI 图片，不要求覆盖全部已开启类型。主 Agent 在现有配图完成核对中检查生成方式分布，不增加程序硬校验、独立审计、补图或比例失败重试流程。暂停重试计入本轮已完成新图，局部生成只统计本轮，单节修改不追补全文比例。

AI 图片画面差异化只约束画什么、怎么画，不改变 AI 数量、占比和布局名额。AI 开启且有图时，`image_requirements` 追加差异化要求：主 Agent 逐图确定画面类型（对照表 AI 类型）、主体、视角景别和画面形式，全文分散且相邻小节不重复相同组合；图组内至少在主体或视角景别上明显不同，按步骤拆分时同时变换景别和主体，同组统一画面形式。并发写作模型在 template 中正向描述画面并注明画面形式名称，不虚构的范围限于数值、型号、品牌、单位名称和可读文字。画面形式以 `electron/services/aiImageStyles.cjs` 的 `AI_IMAGE_STYLES` 为唯一来源，正文配图工具的 AI 项 `style` 必填且只接受其中的值；`aiService` 的 `normalizeImagePrompt()` 经 `buildImageStylePrompt()` 追加对应风格说明，未指定时不再附加默认风格，只保留品牌、水印和无关文字限制。新增或调整形式时同步 `受限HTML生成规范.md` 的 style 列表，检查由 `check-content-generation-agent.cjs` 覆盖。

Step02“插图吗”的“HTML图片二次优化”（`contentGenerationOptions.htmlImageOptimization`）默认关闭。关闭时 HTML 仍正常生成和截图，正文图片工具传 `checkLayout=false` 跳过布局检测，不因字号、越界或重叠进入 Agent 修复；源码生成、读取或转图执行失败仍正常报错。开启后沿用现有布局审核、`needs_repair` 和源码修复流程；其他渲染调用默认保持原有检测。两项开关通过既有生成配置保存，SQLite 列为 `html_image_optimization`、`word_count_repair`，默认0；沿用配置锁定，不迁移旧会话快照。两个开关由程序读取已锁定的项目配置，直接传给正文执行器，不写入 Agent 可读的决策文件。程序选择当前有效的工具和阶段指令；图片修复要求只在需要时加入工具说明，Agent 按实际结果执行，不自行判断用户开关。暂停恢复沿用同一份锁定配置。单节修改按项目 HTML 二次优化开关处理图片，仍不执行全文字数修复。开关在 `check-content-generation-agent.cjs`、`check-outline-content-state.cjs` 中验证。

正文 HTML 配图的 `render-html-image` 必填 `frame_size`，与对应 figure 的 `data-yb-size` 一致；设计宽度1240px，square/wide/tall/panorama高度为1240/827/1653/698px，2倍像素输出。`localImageRenderService.cjs` 以 body 为固定画布，统一四周40px内边距（包含在尺寸中），保留源文档的背景和 Flex/Grid 父子关系，不搬移节点进额外容器。生成要求标题和主体合理利用可用空间，避免底部大块空白，不堆无意义内容或拉伸图形。HTML渲染和布局检查使用同一尺寸，检查文字及图形的横纵向越界、重叠、字号和裁切，通过既有 layout_issues 交给 Agent 调整，不通过扩大截图或整体缩小掩盖问题；不新增留白识别算法。Mermaid与其他用途的 renderExactHtmlToPng 保持原行为。运行 `node scripts/check-content-generation-agent.cjs --render-images` 检查真实Electron转图的四种比例、边距、Flex/Grid高度分配、片段及完整HTML、纵向越界和源码保留。

正文与图片 AI 响应统一由 `electron/utils/aiSourceExtraction.cjs` 的 `extractAiSource()` 提取源码：纯源码沿用原流程；响应中只有一个由一对三个反引号围栏包裹的完整代码块时，提取块内源码，忽略围栏前后的介绍或总结。语言标记只允许与任务对应的 html/mermaid 或省略。支持首尾空白、大小写语言标记和 Windows 换行，源码内部字符保持原样；多代码块、未闭合围栏、语言不匹配及空源码明确报错。正文仅在 AI 响应入口提取，随后执行原有受限 HTML 检查，已有文件及最终结果校验不放宽；图片提取后保存源码并沿用原渲染流程。源码提取与“HTML图片二次优化”分离，该开关仍只控制可选布局检查与修复，不为去除包装重新请求模型。检查复用 `node scripts/check-content-generation-agent.cjs` 及其 `--render-images` 真实转图入口。

正文 HTML 结构由 `electron/utils/htmlStructure.cjs` 统一检查：除空元素及可省略结束标签的元素（p、li、td、tr 等）外，元素须显式闭合；figure 须直接包含且仅包含一个 img，不得嵌套，img 须位于 figure 内，data-yb-size 合法。整本导出将各节 HTML 拼接后一次解析，某节未闭合的 figure 会吞并后续小节，导致“部分 figure 无法定位”或后续正文静默丢失；图片被加粗、链接包裹会导致“figure 必须包含一个 img”。模型可能把工具调用标记（如 DSML 的 `</｜｜DSML｜｜ parameter>`）混入正文：`</` 后不是标签名时解析器按注释丢弃，写在提示词末尾时 `<template>` 未闭合，图片、图注及本节后续正文并入模板，同样报“figure 必须包含一个 img”；写在正文中途时多伴随输出提前结束。检查把这类异常结束标记排在问题首位报告；`closeOpenTemplates()` 在未闭合模板的第一个子元素前补 `</template>` 并删除其中的标记，属无损修复。生成端预防：写作规则和受限 HTML 规范要求元素完整闭合；并发写作请求带 `reject_truncated_output`，`aiService` 在回复 `finish_reason=length` 时按失败处理，不保存被截断的正文。保存时校验：写作输出先无损补齐提示词结束标签，其余结构问题（含正文中途的异常标记）本节失败、不落盘；编辑子任务、进入字数检查及格式补写保存均复用同一校验；Agent 提交结果时 `inspectContentArtifacts()` 一次读取清单和逐节产物，返回阻塞问题报告；需要修复时将小节问题写入 `程序清单/提交校验问题.json` 并退回 Agent（规则见“AI、Agent、文件与日志”中的提交校验）；单节修改提交时同样校验结构。仅转换 Word、继续转换、单节修改后的转换及小节预览不做结构校验：结构完整的正文原样转换；有结构问题的旧正文由 `contentGenerationOutput.cjs` 复用 `repairHtmlStructure()`，按整本导出继续导出的同一规则在内存副本中修复（补齐提示词结束标签并删除异常标记、被加粗或链接包裹的图片移为 figure 直接子元素等）后转换，源 HTML 不回写，旧产物仍可续转。正式转换成功后通过 `onStructureRepaired` 将修复记录写入正文主任务或单节修改任务日志；无法写入 Word 的单张图片由助手原位改为文字提示，本节照常转换，经 `onImagesSkipped` 写入同一任务日志；预览先无损补齐提示词结束标签，按 figure 自身图片（含被包裹的图片）判断缺图并换成占位，再修复其余结构问题：尚无 img 的待生成 figure 保留“图片生成中”占位及图注，被包裹的已生成图片不再误显示为占位。检查由 `node --test electron/utils/htmlStructure.test.cjs`、`electron/services/aiService.truncation.test.cjs`、`check-content-generation-agent.cjs` 和 `check-content-generation-output.cjs`（含 `--real-word`）覆盖。

还原率在回填保存后计算：已还原原文可读字数 ÷ 完整原方案可读字数，按来源行范围并集统计，同一原文行被多个小节采用也只计算一次；分子分母统一复用 `countReadableWords`，不统计新增目录标题、结构标记或后续扩写字数。统计保存在正文任务 `stats.content.original_restoration`，包含 `source_hash`、`total_words`、`restored_words`、`rate`，以及图片引用数量 `total_images`、`restored_images`；图片单独显示“已还原/总数”，同样按来源行范围并集统计引用数量，不纳入字数比率。进度快照只携带统计，不重复扫描。继续任务保留同一原方案的统计，全文重新生成重新统计。正文页顶部显示一位小数和悬浮说明，未统计显示“待统计”，总字数为零显示“—”；替换原方案后指纹不匹配时显示“待统计”，移除后隐藏。新来源记录使用 `source_hash` 和 `source_ranges`，后续原方案优化扩写读取新记录。此指标只反映还原阶段的原文覆盖率，不保证后续扩写保留率。

正文事实模式由 `contentGenerationAgent.cjs` 统一翻译：`正文编排决策.json` 保留 `global_facts_mode`，并在 `global_facts_requirements` 保存当前模式的中文要求。主 Agent 阅读该要求，并发正文生成及共用编辑子任务直接接收同一段说明；不要求模型猜测英文枚举含义。资料核对按工具能力区分：主 Agent 按需检索并提供补充资料摘录，无需为传递全局事实重复摘录；无文件工具的并发写作模型核对程序提供的完整全局事实和补充材料，编辑子 Agent 按需读取工作区文件。写作提示明确“写作内容和全局事实不冲突即可，不要求完全引用全局事实”，仅使用与本节有关的事实，不为覆盖全部事实增加无关段落或重复概况；事实未明确的信息仍按同一请求中的事实缺失处理要求执行。字数要求直接根据现有 checkTotalWords 生成为明确的中文任务范围，不让并发写作模型推测未提供的字段。允许补充缺失事实不代表可以覆盖全局设定；审计仅按已有依据统一口径，不靠重新猜值解决矛盾，去表格仍只改变表达形式。新任务或新一轮目标创建输入时写入，暂停恢复不补写历史快照。受限 HTML 规范说明画框比例与 contain/cover：完整展示流程图、信息图和原图时明确使用 contain；生图服务尺寸不明确时省略 size，沿用主程序配置。

正文目标字数：正文编排使用目录生效字数快照，有上下限时以中点为基准，仅有下限取 120%，仅有上限取 80%。Agent 为目标 AI 叶子提供 `content_plan.target_words`，首次全文生成及主动全文重新生成由程序按篇幅比例校正整数总和，合计等于基准；没有全文目标时沿用 `sectionWords`，都未设置时为 0。正文启动后新增或重新成为 AI 叶子的待生成小节，复用 `pending_item_ids` 识别，提示词及程序分配均固定每节目标为 3000 字，不按全文基准或 `sectionWords` 重新分配；继续局部编排写作重点、表格和配图，保留其他小节已存目标。首次生成前新增目录不使用该固定目标，主动全文重新生成清空待生成范围并重新分配全文；暂停和失败重试复用已保存编排。固定目标不保证连续新增后仍满足全文上限，也不保证实际输出恰好 3000 字。计划版本为 6，不补齐或迁移旧计划，验证新流程需使用现有正文重置/全文重新生成入口。每节生成直接接收已保存目标；还原底稿超过本节目标时优先保留实质内容。Step02“写多少”的“字数不达标修复”（`contentGenerationOptions.wordCountRepair`）默认关闭，控制正文阶段提交后的程序字数校正；关闭时只统计实际字数。主 Agent 在两种情况下都只统计字数。仍统计实际字数、检查小节与图片完整性并启用图片保护，内容完整即进入原有审计；目标和首稿实际总字数写入任务日志。关闭修复时不保证最终字数达标，审计及格式补写仍可能改变最终字数。关闭时 `check-word-count` 返回给模型的结果把 `adjustment` 固定为 `none` 并附“只统计实际字数、不以任何方式（包括脚本批量删改）调整字数”的说明，工具描述和生成提示词同样只描述该行为，不出现用户开关名称；`checkWordCount()` 保持既有计算口径，并支持使用本轮已读取的小节字数。

字数校正（仅开启字数不达标修复时执行）：主 Agent 在正文阶段只统计字数，旧的独立小节/全文字数调整阶段、回写补丁及“强控小节字数”选项已移除；每小节建议字数仍用于目录规模与写作参考，不设置单节硬性上下限。字数上下限使用目录生效快照，任一边界可不设置；全文生成检查总字数，单节或局部重新生成（`checkTotalWords=false`）只统计本次实际字数，不把全文目标交给部分小节。正文和配图全部完成后，主 Agent 调用 `check-word-count`：由 `contentGenerationWordTools.cjs` 读取目标 HTML 的实际可读文字，排除标签、图片提示词及未完成文件，各节字数写入 `程序清单/正文字数统计.json`；向模型只返回总字数、上下限和缺失数，不返回差额，并说明字数由程序在本阶段提交后统一处理。正文阶段提交通过后，`continueTask` 调用 `planWordAdjustment`：总字数不在区间内时，落点从最近的边界向区间内收 2%（上下限都有时不超过区间中点）；按“实际字数 − content_plan.target_words”的偏差，优先把偏离最多的小节拉回本节目标，不够时从可改文字多的小节补足，尽量少改小节；单节调整量不超过本节可改文字（图片块和表格之外）的 40%（缩写）或 60%（扩写），不足 100 字的不改。有调整计划时进入 `word-adjusting` 单工具阶段（不压缩）：阶段提示词只给统计数字，主 Agent 只能调用 `adjust-word-count` 并在该调用上标记 `task_complete=true`，其他工具由门禁拒绝；未调用工具就结束时重发阶段提示词。工具内由程序逐节直接调用 `aiService.chat` 改写，不启动 Pi 子会话，请求走现有文本队列，公共材料（项目概述、全局事实、事实缺失要求、用户额外要求）作为独立 user 消息放在共享前缀并预热。含图片或表格的顶层块先换成 `<!-- yibiao:keep-N -->` 占位，改写后原样换回；占位须按原顺序各出现一次，结果须通过 `checkSectionHtml`、`assertHtmlStructure`，且 `imageStructure` 与原文一致。结果与目标偏差超过调整量的 25%（至少 80 字）或输出不可用时在同一对话追问一次；取有效、方向正确且最接近目标的一版用 tmp+rename 写回，都不合格时保留原文并记为失败。一轮结束后复查总字数，仍未达标且本轮向目标推进时按最新字数再分配一轮，最多 2 轮；仍未达标时如实记录偏差，不因字数偏差报告任务失败。工具完成后进入一致性审计，审计前压缩上下文。并发、连续失败保护、暂停处理和追问由 `contentGenerationAiBatch.cjs` 的 `runAiBatch`、`requestWithFollowUp` 统一提供，去表格和格式补写共用；服务端连续失败时 `failTask` 结束任务，继续后由工具从已保存进度续做。校正状态保存在持久任务 `word_adjust`，每节完成即记录：写回后未记录的小节按字数已变化视为完成，不重复改写；结果不可用的小节不再重试，服务端请求失败的小节继续时重试。完成时任务日志写入总字数变化、改写节数及失败小节的编号、标题和原因。进度显示在正文阶段的 `word-adjust` 步骤（条目按“轮次:小节 ID”记录）。改写规则：缩写优先删除重复表述、冗余修饰和可合并的说明；扩写补充与本节主题相关的实施细节，不虚构具体数值、人员、证书或业绩；两者都保留实质信息、事实参数和承诺，事实冲突以全局事实设定为准。

一致性修复及提交问题修复的并发编辑使用短生命周期 Pi 子会话，其模型请求沿用现有 Pi→aiService 链路和父任务的队列/取消作用域；不是让 aiService 自行解释编辑指令。子会话借用主会话工作区，使用已有原生文件及命令工具和 report-failure，直接修改分配的小节文件，向主会话返回真实状态、问题及产物事实，不返回补丁让主会话再次编辑。各子会话拥有独立会话目录，不取得主会话身份；通过 failure_handled_by_parent: true 标明错误由主 Agent 处理。子会话受 Agent 服务通用的子代理限流和每条提示词 100 轮上限约束（见“AI、Agent、文件与日志”），编辑工具一次派发全部小节即可，无需自行分批。子任务失败（含轮数超限）仍记录运行统计并返回错误，供主 Agent 重试、重新分配或跳过，不单独启动最终失败诊断上传；主任务最终失败时仍沿用完整诊断上报，其他 Agent 任务保持原有行为。结束或失败清理只作用于子任务自己的目录，保留共享的主会话工作区。未命中编辑交给该子会话读取最新原文后修正；暂停保留已写入的正文，继续后重新读取。不新增旧数据兼容或自动数据重置。

一致性修复和提交问题修复共用 contentGenerationEditTools.cjs 的并发编辑及图片保护；编辑批次按小节互斥（同一小节不能同时被两个批次修改，不同小节的批次可并发），在跑批次计数仍供字数检查及各阶段完成工具等待全部结束；子会话提示词先放同批相同的编辑规则、事实要求及（`preloadInput` 时）完整受限 HTML 规范，再在“本次任务”中给出小节编号、文件、修改要求和本节 HTML，便于并发子会话共享请求前缀，使用 Pi 原生文件操作扩展点，不重写文字匹配或替换算法。图片保护不在写入时拦截，改为提交时比对：正文及配图完整后首次 check-word-count 启用保护，正文阶段提交后进入字数校正和审计前也启用；启用时记录全部目标小节的图片结构和原始图片块（含图片的表格整体作为一块，保存在任务目录 `baseline/records/`），word_adjustment_started 保存在既有持久任务检查点，暂停恢复沿用同一记录，旧任务缺少记录时按当前文件补建。提交校验比对全部已有图片块（包括原图、新图、图注和提示词）、图片顺序、外层容器及图片表格结构；图片被删除、替换、复制、调序、移入不可见容器或改变布局时退回，并在 `程序清单/提交校验问题.json` 中附原始图片块要求原样恢复，图文表格中的普通说明文字允许调整。子任务派发时记录本节图片，结束后共用检查只读取一次本节产物，返回结构、引用、图片块问题及表格事实；子会话不再启动提交修复循环，问题回到主阶段统一决定，图片块不一致仍附原始图片块供修复；一批结束后，本批以外且未在其他批次编辑的目标小节与派发前比对，被改动的直接还原并在工具结果 `restored_files` 中列出。该还原只在结束时检查小节是否仍在编辑，依赖批次之间不重叠：当前各派发工具均为 `sequential`，Pi 按顺序执行且主 Agent 等待工具返回，同一主会话内批次不会重叠；若放开 `sequential` 或改为后台派发，执行期间被其他批次接管并先完成的小节会被旧快照覆盖，放开前需先记录各小节被批次接管的次数，只还原次数未变的小节。保护阶段只按阶段门禁限制业务工具，正文重生和配图工具停止开放，Pi 的 beforeToolCall 同时拦住当前轮已排定的禁用调用；原生文件工具和命令照常可用。同批子任务互相改写对方文件时提交校验无法识别，依靠提示词约束。检查脚本使用真实 Pi 自动工具循环和原生 edit、模拟模型响应，覆盖图片结构比对样例、BOM/CRLF、图文表格/三列图/四宫格、主子任务、暂停恢复及越界还原。

### 商务模版填写

目录阶段提取的 `bid-template.docx` 与 version 2 字段清单 `bid-template-fields.json` 由正文任务并行填写：`runContentGenerationTask` 在初始 checkpoint 后启动 `businessTemplateFillTask.cjs` 的副流程，使用独立持久 Pi 任务 `technical-plan-business-template-fill`（`businessTemplateFillAgentConfig.cjs`），与正文主会话并行，`primary_session` 仅在没有 AI 小节时为 true。填写项由 `buildFillUnits()` 按字段清单 v2 语义生成：同一 `table_id` 内同名字段出现在 ≥2 个不同 `row` 时按 `(table_id, row, name)` 逐行填写，其余 `fill_by=ai` 字段按 `name` 合并、同名填同一个值；附件和 `manual` 字段不参与。输入 `商务模版待填字段.json`（`fields` 普通项、`tables` 列与行号）、`资信库.json`（`credentialLibraryService.load()`，键名沿用资信库页面文案，不含图片、水印和时间戳）、`招标文件.md`、`招标关键信息.md`、`全局事实设定.md` 只在新会话写入，继续时沿用工作区快照并只发送“继续之前的任务”。Agent 输出 `商务模版填写结果.json`（`values` / `rows` / `unresolved`，文字用 `value`，勾选项用 `selected` 从 `options` 原样选择），`validateOutput` 检查每个填写项恰好出现一次、类型与选项，缺失逐条计入 `issues` 退回原会话修复。通过后程序把值展开到字段 id，经 `technicalPlanStore.saveBidTemplateFieldValues()` 写入 `value` / `selected` / `unresolved_reason`（互斥），再调用 OpenXmlHelper `fill-template-fields` 以空白底稿 `bid-template-blank.docx` 重新生成 `bid-template.docx`。底稿由 `ensureBidTemplateBlank()` 在首次填写前从刚提取的模版复制；清单已有填写值而底稿缺失时报错要求重新生成目录。

运行时 `contentGenerationRuntime.business_fill` 记录 `phase`（filling / rendering / completed）、`status`、以填写项为单位的统计和无法确定项，随正文运行时与 `stats.content.business_fill` 保存。新一轮（非继续且模版未完成或全文重生）先 `resetBusinessTemplateFill()` 并删除副 Agent 会话；继续按已存阶段续跑，`rendering` 只重试 Word 回填。主流程到达 word-completed、无待办直接成功两处先等待副流程，两者都成功才提交 success；副流程失败以“商务模版填写失败：…”提交 error，暂停时提交“商务模版填写已暂停”。主流程失败或暂停时先中止并等待副流程，未完成的记为 `interrupted` 并保留会话；副流程写进度不改任务状态，暂停或收尾后不再写入。没有 AI 小节但有投标模版时不启动正文主 Agent，只执行副流程（`progressMode='business'`，阶段 `business-filling`）；单节修改和内容矫正不参与。taskService 的“无待办直接返回”在模版未完成时仍启动，AI 生图可用性只在存在 AI 小节时检查。已填值随正文一起失效：正文阶段重置、全局事实保存/重新生成（`clearContentGenerationState`）以及 `saveOutline` 的 `replace` 在同一 `createContentWordTransaction` 中暂存当前模版与清单、从底稿恢复占位并写入去掉填写值的清单，事务失败时先删除 `changes.created` 再恢复暂存文件；清单没有填写值时不碰文件；Word 占用时报 `BID_TEMPLATE_IN_USE`。局部目录变更保留 `business_fill`，资信库修改不自动失效。回填和失效都以底稿重新生成模版，用户在 Word 中对 `bid-template.docx` 的手工修改会被覆盖；整本导出仍不合并商务模版。正文页命令栏显示商务模版状态并提供“打开商务模版”，失败时按钮为“重试商务模版填写”（复用 `retryFailedSections`）。运行 `node scripts/check-business-template-fill.cjs`（真实 SQLite Store、模拟 Agent/助手）检查填写项、结果校验、仅副 Agent、失败重试、暂停继续、并行等待与中断和失效回滚；`node scripts/check-template-extraction.cjs` 用真实助手检查回填。

容易遗漏的状态规则：

- 招标文件的完整合并原文保存在 `technical-plan/tender-original.md`，当前投标范围工作副本是 `tender.md`，单份来源 Markdown 在 `tender-files/`；Word 原件（`.docx`，或由 `.doc`/`.wps` 转换）在 `tender-originals/`。切换标段会从原文重建工作副本并清空下游。旧工作区没有原件时须重新导入。
- 目录属性使用“通用、商务/资信、技术、其他、目录、报价、业绩”，叶子处理模式使用 `ai-generate`、`template-fill`、`directory-generate`、`manual-fill`、`other`。Agent 生成一级目录时固定将商务/资信与业绩标记为 `template-fill`、目录标记为 `directory-generate`、报价标记为 `manual-fill`；确认弹窗仍允许分别调整属性和处理模式。一级目录弹窗按生成范围设置默认选择：完整投标文件选择全部，技术文件独立成册选择技术目录，商务标独立成册选择 `template-fill`、`directory-generate` 和 `manual-fill` 目录。一级目录确认后，存在 `ai-generate` 根目录时 Main 恢复原目录生成 primary Session 继续生成完整目录；没有时直接保留用户选择。仅当确认结果中存在 `content_mode=template-fill` 的一级目录且存在招标 Word 原件时，才额外创建独立普通 Session，并只传入这些“模板填写”目录执行投标模版提取；`directory-generate`、`manual-fill`、`ai-generate` 和 `other` 均不参与抽章、字段标注或 AI 正文生成。相关任务都返回成功后目录业务任务才完成；没有模板填写目录或 Word 原件时自动跳过模版提取，技术文件独立成册只走目录生成。模版提取普通 Session 调用 `openxml` 依次列块、抽章、扫描待填候选并写入 `w:sdt`，成对生成 `technical-plan/bid-template.docx` 与 `technical-plan/bid-template-fields.json`；原文结构以紧凑文本 `招标原文结构.txt` 提供给 Agent，没有 `[标题N]` 标记的原文标题必须用 `startBlock` / `endBlock` 明确章节边界，不能用忽略候选掩盖误抽取章节。字段语义按企业信息库自动填写设计：`fill_by=ai` 由企业信息库或招标信息自动填写，`manual` 只用于签字、仅盖章位置和附件材料；同一实体全文同名。字段清单为 version 2，带 `kind`（text/choice/attachment）、勾选项 `options` 及表格单元格的 `table_id`/`row`，同一表格下同名不同行的字段逐行填写，其余同名字段填同一个值；旧 v1 文件不迁移。模版提取在公共层统一开放的原生工具之外，只开放 openxml、report-failure。`openxml` 遇到文件被占用、无权限等环境错误，或同一动作连续 3 次返回相同错误时，通过 `reportTaskFailure` 直接结束任务，按整体失败处理。列块、抽章、扫描、开始写入字段分 4 步经 `onStep` 推进目录任务日志；目录分支先结束时，进度按模版步骤在 88～97 之间推进。细则见 `openxmlhelper/开发说明.md`，真实助手检查运行 `node scripts/check-template-extraction.cjs`（可加 `--source <招标文件.docx>` 对真实文件做冒烟检查）。
- 技术方案目录从生成阶段起区分身份和编号：`id` 为程序生成的 UUID，`number` 为按目录树位置计算的显示编号；`parent_node_id` 和 `sort_order` 仍是数据库的层级和顺序依据，不新增编号存储字段。Agent 新节点填 `id:null`，程序在阶段交接时分配 ID 并写回会话；已有节点必须原样保留 ID，评分规划及叶子分配通过 `root_id` 引用稳定的根节点 ID，不再维护 `branch_id`。评分规划阶段经用户批准新增的一级目录（仅限技术、`ai-generate`、无 children）由 Agent 以 `id:null` 插入 `outline.json`，规划分支 `root_id` 填 null 并以 `root_title` 与新目录标题对应；程序在阶段交接时校验已确认一级目录未被改动、分配 ID、按标题回填 `root_id` 并写回会话，非空 `root_id` 及 `extra_titles.root_id` 必须属于已确认一级目录。删除、合并、改名、排序等其他一级目录调整仍在完整目录生成阶段执行。技术方案使用独立的 `TechnicalPlanOutlineItem` / `TechnicalPlanOutlineData` 类型，不改变可研目录身份协议。
- 正文编排、原方案还原、生成工具及结果清单使用稳定的 `id` / `node_id` / `section_id` 关联；提示词和页面显示使用 `number`。正文 HTML、还原底稿和业务目录内每小节 Word 均按稳定 ID 命名；转换失败后排序再重试不会改变输入输出归属。此次改造不兼容旧目录和产物，不迁移、不做升级重置或历史清理；用户自行执行现有重置操作。
- 目录结构和非 AI 节点正文的权威来源是 `technical_plan_outline_nodes`，Renderer 对应 `outlineData.outline[*].content`；`contentGenerationSections` 主要保存生成状态和错误。新正文 Agent 的受限 HTML 保存在持久会话工作区，整本 Word 导出直接读取这些文件，不额外保存 HTML 到数据库。
- 正文 HTML 经最终检查后，实际字数按稳定小节 ID 保存在既有运行时的 `section_words` 中；页面小节、父章节及全文统计使用这份字数，单节修改同步更新。每节 Word 转换成功时通过同一 checkpoint 保存成功状态、转换记录并移出 `pending_item_ids`，转换重试保留已完成项。待生成判断不能把数据库 AI 正文为空当作未完成；普通生成没有待办时直接返回已有成功任务，不删除会话。数据库只保存状态和字数，不增加 HTML 副本。
- Step02“写多少”中的 `outlineWordControlOptions` 是当前可编辑配置，目录成功时固化为 `outlineWordControlSnapshot`；正文生成只使用生效快照。只改当前配置不会改变已生成目录对应的正文目标。
- `saveOutline()` 的 `reason` 是持久化协议：`replace` 清空全部旧正文；`edit` 只更新标题和 Markdown 描述，保留正文和编排；`delete`、`add-root`、`add-child` 结合稳定节点 ID / `affectedNodeIds` 只清理受影响节点。叶子下添加子目录清空原叶子正文和编排；删完全部子目录后，父节点成为 AI 叶子并重新编排、生成。`sort` 只更新目录顺序，显示编号按树位置重新计算；节点 ID、正文、编排、图片关联、运行时及小节 Word 文件名保持不变，不执行 ID 重映射或 Word 换名。不要省略 `reason`，否则 Store 会按 `replace` 处理。
- 目录标题或描述编辑保留正文任务和运行时；局部增删清理本轮任务进度，但保留正文持久 Session 和工作区，按当前有效 AI 叶子 ID 保留未受影响小节的成功状态、编排、`section_words` 与 Word 转换记录。新增及重新成为叶子的节点加入待生成列表并跳过原方案还原；已删节点的 HTML、图片和 Word 允许留为孤儿文件，导出只按当前目录 ID 读取。叶子与父章节互换仍清空该节点的正文、状态和编排，同时清除对应 HTML、Word 及字数，不影响其他小节或共享图片。
- 新一轮局部生成在原正文 Session 中更新输入快照与 targets，重置上一轮字数调整和审计进度，保留其他正文及图片；本轮暂停/失败继续不重置输入和阶段。仅生成、调整、审计及转换本轮目标，成功后合并字数、状态及 Word 记录。局部目录保存不调用 AI；只有明确全文重新生成、整目录替换或重置才按原流程删除正文会话，不新增历史数据处理及后处理流程。
- 全局事实页面保存、增删、重新解析，在已有正文时必须先确认清空；取消不保存，无正文直接执行。AI 调整复用已有清空提示。确认后 Main 清空正文、编排、任务和运行时，解除配置锁定。运行或暂停的正文任务仍禁止修改全局事实。检查目录状态执行 `node scripts/check-outline-content-state.cjs`，使用系统临时目录中的独立 Electron/SQLite 工作区。
- 正文任务处于 running、pausing 或 paused 时，Store 禁止目录变更和手工正文保存，避免破坏可恢复状态。

统一正文样张以 `electron/resources/content-generation/正文模板.html` 为唯一来源，保留标题、正文、表格及图片布局。模板设置页面通过 `src/shared/bodyHtml/documentTemplate.ts` 读取同一文件，仅将示例图片 src 替换为打包后的本地地址；正文 Agent 输入移除 img 的 src 和 data-yb-asset-ref，保留结构、提示词及图注。样张标题仅展示排版效果，小节正文仍不得输出 h1～h6 或外层章节标题。生成规范在同目录的 `受限HTML生成规范.md`，用户选中的模板配置另行提供；暂停恢复沿用已有会话快照，不主动更新历史输入文件。

受限 HTML 开启章节页框时，由 `RestrictedHtmlDocumentRenderer` 在应用各类内容样式后，将相邻标题之间的正文、列表、表题、图题、图片和业务表格融合为一张真实表格；无标题的小节正文同样处理。原业务表格的行直接并入统一列网格，通过跨列、跨行合并保留原布局，不产生嵌套表格；融合后的业务表头不单独重复。遇到任意一级至六级标题、模板样式范围或页面分节即结束当前表格，分节属性始终在表格外。页框不成为不可拆分的分页单位，正文与业务行继续按内容跨页，图片不得切片，放不下时整体移到下一页或下一栏。A3 横版双栏继续使用实际单栏宽度。页框表格与满宽业务表格按栏宽 100% 输出并声明 Word 兼容模式 15，用户在 Word 中调整页边距后正文框与标题边框同步移动，规则见 `openxmlhelper/开发说明.md`。

一至六级标题始终是正文顶层段落，保留 Word 导航、编号、`keepNext` 和一级标题另起页设置。`heading_border.include_headings` 对应“标题也放入页框”，只在章节页框开启时生效，默认 `true`；已有模板缺字段也按 `true` 读取，不迁移、不批量改写模板。关闭时仅取消标题边框，保留底纹、缩进和其他标题样式，正文表格在标题前后分别收口。模板预览、小节 Word 和整本导出共用 C# 转换。模板设置页“导出测试 → 从投标文件导出”复用技术方案整本导出（`source: 'technical-plan'`），只以传入的当前编辑模板配置替代项目“长嘛样”已选模板，正文结构确认和未完成小节处理与技术方案页一致；预检查按 AI 小节生成状态及非 AI 小节正文判断是否有已完成标书，AI 正文不在目录 `content` 中。`exportService.cjs` 中仍在使用的 Markdown 导出保留段落页框结构，但同步遵循标题边框开关；不把受限 HTML 的融合逻辑复制到该路径。左题栏功能已移除，旧配置不读取、不迁移。

`npm run check:docx` 检查真实表格分页和 Markdown 标题开关，`node scripts/check-technical-plan-export.cjs` 检查受限 HTML 的平面融合、标题导航属性、开关以及预览与正式导出范围。

模板的纸张、方向、双栏及四向页边距始终应用于整个文件，其余标题、正文、列表、表格、图片、章节页框、页眉页脚和页码遵循项目范围。`ai-only` 按叶子目录的 `content_mode=ai-generate` 识别，全部后代均为 AI 生成时父标题也套模板；混合父标题保持基础样式，并跟随首个子目录所在的页面。非 AI 内容不得通过文档默认字体或标题样式间接继承模板。连续同范围目录正常接续，AI 与非 AI 范围交界使用 Word 原生下一页分节，不加表格包装；页框在章节或样式范围结束处收尾。`document` 模式下待填写提示同样接续页框，`ai-only` 模式下非 AI 提示不画框。范围外的节必须显式写入空页眉页脚，避免 Word 继承上一节；页码沿全文连续计数，只在文档起点设起始值，后续节不重启；“首页不同”为封面预留，整本导出尚未接入封面，因此暂时忽略该设置：不创建首页专用空白页眉页脚，第一页按所在范围的普通页面规则排版。用户设置仍保留，普通小节转换和模板样张继续遵循该设置。

页眉页脚的预定义样式只负责色条、边框、图标、分栏和固有高度等结构；模板设置中的页脚距底边距离、字体、字号、正文颜色和正文对齐方式对全部样式生效，预览与 Word 导出必须读取同一组设置。选择色带页脚或为其应用主题时，应根据强调色计算可读颜色并写入 `footer_color`；用户后续修改该设置时，渲染和导出不得再自动覆盖。页码徽标和图标的前景色可继续根据结构底色自动计算对比色。

正文间距使用 `spacing_before/spacing_after` 与各自的 `_unit`（`lines` / `pt`），行距使用 `line_spacing_mode` 与 `line_spacing_value`。旧正文间距字段不读取、不迁移，缺少新字段时默认为段前后 0 行、多倍行距 1.2。普通正文与列表逐段应用，表格只共享行距；基础样式不携带正文的行单位段间距，避免标题、图注和表格继承。模板预览、模板样张导出和投标文件导出都写入 Word 原生 `beforeLines/afterLines`、`line/lineRule`，不将导出文件中的行单位换算成磅。

DOCX 预览引擎固定使用 `@docx-editor.dev/core@2.15.0`，项目修复统一保存在 `patches/@docx-editor.dev+core+2.15.0.patch`，同时覆盖 ESM 与 CommonJS 两份构建。`postinstall` 通过 `patch-package --error-on-fail --error-on-warn` 自动应用；补丁失败或版本不匹配必须中止安装，不再维护另一套替换脚本。

该补丁包含两类修复：标准行段间距（标记 `yibiao: standard-line OOXML paragraph spacing`）补齐 `beforeLines/afterLines`，按一个标准行等于 240 twips（12pt）换算，并保留自动间距优先、属性分别继承的规则，限定项目生成的无 `docGrid` 文档，不支持自定义网格行高；表格分页（标记 `yibiao: flowing table rows and keepNext`）让可拆分的表格行先使用当前页剩余空间再续排，并让单元格内表题与表格、标题行与下一行首块保持同页。同页关联的容量判断必须扣除已启用的重复表头高度和单元格上下内边距；关联块超过该容量时按原拆行规则续排，不得为保留关联块而丢掉续页表头。表格流式排版对顶层业务表格和段落边框页框同样关键，不得删去。

补丁必须随代码纳入版本控制，`node_modules` 只保存应用后的结果，不作为修复的唯一来源。补丁以原始依赖包为基线；有局部手改或局部补丁的环境使用 `npm ci` 重建依赖，由 `postinstall` 完整重放，不兼容局部修改状态。升级依赖时同步更新补丁及版本，不能跳过补丁后继续声称预览支持对应排版行为。

Mermaid 以 Markdown `mermaid` 代码块持久化。Renderer 由 `MarkdownRenderer` 本地预览，Word 导出由 Main 的 `localImageRenderService.cjs` 本地转图，不依赖在线 Mermaid 服务。

### 正文格式自检

格式自检是可选阶段，由 Step02“长嘛样”的“格式自检及修复”（`layoutCheck`）控制，默认关闭。开启时，全文及局部正文生成在字数校正、一致性审计和可选去表格结束后进入 `layout-checking`，随后执行原有逐节 Word 转换；关闭时任务入口不传入检测函数，沿用 `finishLayout()` 的跳过分支直接进入 Word 转换，不导出整本、不请求模型。后端不校验该开关，锁定只在页面层；已暂停在格式自检中途的任务在开关关闭后完成当前补写即转换，不再复查。单小节重新生成不增加此阶段。`contentGenerationLayout.cjs` 复用整本导出，按当前目录和模板将 Word 写入系统临时目录。`wordLayoutPreload.cjs` 在独立隐藏 Electron 窗口中调用 docx-editor 2.15.0 的导出布局 API，显式传入 Canvas 字体测量器，不使用近似测量、截图或 AI 读 Word。窗口和临时文件在完成、失败、暂停时清理，继续任务时重新创建。

检测只处理实际文流中图片或图片组放不下而进入下一页/栏的尾部留白，阈值为至少 3cm 且超过邻近正文 4 行；页边距、页眉页脚、图内和单元格内部留白不计入。双栏按左栏、右栏、下一页左栏分析，通栏标题分隔文流；章节另起页及文档末尾不补写。字数取邻近同栏宽的完整正文行估算，扣除段间距并预留一行，不按整页字数平均。布局只有 docx-editor 排版口径，不承诺与其他 Word 排版引擎逐页一致。

自检导出副本携带不可见书签，映射稳定小节 ID、顶层块下标及图片标识；不修改源 HTML，不向 Agent 工作区放 Word。任务集合、已完成小节、`failures` 与 `failed_gaps` 保存在正文 Session 的 `state.layout_check`。初检与复查作为主任务 `continueTask` 中的程序步骤，不额外请求模型；有补写任务时才进入 `layout-checking` 单工具阶段（不压缩），阶段提示词只给小节数和留白处数，主 Agent 只能调用无参数的 `supplement-layout-sections` 并在该调用上标记 `task_complete=true`，未调用就结束时重发阶段提示词。工具由程序逐处补写：按 `figure_ids` 定位留白后的图片块（图片本身或图片表格，缺少图片标识时才退回检测时的顶层下标），把块前两段文字、图注、本节标题与写作重点交给模型，只生成一段纯文本；全局事实与事实缺失要求作为独立 user 消息组成共享前缀。字数按程序口径须在建议字数的 70%～100%（宁少勿多）：超出上限或含标签时追问一次，偏少的结果可作为备选，仍不合格则记为未补写。程序转义后包成 `<p id="<图片块id>_lead">`，连同 `yibiao:block` 分隔插在图片块的分隔注释之前，其余内容逐字节不变；该 id 已存在即视为已补写，续跑和重复调用都不会重复追加。结果不可用的位置不再重试，服务端请求失败的位置继续时重试。工具完成即保存 `submission`，主流程置为 `rechecking` 后由程序复查；不再由提交检查把未补写位置退回重做。程序最多执行一轮补写和一次重新导出复查；完成时任务日志先列补写失败的位置（编号、标题、图片 id、原因），再列复查后仍有的留白。无合格留白时不调用模型。补写后不重复检查字数范围或一致性，仅刷新实际字数。局部生成分析全书但只补写本次 targets，成功和恢复继续沿用现有小节转换、统计与文件生命周期。

页面显示格式自检、补写、复查进度，暂停及失败继续原阶段。格式检查函数每次只执行当前初检或复查，补写工具提交后由主会话接回程序复查；同一轮使用相同模板快照。恢复到初检/复查阶段时先执行程序步骤，无需补写则不重启主模型。正式小节 Word 转换仍在主 Agent 完成后由程序执行，转换重试只处理剩余文件。全文进度范围为正文至 70%、审计至 80%、去表格至 83%、自检至 88%、转换至 99%，任务成功才为 100%。运行 `node scripts/check-content-layout.cjs` 验证真实整本 Word、Canvas 分页、书签不影响版式、单/双栏及图文表格、章节页框、估算补写和一次复查；原会话工具和任务恢复分别由 `check-content-generation-agent.cjs`、`check-content-generation-output.cjs` 覆盖。

## UI 与样式复用

UI 使用全局 CSS + Radix primitives，不使用 Tailwind。优先从 `src/shared/ui/index.ts` 引入：

| 场景 | 复用入口 |
|---|---|
| 页面底部操作 | `FloatingToolbar` |
| 对话框、开关、提示 | `AppDialog`、`AppSwitch`、`useToast` |
| 上传区 | `UploadBoard`、`UploadRow`、`UploadFilePill`、`UploadEmpty` |
| 进度、加载、空态 | `ProgressBar`、`InlineSpinner`、`EmptyState` |
| Markdown | `MarkdownRenderer`、`MarkdownEditor`、`MarkdownFullscreenViewer` |
| 全局特殊交互 | `AgentQuestionDialogProvider`、`AiHttpErrorDialogProvider`、`DocumentParseNoticeProvider` |

- `AppProviders` 已挂载全局 Provider，feature 使用对应 Hook，不重复创建全局弹窗或提示状态。
- 成功、错误和普通提示使用 `useToast()` 的 `success`、`error`、`info`；不要使用 `alert`、`window.confirm` 或 `window.prompt`。需要确认或长文案时使用 `AppDialog`/Radix Dialog 和共享按钮类。
- 复用 `.primary-action`、`.secondary-action`、`.danger-action`、`.text-button`、`.panel`、`.section-kicker` 等基础类；颜色、圆角、阴影、焦点和动效优先使用 `styles/tokens.css` 的 `--yb-*` 变量。
- 新 feature 样式放 `styles/feature-<name>.css` 并在 `styles.css` 的 feature 区导入；共享样式才进入 `shared-*.css`。总入口的 `tokens → layout → shared → feature` 顺序参与 CSS 优先级，不随意重排，也不要照搬开发者测试页中的内联视觉样式。
- `body` 固定 `overflow: hidden`。页面根节点保持 `width/height: 100%`、`min-height: 0`，滚动放在页面内部；`FloatingToolbar` 是覆盖层，不为它预留大段底部空白。
- `MarkdownRenderer` 当前默认 `allowRawHtml=true`，调用方不要依赖默认值：远程公告、Agent/AI 文本及其他非本地可信内容显式传 `false`；只有确需保留本地解析 HTML 结构时才传 `true`。
- 所有用户可见文案使用中文，并给失败状态提供可操作信息。

## AI、Agent、文件与日志

- 投标文件生成各阶段及编辑子任务均启用七个原生工具 `read/write/edit/bash/grep/find/ls`，其中 `grep` 使用 Pi 原生工具；也可通过 `bash` 使用运行环境提供的命令。公共层确保阶段切换、暂停恢复及失败重试不缩减原生工具，自定义工具的权限保持各任务原有声明。任务提示词优先推荐专用工具；业务工具仍按阶段权限开放。文件修改不在 write/edit 层校验，任何写入方式（含命令）的结果统一在提交时校验，见本节“提交校验”。
- 业务模型请求统一经过 `electron/services/aiService.cjs`。它集中处理模型配置、文本/生图独立队列、并发、重试、取消、日志、Token 统计和埋点；Main 业务代码不要直接请求模型 HTTP。
- AI 响应的 Agent 计时归属统一由 `electron/utils/aiRequestActivity.cjs` 的异步上下文维护：Runtime 启动任务时登记本轮刷新回调并继承父 Agent；AI 服务入队时捕获上下文、出队及重试时恢复；Agent 本地 HTTP 代理按所属 Runtime 显式恢复上下文。每次实际文本或生图请求成功、失败，以及收到非空流式数据块时，更新所属 Agent 和父调用链的 `last_activity_at`，不广播给同队列其他 Agent。JSON 修复和内部重试逐次通知；生图结果在图片下载和落盘前通知。已结束或取消的运行忽略迟到响应，普通非 Agent 调用不刷新 Agent。
- AI 统一通知只刷新空闲时间，不重复转发业务 `onActivity`；状态沿用 Runtime 每秒推送。代理成功、失败、流式响应和模型回答完成的旧重复计时已移除，原诊断、日志和统计保留。Agent 无进展检测、请求自身超时、流式连接空闲计时、工具及业务阶段进度继续保留；现有排队和普通请求等待心跳保持原行为，不作为 AI 响应接入新增父链通知。本机制不增加定时心跳，不改变重试、取消及错误结果。
- 易标官方 API 余额不足返回 HTTP 402，正文 `error.type=yibiao_ai_error`、`error.code=INSUFFICIENT_BALANCE`，不重试。所有 AI 失败出口共用的 `emitAiHttpErrorToWindows()` 识别后广播 `ai:balance-insufficient`（bridge 为 `window.yibiao.ai.onBalanceInsufficient()`）。主窗口由 `src/app/useTextModelSetupRedirect.ts` 统一跳到设置-文本模型并打开官方充值，5 分钟内只跳一次，余额上升（充值、兑换到账）后解除冷却；启动时官方余额 ≤ 0，或非官方服务商缺 API Key、模型名称、Base URL 时执行同一跳转，后者不打开充值。跳转经 `requestSectionChange` 走页面离开守卫，设置页通过一次性 `SettingsPageRequest` 切换分类；功能页面不单独处理余额不足或未配置跳转，其他服务商的 402 不在此处理。
- `taskService` 为任务绑定 `queueScopeId`、取消信号以及 scoped `aiService` / `agentService`。暂停或取消应沿该作用域传播，不在业务任务里复制队列。
- 批量程序步骤（一致性核对及 `recheck-sections`、`generate-sections`、`generate-section-images` 与两个转图工具）用 `electron/utils/aiBatchGuard.cjs` 识别服务端故障：同一批连续 10 个 AI 请求本身失败（带 `isAiRequestError`，即未拿到可用回复，含 HTTP/流式错误、网络、超时和截断）且期间无成功时，以 `AI_UPSTREAM_UNAVAILABLE` 停止派发剩余项，消息带最后一次错误原文，已完成结果保留；成功或服务有响应的校验失败清零，暂停时队列丢弃（`AI_QUEUE_SCOPE_PAUSED`）和取消记为已中断、不计入。核对步骤直接抛错；工具内批量通过 `failTask` 中止所属正文或单节修改任务（图片批量先保留本批结果），不交回 Agent 反复重试；该错误不属于预期中断，照常计入 Agent 失败统计与诊断。AI 队列层和 Pi 子会话编辑批次不接入。`requestJson` 等 JSON 请求最终失败时在 `failureMessage` 后附最后一次校验或修复错误原因，并保留 AI 请求错误标记。检查由 `node --test electron/utils/aiBatchGuard.test.cjs` 和 `check-content-generation-agent.cjs` 覆盖。
- Pi SDK 模块和工具环境全局共享，`agentService.cjs` 为每个实际 Agent 调用创建独立 Runtime/Session；模型请求仍由 `aiService` 文本队列统一控制并发、取消和统计。`startTask` 通过 `getAiRequestActivity()` 识别子代理：在某个 Agent 执行过程中（工具调用、阶段交接）发起的调用即为子代理（如编辑子会话、原方案还原），业务代码在 Agent 之外发起的为主任务。子代理按父 Agent 分池限流，同一父 Agent 同时运行的子代理不超过文本并发上限的 2 倍，超出部分在创建 Runtime/Proxy 之前排队（不计空闲超时，数量见状态 `queued_count`），排队中中止或服务关闭时直接拒绝；孙代理进入子代理自己的池，不会互相等待。子代理每条提示词之后最多执行 100 轮（发送新提示词时清零，压缩不清零），超限以 `AGENT_TURN_LIMIT` 中止，不走 `max_retries` 续跑，错误交由调用方处理；主任务不设轮数上限。失败诊断上报仍只由 `failure_handled_by_parent` 决定。这些规则由服务层默认启用，业务调用不传参数。各 Runtime 的状态变化在 `agentService` 中合并为最多每 250ms 推送一次，Runtime 推送不再查询队列；AI 队列的并发上限缓存 1 秒，避免高频同步读取配置文件。业务任务通过 `primary_session` 显式指定主 Session，执行监视器展示 `active_tasks`，桌宠插件只访问主 Session。`services/agent/` 和 `services/pi/` 只实现 Runtime、Proxy、Session、工具、诊断和持久任务，不引用业务 Store 或业务 Prompt。业务适配器通过 `agentService` 公共接口调用。
- 普通 Agent workspace 是临时目录；目录生成 V2 使用持久 task workspace/Session 才能在一级目录确认阶段恢复。结构化 Agent 输出的 Schema 定义在业务任务代码中，通过 `json_validation_schemas` 注入，Agent 调用 `json-validation` 时只传 `file_path`。
- 目录生成按阶段声明必需产物：一级目录、子目录和数量调整使用 `outline.json`；评分规划使用 `technical-score-groups.json` 与 `score-directory-plan.json`，用户批准新增一级目录时同时在 `outline.json` 插入新目录；多技术分支且有字数目标时由 Agent 填写 `leaf-allocation.json`；最终审核使用 `outline.json` 与 `outline-review.json`；模板提取使用 `投标模版字段分类.json`，最终 Word 和字段清单仍由 `openxml apply-template-fields` 生成。无评分流程跳过评分及分配文件，单分支或无字数目标的分配内容由程序直接写入。字段分类 Schema 由模板任务与 OpenXML 工具共用，零候选时两个分类数组可以为空。
- Runtime 的阶段交接上下文提供 `signal` 和 `onActivity`：程序等待子任务或本地导出时传递父任务取消信号，并反馈真实活动；活动绑定父任务身份，沿用原空闲超时规则。交接结果可带 `await_before_prompt`（Promise），表示与上下文压缩并行的程序步骤：Runtime 先登记其错误处理再执行压缩，压缩结束后等待它完成才发送下一阶段提示词；它失败则任务失败，任务取消时按取消原因结束；未提供时行为不变。
- 公共会话工厂先注册本任务的基础工具和全部业务工具，再在首次请求前启用当前阶段工具；Pi SDK 的 `tools` 同时限制注册范围，不能直接用阶段工具子集作为注册列表。后续阶段沿用 `setActiveToolsByName()` 切换，保留同一个 Session 和现有执行前门禁。调用方传 `fixed_tool_list: true`（Session 工厂 `fixedToolList`）时改为一次启用全部工具，`setActiveTools` 只更新阶段门禁，门禁在业务执行前回调之前拒绝当前阶段不可用的工具，并在 system prompt 追加固定说明；`snapshot.active_tools` 表示当前阶段可用工具，`registered_tools` 为实际启用列表。默认关闭，其他任务行为不变。
- Runtime 接收任务或阶段交接的 `prepare_output_files`，在写入阶段输入后，以 UTF-8、仅新建方式在当前工作区准备空白文件；已存在文件保持原样，修复轮不清空或重新预建。提示词要求 Agent 用 `write` 首次填入空文件，内容较多时可分多次写入（之后用 edit 补充），准确使用工作区根目录文件名。目录和模板任务在 `validateOutput` 中检查当前阶段全部必需产物的非空、JSON 和结构要求，校验通过后才将 `validation_result` 交给循环外的 `continueTask` 推进流程。校验不通过按本节“提交校验”的退回规则在原 Session 修复，执行失败仍按 `max_retries`；修复沿用已有内容与用户选择，不重复执行交接副作用。任务通过 `buildRetryPrompt(request, meta)` 提供文件及操作细节：`kind=execution` 接收执行错误，`kind=submission` 接收报告和修复模式；执行异常不伪装为提交问题，修复预算和提示规则由公共层统一管理。
- `agentService.runTask()` 的 `summary_enabled` 默认开启；仅显式传 `false` 时关闭结束总结。公共 Pi 层会让 Agent 在最后一批工具调用上附加 `task_complete=true`，整批成功后直接结束当前阶段；Main 业务任务也可通过 `is_final_tool_call` 回调声明结束工具，此时由程序判断，不向模型提供完成标记。工具失败继续处理，原有结果校验和多阶段续跑照常执行。该参数按调用生效，不写入全局配置，业务调用自行决定是否关闭。技术方案一级目录和完整目录生成、原方案还原、投标模版提取、全局事实生成已关闭结束总结；全局事实 AI 调整保留总结供界面展示。投标模版提取将完整分类写入 `投标模版字段分类.json`，`openxml` 的 `apply-template-fields` 只接收 `fields_file`；工具完成文件结构、候选分类、Word 校验和产物检查后自动结束该任务。`openxml` 工具可选接收 `reportTaskFailure`（由会话工厂注入）和 `onStep` 进度回调。
- Agent 提问由全局 `AgentQuestionDialogProvider` 和 Main 的问答/自动确认服务承接，feature 不实现第二套等待 Promise 或弹窗。
- Agent 不得自行终止任务：`report-failure` 由 `pi/piTaskFailureTool.cjs` 统一改为请求终止，工具先经运行时提问通道向用户展示原因并提醒继续需降低质量，固定选项为“降低质量继续”“终止任务”“补充处理要求”（自定义输入）。用户确认终止才沿用 `AGENT_REPORTED_FAILURE` 结束任务，错误信息追加“（已按您的选择终止任务）”，照常计入 Agent 失败统计和诊断；选择继续或补充要求时，工具向 Agent 返回放宽指令：质量要求均可降低或放弃，唯一底线是写出必需文件并通过程序校验、使流程稳定继续，用户补充要求优先。同一次运行中首次确认允许自动作答（自动选择继续），选择继续后再次请求终止关闭自动作答（`auto_answer=false`），须人工选择。终止确认的回答不写入业务可读的 `user_question_answers`，只记录可见活动。规则在工具层对所有 Agent、所有阶段生效，与该阶段是否开放 `ask-user` 无关，业务提示词中的“调用 report-failure”无需改写；`failure_handled_by_parent=true` 的子会话及没有提问通道的会话（运行环境自检）保持直接报告失败。程序侧提交校验连续阻塞后的终止不在此规则内。
- 提交校验：文件写入不在 write/edit 层校验或拦截，`json_validation_schemas` 仅供 Agent 自查。Agent 结束一轮后，Runtime 先还原受保护文件，再由 `validateOutput` 返回统一报告 `{ value, issues, progress?, minimumGoal? }`：`issues` 每项用 `severity=blocking|quality` 和 `message` 描述问题，其他业务定位字段保留；无问题返回空数组。影响 JSON 读取、产物完整性、HTML 转换或必要图片的错误属于 blocking；字数、一致性、残留表格及未完成格式补写属于 quality。业务校验正常返回报告，文件读取、模型中断及程序异常仍抛出并按 `max_retries` 处理，不消耗提交修复预算。`pi/piSubmissionPolicy.cjs` 为每个阶段统一维护相邻两轮进展：阻塞问题数优先，其均为零时比较质量问题数或业务提供的数值剩余量（字数差额）。一次无改善要求更换方法；连续两次无改善时，只有质量问题则记录后接受，有阻塞问题则降低质量约束并明确最低目标，最后尝试一轮，仍阻塞才终止。删除固定三次总上限；有改善继续修复，同阶段续接不重置，真正切换阶段或暂停后重新运行才重建策略。公共层拼接修复模式说明，业务回调仅补充文件和工具信息。接受时 `report.value` 作为 `validation_result` 传给循环外的 `continueTask`，本次放行问题放在 `accepted_issues`；最终结果保留 `accepted_submission_issues`，不把质量遗留伪称为修复成功。受保护文件仍由 `pi/piWorkspaceBaseline.cjs` 管理，登记的输入、非目标小节、原图和台账在提交前还原并记录活动，图片块比对仍保留。正文主阶段复用一次清单和小节读取，再叠加当前阶段质量规则；审计、去表格、格式补写完成工具只保存提交请求，主流程接受后才推进状态。共用编辑子任务在退出后检查一次产物并回传问题及事实，修复决策归主阶段；独立单节修改仍有自己的主任务提交策略。提交问题涉及超过五节时继续使用 `fix-submission-issues`，其余由主 Agent 直接修改。目录、全局事实、正文编排、原方案还原和模板提取均使用相同报告协议，不兼容旧返回结构。检查复用 `node --test electron/services/pi/piRuntimeService.test.cjs` 与 `node scripts/check-content-generation-agent.cjs`。
- 新的文档导入优先复用 `fileService.cjs` / `parseDocumentWithConfig()`，保留配置中的本地或 MinerU 选择、格式 fallback、图片 scope 和统一错误文案。涉及 LibreOffice 缺失提示时复用 `DocumentParseNoticeProvider`。
- Word 导出统一走 `exportService.cjs` 和 `window.yibiao.export.onWordExportProgress()`；Mermaid/HTML 转图由 Main 本地完成。
- AI 返回的局部文本修改复用 `electron/utils/textEdit.cjs`：未知位置用 `applyTextEdit()` / `applyTextEdits()` 并保持唯一命中，已知范围用 `applyRangeEdit()` / `applyRangeEdits()`；未命中或多命中应返回错误，不把替换内容静默追加到末尾。
- 提示词前缀缓存：模型服务只在请求最后一条消息末尾写入缓存，后续请求仅在消息边界上前缀逐字一致时命中，同一条消息内的相同前缀、内容块拆分、`cache_control` 和 `prompt_cache_key` 均不起作用。多个请求共用的材料单独作为消息并排在变化内容之前，固定规则不放在变化内容之后；并发或连续发出两次及以上时，先用 `electron/utils/promptPrefixCache.cjs` 的 `warmPromptPrefix()` 发送只含该前缀的预热请求（输出上限 1，失败不影响后续请求），预热与正式请求用同一函数构造前缀。正文批处理（`sharedPrefixMessages()`）、招标解析（每段招标文件）、可研正文与审校、知识库 L1 block 前缀及多批条目、废标/错别字/逻辑检查共用的投标文件原文消息均按此组织。
- 排查异常先记录可复现的阶段、输入摘要和错误链：开发者模式模块日志使用 `createDeveloperLogger()` 写到 `userData/logs/<module>/`，AI 请求日志在 `userData/logs/ai/`。可丢弃文件日志通过 `silentFileLog.cjs` 异步写入，日志失败不得影响主流程。

## 仓库级关联代码

`client/` 不依赖仓库内其他旧前后端目录。只有以下仓库级代码需要按改动联动检查：

| 目录 | 何时查看 |
|---|---|
| `analytics/worker/` | 修改事件、字段、模型统计、Agent 运行统计或失败诊断上传协议时 |
| `analytics/dashboard/` | 新增页面路由、配置统计维度或调整 Dashboard 展示时 |
| `sql/workspace_schema.sql` | 修改 `sqliteDatabase.cjs` migration 或目标表结构时；运行时仍以 migration 为准 |
| `.github/workflows/release.yml`、`.github/scripts/` | 修改打包目标、产物命名、构建证明、更新清单或发布渠道时 |
| `openxmlhelper/` | 修改 Word / Open XML 助手协议、任务目录约定或打包进 extraResources 时；细则见 `openxmlhelper/开发说明.md` |

Renderer 埋点入口是 `src/shared/analytics/analytics.ts`，AI 与 Agent 统计分别在 Main 的 `aiService.cjs`、`services/agent/`。埋点失败必须静默，不影响主流程，也不得删除或绕过现有统计。普通 `/track` 埋点不得上传 API Key、Prompt、模型响应、文件内容、文件名或本地路径；Agent 最终失败诊断是独立 `/agent-errors` 链路，由专用进程采集并脱敏诊断包，不得并入普通埋点或随意弱化。新增菜单页面时完成前述 Dashboard 中文名映射。

## 验证清单

| 改动范围 | 最低验证 |
|---|---|
| Renderer / TypeScript | `npm run build` |
| CSS / 页面布局 | `npm run build`，再 `npm run dev` 检查目标窗口尺寸、内部滚动、Dialog 和 FloatingToolbar |
| Main / preload / IPC | 对每个改动的 `.cjs` 执行 `node --check <file>`，再运行 `npm run build` |
| IPC 事件、文件选择、导入、导出、窗口 | 上述命令后用 `npm run dev` 手动走完整链路，并确认取消订阅和进度回放 |
| Store / migration / 后台任务 | 上述命令 + `npm run smoke:electron-native`；手动验证保存、重启恢复、清空与中断状态 |
| 有对应 `*.test.cjs` 的模块 | `node --test <test-file>` |
| 依赖变更 | `npm ci`、`npm run build`、`npm audit` |
| Windows / macOS 打包 | `npm run dist:win` / `npm run dist:mac`；产物在 `release/` |
| Agent 工具或打包内容 | 对应运行 `scripts/verify-agent-tools.cjs`、`scripts/verify-packaged-agent-tools.cjs` |

`npm run build` 出现既有 chunk 体积警告但退出码为 0 时仍算成功。涉及文件路径时至少覆盖 Windows 中文目录；涉及持久任务、IPC 或窗口生命周期时，单纯编译通过不等于验证完成。

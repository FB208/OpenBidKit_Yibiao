# 易标投标工具箱开发说明

本文面向参与 `client/` 开发的成员。具体功能行为以当前代码为准；本文只保留能帮助定位代码、跨进程协作、复用 UI、维护持久状态和完成验证的稳定规则。

## 快速开始

仓库根目录没有客户端 `package.json`，所有客户端命令先进入 `client/`：

```powershell
cd client
npm ci             # 安装依赖；postinstall 会按当前 Electron 重建 native 模块
npm run dev        # Vite 127.0.0.1:5173 启动后打开 Electron
npm run build      # tsc --noEmit && vite build
```

- CI 使用 Node 22，排查本地与发布构建差异时优先对齐该版本。
- `better-sqlite3` 是 Electron native 依赖。出现 `NODE_MODULE_VERSION` 不匹配时运行 `npm run postinstall`；验证 ABI 用 `npm run smoke:electron-native`，不要用普通 Node 进程加载 Store 代替。
- 项目没有统一 lint 脚本，也没有覆盖全项目的 test 脚本；现有 `*.test.cjs` 需按改动范围用 `node --test <file>` 定向执行。

## 运行结构

```text
src/main.tsx
├─ 开发者独立窗口（由 ?window=... 选择）
└─ AppProviders
   └─ WorkspaceDatabaseGate
      └─ App
         └─ AppShell + AppRouter

Renderer
  └─ window.yibiao
      └─ electron/preload.cjs
          └─ electron/ipc/*.cjs
              └─ electron/services/*.cjs
                  ├─ SQLite Store / 配置
                  ├─ 文件与导出
                  └─ AI / Agent / 后台任务
```

- Renderer 是 Vite + React + TypeScript ESM；Electron Main、preload、IPC 和 Main 服务是 CommonJS，保持 `.cjs`。
- 主窗口启用 `contextIsolation`、关闭 `nodeIntegration`。Renderer 不导入 `electron`、`fs`、`path`，也不直接使用 `ipcRenderer`，本地能力统一通过 `window.yibiao`。
- Renderer 负责页面状态和交互编排；Main 负责配置、SQLite、文件解析、AI、Agent、后台任务、导出、插件和更新。
- `WorkspaceDatabaseGate` 在数据库检查、迁移和历史清理完成前阻止业务页面挂载；数据库相关 IPC 也会先注册为 pending/unavailable handler。
- `AppRouter` 是基于 `SectionId` 的组件分发，不是 URL 路由。不要按 React Router 的约定添加页面。

## 代码放在哪里

| 位置 | 职责 |
|---|---|
| `src/app/` | 应用级路由、菜单、全局 Provider、数据库 Gate、启动提示与状态条 |
| `src/components/` | 应用壳层组件，目前主要是 `AppShell`、`Sidebar` |
| `src/features/<feature>/` | 功能页面及其专用组件、Hook、类型和 Renderer 轻量编排；目录按实际复杂度创建，不补空层级 |
| `src/shared/ui/` | 跨功能 UI 组件和全局交互 Provider |
| `src/shared/types/` | 跨功能类型、导航类型和 `window.yibiao` bridge 类型 |
| `src/shared/prompts/` | 仍在 Renderer 使用的 Prompt builder |
| `src/shared/utils/`、`src/shared/markdown/` | 跨功能纯工具和 Markdown 渲染辅助 |
| `src/styles/` | token、壳层、共享组件和各 feature 样式；`src/styles.css` 是唯一总入口 |
| `electron/main.cjs` | 窗口、协议、应用生命周期和 Main 入口 |
| `electron/preload.cjs` | 主窗口 bridge；拖拽文件路径也在这里通过 `webUtils` 暴露；插件配置窗另用 `preload-plugin-config.cjs` |
| `electron/ipc/` | IPC 注册与参数转发；`index.cjs` 负责服务装配和数据库生命周期 |
| `electron/services/` | Main 业务服务、Store、任务实现；`agent/`、`pi/`、`doc2markdown/` 是专用子层 |
| `electron/utils/` | Main 纯工具、路径、日志、队列、文本编辑和导入图片清理 |
| `electron/resources/` | 打包进入客户端的 Agent 指令、许可证公钥和构建证明 |
| `vendor/agent-tools/`、`scripts/` | 随包 Agent 命令工具及构建/校验脚本 |

放置原则：

- 只被一个功能使用的代码留在该 feature；出现真实跨功能复用后再上移 `shared/`。
- `shared/` 的运行时代码不要依赖 feature。现有 `shared/types/ipc.ts`、`shared/types/index.ts` 会组合或转出部分 feature 类型，这是 bridge/type 边界的现状，不应扩展成 shared 引用 feature 组件或服务。
- Renderer 的 `services/` 只做 bridge 调用或轻量编排；耗时流程和权威持久化放 Main。
- 新业务 IPC 默认保持薄。`ipc/index.cjs` 的生命周期装配以及 `pluginIpc.cjs` 的现有插件市场/配置编排是例外，不要把它们复制成普通功能模板。
- Prompt 不写进组件：Renderer Prompt 放 `src/shared/prompts/`，Main 后台任务的 Prompt 与对应任务服务放在一起。

### 新增菜单页面

至少同步检查以下位置：

1. `src/shared/types/navigation.ts`：增加 `SectionId`。
2. `src/app/menuConfig.ts`：配置一级或二级菜单。
3. `src/app/AppRouter.tsx`：注册页面分发。
4. `src/components/Sidebar.tsx`：为 `navigationIcons` 补齐图标映射。
5. `analytics/dashboard/public/src/pages/traffic.js`：为新增埋点路由补中文显示名。

一级菜单有 `children` 时，`AppRouter` 会使用 `shared/ui/SecondaryMenuPage.tsx` 显示二级入口，不在侧边栏实现展开菜单。设置页是侧边栏底部的独立入口。

## Renderer 与 Main 协作

新增或修改 bridge API 时按完整链路更新：

1. 在 `electron/services/` 实现业务能力或 Store 操作。
2. 在对应 `electron/ipc/*Ipc.cjs` 注册通道，并在 `electron/ipc/index.cjs` 装配依赖。
3. 若通道依赖工作区数据库，同时加入 `index.cjs` 的 `workspaceDatabaseChannels`，确保数据库就绪前不会漏注册或重复注册。
4. 在 `electron/preload.cjs` 暴露方法或事件。
5. 在 `src/shared/types/ipc.ts` 同步参数、返回值和事件类型；全局声明由 `src/vite-env.d.ts` 引用该类型。

其他约定：

- `onXxx` 事件 API 必须返回取消订阅函数，React effect 卸载时调用。
- 受管任务页面先读取 Store 快照，再订阅 `tasks.onTaskEvent()`，随后调用 `tasks.getActiveTasks()`；后一步会再次订阅并回放活动任务，避免首次事件早于 listener 注册。
- IPC patch 以“字段是否存在”为语义：字段缺失表示保留，字段出现表示应用该值；`undefined`、`null` 或空集合通常用于显式清理，具体由对应 Store 定义。Renderer 合并 patch 时使用 `hasOwnProperty`，不要用 truthy 判断。
- 命令接口可能返回 `void`、实体或局部 patch，不假定每次写入都会返回完整工作区；需要全量状态时显式调用 `load*` / `get*` / `list*`。
- 拖拽得到的浏览器 `File` 通过 `window.yibiao.file.getPathForFile(file)` 转为本地路径，不读取非标准 `file.path`。
- 外部链接通过 `window.yibiao.openExternal()`；本地导入图和生成图使用 Main 注册的 `yibiao-asset://imported-images/...`、`yibiao-asset://generated-images/...`，不要向 Renderer 暴露 `file://` 路径。
- 只在用户输入和外部响应边界做必要校验；Renderer、preload、IPC、service 之间不重复堆叠同一套内部参数校验。

## 数据与后台任务

### 持久化位置

| 数据 | 位置 / 权威实现 |
|---|---|
| 用户配置与 API Key | `userData/user_config.json`，由 `configStore.cjs` 管理 |
| 结构化业务状态 | `userData/workspace/yibiao.sqlite` |
| 导入/解析源 Markdown、图片及文件型产物 | `userData/workspace/<feature>/`、`imported-images/`、`generated-images/` |
| Pi 运行环境和持久任务 | `userData/agent-runtime/pi/` |
| 开发诊断日志 | `userData/logs/` |
| 插件与插件配置 | `userData/plugins/`、`userData/plugin-configs/`、`userData/plugin-states.json` |

- 核心工作区、配置、日志和 Agent 路径集中在 `electron/utils/paths.cjs`；新增核心路径优先补在这里。插件自身路径目前由插件服务管理。
- Main 文件读写显式使用 UTF-8，并以 Windows 中文路径为常规场景。
- SQLite 建表、升级、健康检查和备份逻辑以 `electron/services/sqliteDatabase.cjs` 为运行时权威。改表时增加 migration，并同步仓库根目录 `sql/workspace_schema.sql` 的目标结构。
- 数据放 SQLite 还是文件系统由对应 Store 定义：导入源 Markdown 和图片通常是文件，技术方案正文则以 `technical_plan_outline_nodes.content` 为权威。不要按文本大小另建平行 JSON 缓存；删除文件型资源时同步清理其导入图片 scope。
- 不在 Renderer 保存业务状态、草稿或密钥。当前 `localStorage` 只用于远程公告已读标记，以及旧 analytics client id 向配置文件迁移。

### 单小节重新生成

正文页单节重新生成由 `contentSectionRegenerationTask.cjs` 续接原正文持久 Session，复用现有 `content-generation` 任务类型和入口，不删除会话或工作区。提示词只提供目标小节当前标题、编号、稳定 ID、HTML 路径和用户修改要求，不主动加入其他小节内容或参考指令。Agent 使用 Pi 原生 edit 和原有三类图片工具，不重新编排、还原、检查全文字数或执行一致性审计，也不改写全文结果清单；原审计状态保留。本次只修改目标正文，未要求调整的图片与内容保留，原方案表格和图片继续保留。

程序读取目标 HTML，复用格式、图片引用检查及字数统计，然后按会话中的模板配置仅转换该小节正文，不插入目录标题，覆盖业务目录中同一稳定 ID 的 Word。其他小节文件及转换记录不变，目标转换成功后刷新预览。运行时沿用 target_item_id、regenerate_requirement、phase 和 html_output，不新增表或字段；修改阶段暂停/失败继续原 Session，转换阶段失败只重试转换。提交中、运行中、正在暂停及已暂停期间禁用全部小节重新生成入口，Main 沿用任务互斥。会话或目标 HTML 不存在时明确报错，不自动重建。运行 `node scripts/check-content-section-regeneration.cjs --real-word` 检查真实 Pi 原生编辑、会话续接、互斥、暂停重试及单节 Word 更新。

### 长任务模型

正文任务启动入口在准备运行态、任务落库和清理旧会话前，读取 Step02 已保存的配图设置。有图模式且开启 AI 配图时，仅读取 `user_config.json` 中当前渠道的 `image_model.status`；不是 `available` 就阻止启动并提示“去设置-生图模型中点击测试，并配置可用渠道”，不发起模型测试请求。无图或关闭 AI 配图不检查；普通生成无待办时仍直接返回已有结果。运行 `node scripts/check-content-generation-output.cjs` 检查该启动规则。

正文生成已移除“忽略失败小节，继续后续流程”：不再提供忽略按钮、确认弹窗和后台请求，不再使用 ignored 小节状态、等待用户选择或忽略数量字段。只有 success 表示小节完成，失败与未完成小节不从生成范围或字数统计中排除。正文生成、单节修改、一致性审计、去表格失败均使用现有原会话重试，Word 转换失败只重试转换；整本导出仍按当前目录读取全部 AI 小节 HTML。此次仅删除功能及其点击上报，其他埋点和服务端历史统计保留，不迁移、清理或重置历史数据。

正文首次生成、新增小节生成及全文重新生成在任务首次落库前统一准备运行时，清除上一轮单节目标、修改要求及执行阶段，从编排阶段开始。新增小节生成保留已有小节状态、字数和 Word 登记；全文重新生成按原规则删除旧正文 Session，并在首次落库时清空旧正文、编排、字数及转换记录，重建待生成状态。继续和失败重试保留当前运行时及 Session，不执行新任务初始化；即使首次落库后、runner 第一次 checkpoint 前退出，重启也按本轮任务恢复。启动恢复检查包含在 `node scripts/check-outline-content-state.cjs` 和 `node scripts/check-content-generation-output.cjs` 中。

`taskService.cjs` 统一管理技术方案、标书查重和废标检查任务；三个业务组当前均为组内互斥。知识库是明确例外：`knowledgeBaseService.cjs` 按文档维护 preparation/matching 活动集合，并通过 `knowledge-base:event` 推送。Word 导出也有独立的进度事件。

知识库全局检索使用 `knowledgeBase.search({ keyword, page })`，页码从 1 开始，返回 `{ items, total, page, pageSize }`，每页 100 条。`total` 与当前页在同一 SQLite 读事务中查询；数据减少导致页码越界时返回最后一个有效页。Renderer 使用返回页码和总数展示，翻页沿用已提交关键字，失败保留上次成功页，清空搜索使未完成请求失效。检索仍是 Main 同步子串扫描，分页不代表全文索引或后台线程查询。

受管任务遵循以下流程：

1. Main 创建 running 任务并持久化初始状态。
2. 无恢复价值的高频进度调用 `updateTask()`，只更新 Main 内存并推送事件。
3. 阶段结果调用 `checkpointTask(taskPatch, workspacePatch, eventPatch)`，在 Store 事务中一次提交任务和业务 patch，成功后再推送同一份局部事件。
4. 页面卸载不取消任务；重新挂载从 Store 和活动任务回放恢复展示。
5. 应用重启后的恢复策略由 `taskService.cjs` 按任务类型决定：正文任务可转为 paused，目录等待选择仅在持久 Session 完整时恢复，其余中断任务通常转为 error。Renderer 不自行把残留 running 状态改成 idle。

会清空任务或下游结果的 Main 命令，必须先取消相关活动任务并等待 runner settled，再提交 Store；取消后的 runner 不得继续 checkpoint。技术方案和废标检查的导入、删除、重置已经通过 `taskService` 的 `beforeCommit` 链路处理，新入口应复用该模式。

## 技术方案关键不变量

原方案覆盖审计、旧全文图片编排及后置配图流程已移除，包括重新配图入口、专用进度、计划与图片项目存储；原方案还原、生成时保留原文表格和图片、新版 Agent 配图工具与图片保护继续保留。一致性审计及去表格在正文持久主会话中完成。新建数据库不再创建旧配图计划/项目表及三类图片上限列，启动修复也不要求它们存在；已有表、列和数据不迁移、不主动删除，历史迁移编号保持不变。

全流程“重置”先复用 `taskService` 取消并等待后台任务退出、关闭 OpenXmlHelper，再由 Store 整体删除 `workspace/technical-plan/` 和该流程专属的生成图片、导入图片、持久 Agent 会话，按业务表清空流程记录并恢复初始配置。该入口不按小节 ID 暂存或删除 Word，未登记的 Word、暂存文件和提取的投标模板均随专属目录清除；用户原始上传文件、共享知识库、公共模板库、全局配置及其他业务数据不清理。正文阶段重置、全局事实保存、目录修改仍遵循原有局部失效范围。Renderer 对全流程重置、正文阶段重置、全局事实保存和目录保存统一在 `finally` 中重新读取完整状态并替换页面快照，操作失败也刷新 Word 预览上下文；原操作错误继续提示，刷新失败单独说明且不提示重置成功。

技术方案统一使用 `technical-plan` 入口；Step02 可选上传已有方案，目录、全局事实和正文阶段以 `originalPlanFile` 是否存在决定是否启用原方案扩写能力，不再维护独立扩写入口或工作流开关。

项目级生成配置统一保存在 `technical_plan_generation_config`、`technical_plan_generation_bid_tasks` 和 `technical_plan_generation_reference_docs`，Main 通过 `technicalPlanStore.loadGenerationConfig()` / `saveGenerationConfig()` 读写，Renderer 使用同名 `window.yibiao.technicalPlan` API。Step02“长嘛样”在配置初始化或全流程重置后默认选择系统模板“标准投标简版”（`tpl-system-standard-bid`），不自动改写已有配置。Step02 的“写嘛”复用 `outlineMode`：`response-file`、`standalone-technical`、`standalone-business` 分别表示完整投标文件、技术文件独立成册和商务标独立成册；“我有方案”保存 `outlineExpansionMode`，“知识库”保存 `referenceKnowledgeDocumentIds`，“写多少”保存 `outlineWordControlOptions` 和 `contentGenerationOptions.tableRequirement`，“插图吗”保存 AI、Mermaid、HTML 配图字段，“怎么写”保存 `globalFactsMode`。选择、开关和下拉框改变后立即保存，数字或文本输入在失焦或按回车后保存；每次成功均提示“保存成功”。目录生成页、全局事实设定页和正文生成页不再维护这些生成设置，点击生成或重新生成时直接使用 Step02 已保存配置。一致性审计在正文持久主会话内完成；选择“不要表格”时，审计结束后在同一会话中将数据表格转换为普通文字，再转换 Word。正文生成页不再提供配置弹窗。开发者模式下，正文页操作区提供“重置正文阶段”。正文任务启动前修改生成配置只更新存储，不清空已有结果；正文任务一旦启动（含编排、还原阶段），Step02 除“长嘛样”外统一锁定。暂停、失败、完成及重启后保持锁定，目录增删改不解锁；明确重置正文或确认修改全局事实并清空正文后解锁。锁定状态复用正文运行时保存，不另建配置表。模型、API、文件解析器和 Word 导出样式仍属于全局 `user_config.json`；目录字数生效快照、任务运行时和业务结果不属于可编辑生成配置。

正文编排的 `正文编排目录.json` 是只读参考，包含完整目录及已有编排；Agent 单独将本轮目标写入 `正文编排结果.json`，格式为 `{ "plans": [{ "id": "目标小节稳定 ID", "content_plan": { ... } }] }`。每项只返回写作重点、目标字数、知识条目、表格安排和配图适配评分，不复制标题、编号、描述或父子结构，也不输出程序计算的 `image_needed`。程序在模型输出边界校验结构、目标完整性、重复及非目标 ID、知识引用和表格用途，按当前目录顺序建立 ID 映射后沿用字数校正与局部保存。新一轮编排清空结果，同一轮在编排阶段暂停或失败后继续时保留草稿；输入参考按当前目录刷新。不接受旧版整目录结果，不新增兼容解析或数据迁移；已保存编排的数据结构及版本不变。总结和 JSON 自动校验开关保持原状。运行 `node scripts/check-content-planning.cjs` 和 `node scripts/check-content-generation-output.cjs` 检查精简结果、局部保存、字数传递及继续任务。

原方案还原统一使用 Agent。仅当 `technical_plan_meta.original_plan_markdown_path` 非空（Main 对应 `originalPlanFile.markdownPath`）时读取原方案、执行还原和计算还原率；无原方案不扫描来源记录，也不展示还原率。`originalPlanRestoration.cjs` 将完整原方案、由 `numberMarkdownLines()` 生成的 `original-plan-numbered.md` 行号视图、目标目录和项目背景放入 Agent 工作区，不按标题或固定字符数预分段。完整行号视图另按 UTF-8 大小切成约 40KB 的固定读取分片，并生成只作导航的 `original-plan-index.md`，列出分片与真实行号范围、表格范围、图片行和候选标题行；同一真实行的展示片段可以跨相邻分片，语义判断仍以完整材料为准。首次任务的输入文件已完整列出，通常无需先执行 `ls`；继续任务仍先检查已有输出。提示词说明各文件用途和读取顺序：先了解目标目录、项目背景和已有覆盖范围，再用导航索引定位，随后按编号处理行号分片；具体工具调用和读取节奏由 Agent 自行安排。完成必要阅读和语义判断后优先直接写入结果，不先展开完整文字版映射，也不只为确认程序生成的首尾行号额外运行 `bash`；发现读取异常、索引或行号冲突、判断存疑或校验失败时，仍可自行复核。超长物理行在行号视图中使用同一 `L` 编号和分片序号，Agent 按真实 `L` 行号输出小节来源范围、标题处理以及未还原范围，不输出正文 `content`；无行号原文仅供必要时核对 Markdown 结构。目标小节允许没有对应原文；同一段原文优先只分配到最合适的小节，大型表格、成组图片、证书和清单等大块材料只有在多个目标小节都确实需要完整保留时才复用，不因主题相关或填补空小节而重复。纯空白签字、职务、日期、盖章栏及不属于方案正文的评标提示可列入未还原范围；实际授权、资质信息、证书标题和图片仍须还原。程序使用原始 `source.lines` 和 `restoredAssignmentContent()` 按声明范围逐字重建正文，避免 Agent 复制、转义或改写原文。标题去留和重新编号由 Agent 按新目录结构判断，保留标题含义及年份、型号、“3D”等文字；外层标题由程序生成，内部标题用单行加粗文字表示。Agent 在 `heading_edits` 中记录独立标题的原文行号 `line` 和处理后的完整标题 `content`，空字符串表示删除该标题行；无标题时填空数组。标题记录不得指向表格或图片行。原方案优化扩写提示同步采用新标题约定，普通正文生成规则不变；新 Schema 不接受旧输出中的正文 `content`，改造前暂停的还原任务需要重新开始，不做兼容。校验单节来源范围有序且不重叠、表格未切断、非空原文行均有去向；仅标题无正文或图片不算实质还原，图片不能列入未还原范围。错误交回 Agent 修正，通过后保存。单节或部分重生时，其他小节的有效来源范围写入 covered-ranges.json，仅用于核对全文覆盖情况；程序不对跨小节来源重叠报错。已覆盖原文不能同时列入未还原范围。移除旧分段记录复用和重建逻辑，通过 `completed_stages` 的 `restoring` 标记跳过已经完成的还原阶段，保护后续扩写正文；旧分段数据不兼容，已有任务需要重新执行还原。

还原率在回填保存后计算：已还原原文可读字数 ÷ 完整原方案可读字数，按来源行范围并集统计，同一原文行被多个小节采用也只计算一次；分子分母统一复用 `countReadableWords`，不统计新增目录标题、结构标记或后续扩写字数。统计保存在正文任务 `stats.content.original_restoration`，包含 `source_hash`、`total_words`、`restored_words`、`rate`，以及图片引用数量 `total_images`、`restored_images`；图片单独显示“已还原/总数”，同样按来源行范围并集统计引用数量，不纳入字数比率。进度快照只携带统计，不重复扫描。继续任务保留同一原方案的统计，全文重新生成重新统计。正文页顶部显示一位小数和悬浮说明，未统计显示“待统计”，总字数为零显示“—”；替换原方案后指纹不匹配时显示“待统计”，移除后隐藏。新来源记录使用 `source_hash` 和 `source_ranges`，后续原方案优化扩写读取新记录。此指标只反映还原阶段的原文覆盖率，不保证后续扩写保留率。

正文事实模式由 `contentGenerationAgent.cjs` 统一翻译：`正文编排决策.json` 保留 `global_facts_mode`，并在 `global_facts_requirements` 保存当前模式的中文要求。主 Agent 阅读该要求，并发正文生成及共用编辑子任务直接接收同一段说明；不要求模型猜测英文枚举含义。资料核对按工具能力区分：主 Agent 检索并提供参考摘录，无文件工具的并发写作模型只核对请求内的材料，编辑子 Agent 按需读取工作区文件。字数要求直接根据现有 checkTotalWords 生成为明确的中文任务范围，不让并发写作模型推测未提供的字段。允许补充缺失事实不代表可以覆盖全局设定；审计仅按已有依据统一口径，不靠重新猜值解决矛盾，去表格仍只改变表达形式。新任务或新一轮目标创建输入时写入，暂停恢复不补写历史快照。受限 HTML 规范说明画框比例与 contain/cover：完整展示流程图、信息图和原图时明确使用 contain；生图服务尺寸不明确时省略 size，沿用主程序配置。

当前首稿试验：正文编排使用目录生效字数快照，有上下限时以中点为基准，仅有下限取 120%，仅有上限取 80%。Agent 为目标 AI 叶子提供 `content_plan.target_words`，首次全文生成及主动全文重新生成由程序按篇幅比例校正整数总和，合计等于基准；没有全文目标时沿用 `sectionWords`，都未设置时为 0。正文启动后新增或重新成为 AI 叶子的待生成小节，复用 `pending_item_ids` 识别，提示词及程序分配均固定每节目标为 3000 字，不按全文基准或 `sectionWords` 重新分配；继续局部编排写作重点、表格和配图，保留其他小节已存目标。首次生成前新增目录不使用该固定目标，主动全文重新生成清空待生成范围并重新分配全文；暂停和失败重试复用已保存编排。固定目标不保证连续新增后仍满足全文上限，也不保证实际输出恰好 3000 字。计划版本为 6，不补齐或迁移旧计划，验证新流程需使用现有正文重置/全文重新生成入口。每节生成直接接收已保存目标；还原底稿超过本节目标时优先保留实质内容。`contentGenerationAgent.cjs` 的 `WORD_ADJUSTMENT_ENABLED=false` 仅关闭主流程的扩缩写工具入口、提示入口和不达标续跑入口，原扩缩写实现及下述能力说明保留。仍统计实际字数、检查小节与图片完整性并启用图片保护，内容完整即进入原有审计；目标和首稿实际总字数写入任务日志。试验期间不保证最终字数达标，审计及格式补写仍可能改变最终字数。

原扩缩写能力（当前试验停用入口）：正文总字数检查与扩缩写在上述持久 Pi 主会话内完成，旧的独立小节/全文字数调整阶段、重试算法、回写补丁、进度状态及“强控小节字数”选项已移除；每小节建议字数仍用于目录规模与写作参考，不设置单节硬性上下限。字数上下限使用目录生效快照，任一边界可不设置；全文生成检查总字数，单节或局部重新生成只报告本次实际字数，不把全文目标交给部分小节。所有并发任务结束后，主 Agent 调用 `check-word-count`，由 `contentGenerationWordTools.cjs` 读取目标 HTML 的实际可读文字，排除标签、图片提示词及未完成文件，返回各节字数、总字数、上下限与距离要求范围的差额。差额大于 10000 字时，主 Agent 调用 `adjust-sections` 分配不同小节的增减要求；差额小于等于 10000 字时，主 Agent 直接使用 Pi 原生 read/edit 微调。每轮全部完成后重新计数并选择方式，直到达标，不设固定调整轮数；最终提交仍未达标则使用 `continueTask` 继续同一主会话，达标后进入同一会话的一致性审计，审计结束后按设置去表格，再执行格式自检并进入原有 Word 转换。要求保留原表格、原图、实质信息和承诺，事实冲突以全局事实设定为准；无法在保留要求下达标时报告失败。

并发扩缩写使用短生命周期 Pi 子会话，其模型请求沿用现有 Pi→aiService 链路和父任务的队列/取消作用域；不是让 aiService 自行解释编辑指令。子会话借用主会话工作区，只启用原生 read/edit 和 report-failure，直接修改分配的小节文件，仅向主会话返回状态及错误，不返回补丁让主会话再次编辑。各子会话拥有独立会话目录，不取得主会话身份；通过 failure_handled_by_parent: true 标明错误由主 Agent 处理。子任务失败仍记录运行统计并返回错误，供主 Agent 重试或重新分配，不单独启动最终失败诊断上传；主任务最终失败时仍沿用完整诊断上报，其他 Agent 任务保持原有行为。结束或失败清理只作用于子任务自己的目录，保留共享的主会话工作区。未命中编辑交给该子会话读取最新原文后修正；暂停保留已写入的正文，继续后重新读取并计数。不新增旧数据兼容或自动数据重置。运行 `node scripts/check-content-word-adjustment.cjs` 检查字数边界、并发等待、Pi 原生编辑、多轮继续、取消、共享工作区生命周期、子任务失败不上报且运行统计保留，以及主任务和普通任务最终失败仍上报。

扩缩写、一致性修复、去表格和格式补写共用 contentGenerationEditTools.cjs 的并发编辑及图片保护，使用 Pi 原生文件操作扩展点，不重写文字匹配或替换算法。该模块 在原生 edit 的同文件队列内取得本次原文，Pi 计算新内容后、真正写盘前，对比全部已有图片块（包括原图、新图、图注和提示词）、图片顺序、外层容器及图片表格结构；禁止图片被删除、替换、复制、调序、移入不可见容器或改变布局，允许扩缩写图文表格中的普通说明文字。拒绝时整次编辑不落盘，错误交给调用方 Agent 继续修正。正文及配图完整后首次 check-word-count 启用保护，adjust-sections 入口及提前提交后程序要求继续调整也启用；word_adjustment_started 保存在既有持久任务检查点，暂停恢复即恢复权限。主 Agent 在保护阶段只能 edit 本次正文，write/edit 可保存结果清单；子 Agent 只能 edit 自己的小节。命令、正文重生和配图工具停止开放，Pi 的 beforeToolCall 同时拦住当前轮已排定的禁用调用。公共文件操作包装 withFileWriteHooks 提供可选写入前回调，保留原有写入后 JSON 自动校验；未设置回调的其他任务维持原有行为。检查脚本使用真实 Pi 自动工具循环和原生 edit、模拟模型响应，覆盖拒绝后原文件及 BOM/CRLF 不变、正常扩缩写、图文表格/三列图/四宫格、主子任务、工具绕过、暂停恢复和 JSON 校验。

正文一致性审计由生成正文的同一持久 Pi 主 Agent 执行，位于全部正文、图片和总字数调整完成之后，Word 转换之前。程序在首次进入审计、进入下一轮和恢复未完成审计时，按目录中的 targets 顺序读取最新小节 HTML，生成只读的 `正文一致性检查汇总.txt`，标明编号、标题、稳定 ID 和原文件路径；复用 `numberMarkdownLines()` 保留完整内容并分拆超长行，表格、图片标签及提示词不做摘要或删减。主 Agent 首先阅读汇总，自行安排分段读取，不要求一次读入全部内容；核对项目概述、全局事实、已还原材料及按需检索的已选知识库，并检查正文内部及跨小节的事实、参数、时间、职责与承诺是否矛盾；冲突以全局事实设定为准，依据不足则记录未解决问题。单节或局部生成只汇总和审计本次输入，不声称覆盖其他正文。主 Agent 统一修复口径后可直接原生 edit，或调用 `repair-sections` 并发分配不同小节修复；修改仍写入原小节 HTML，轮内修复核实读取最新原文件，不使用汇总快照判断修复结果。汇总由程序刷新，沿用现有图片保护中的可写目标限制，Agent 不可编辑。一致性修复调用共用编辑函数时启用 `preloadInput`：每次派发（含失败后重新派发）直接读取本小节最新完整 HTML 和完整受限 HTML 规范，与事实处理要求及主 Agent 的修复指令一起提供给子会话，不使用审计汇总快照，不摘要或删减材料。材料充分时子会话可直接 edit，仍可按需补读资料及在编辑失败后读取最新文件自行修正；修改后的核实以最新原文件为准。该参数默认关闭，扩缩写、去表格和格式补写沿用原读取方式。子会话仅编辑自己的 HTML，复用图片写入前保护、队列、取消与父任务处理失败的约定，不回传补丁。子任务未完成或失败时不允许提交本轮结论，失败小节重试成功后才能结束本轮。

每轮审计及修复后由主 Agent 核实修改位置与关联内容，调用 `complete-consistency-round` 提交结论和剩余问题。无问题提前完成，有问题继续下一轮，最多三轮；第三轮后停止，保留未解决问题并写入任务日志，进入可选去表格和格式自检，不把残留矛盾伪称为全部修复；执行错误仍按失败处理。轮次、状态、剩余问题和未完成修复小节保存在原有 Pi 持久任务 state.consistency 中，暂停或失败恢复沿用当前轮次，不新增表或跨会话档案。页面显示轮次，审计失败从原正文主会话继续，不走旧内容矫正入口。审计阶段停用字数检查及扩缩写工具，继续流程直接处理审计结论，修复后不再检查字数上下限，仅为展示统计最终实际字数。旧的独立审计 Agent、合并 Markdown、标记解析回写和部分输出恢复已移除；Word 转换及后续流程保持原样。运行 `node scripts/check-content-consistency.cjs` 检查轮次上限、恢复、提前结束、并发修复、图片保护、失败重试及审计后不再检查字数。

正文去表格由 `contentGenerationTableTools.cjs` 在同一主会话中执行：输入快照的 `table_requirement=none` 时，一致性审计后进入 `table-cleaning`，其他档位进入格式自检。主 Agent 检查本次 targets 的全部 HTML，调用 `remove-section-tables` 按小节并发转换；每个子任务使用 Pi 原生 edit，将数据表格（包括原方案表格）改成段落或列表，完整保留表头对应关系、数值、单位、条件、备注与承诺。imageText、threeImages、fourImages 图片表格整块保留，继续使用已有图片保护；只有去表格任务允许改变原数据表格的表达形式。子任务失败由主 Agent 重试，完成小节即时登记到原 Session 的 `state.table_cleanup`，暂停/失败继续原会话，不重跑审计或调整字数。主 Agent 核实后调用 `complete-table-cleanup`，检查所有目标无遗漏数据表格才进入格式自检；无数据表格也须提交完成。页面按已处理小节展示进度，最终实际字数从修改后的 HTML 重新统计，HTML 不回写数据库。旧数据库正文去表格、字符范围补丁和跳过失败表格逻辑已删除。运行 `node scripts/check-content-generation-agent.cjs` 与 `node scripts/check-content-generation-output.cjs --real-word` 检查原生并发编辑、图片表格保留、失败/暂停续接和最终 Word。

Step02“插图吗”保留 AI、Mermaid、HTML 三类图片开关、示例预览和 HTML 高级设置，不再显示三类生图上限输入框。“图片数量”保存为 `contentGenerationOptions.imageQuantity`（SQLite 的 `image_quantity`），取 `none`（无图）、`light`（少图）、`heavy`（多图），默认少图，切换立即保存。切换无图时同步关闭三类开关；切换少图或多图时同步打开，AI 生图仍受现有模型可用性限制。联动只发生在档位切换时，用户随后可单独调整类型开关。档位继续用于编排后的配图标记计算，并与开关和 HTML 类型一起传给正文 Agent。旧的三类图片数量上限已移除；档位用于计算本轮新增布局名额，正文主 Agent 根据上下文分配到小节。

容易遗漏的状态规则：

- 招标文件的完整合并原文保存在 `technical-plan/tender-original.md`，当前投标范围工作副本是 `tender.md`，单份来源 Markdown 在 `tender-files/`；Word 原件（`.docx`，或由 `.doc`/`.wps` 转换）在 `tender-originals/`。切换标段会从原文重建工作副本并清空下游。旧工作区没有原件时须重新导入。
- 目录属性使用“通用、商务/资信、技术、其他、目录、报价、业绩”，叶子处理模式使用 `ai-generate`、`template-fill`、`directory-generate`、`manual-fill`、`other`。Agent 生成一级目录时固定将商务/资信与业绩标记为 `template-fill`、目录标记为 `directory-generate`、报价标记为 `manual-fill`；确认弹窗仍允许分别调整属性和处理模式。一级目录弹窗按生成范围设置默认选择：完整投标文件选择全部，技术文件独立成册选择技术目录，商务标独立成册选择 `template-fill`、`directory-generate` 和 `manual-fill` 目录。一级目录确认后，存在 `ai-generate` 根目录时 Main 恢复原目录生成 primary Session 继续生成完整目录；没有时直接保留用户选择。仅当确认结果中存在 `content_mode=template-fill` 的一级目录且存在招标 Word 原件时，才额外创建独立普通 Session，并只传入这些“模板填写”目录执行投标模版提取；`directory-generate`、`manual-fill`、`ai-generate` 和 `other` 均不参与抽章、字段标注或 AI 正文生成。相关任务都返回成功后目录业务任务才完成；没有模板填写目录或 Word 原件时自动跳过模版提取，技术文件独立成册只走目录生成。模版提取普通 Session 调用 `openxml` 依次列块、抽章、扫描待填候选并写入 `w:sdt`，成对生成 `technical-plan/bid-template.docx` 与 `technical-plan/bid-template-fields.json`；原文标题块 `heading=false` 时必须用 `startBlock` / `endBlock` 明确章节边界，不能用忽略候选掩盖误抽取章节。细则见 `openxmlhelper/开发说明.md`。
- 技术方案目录从生成阶段起区分身份和编号：`id` 为程序生成的 UUID，`number` 为按目录树位置计算的显示编号；`parent_node_id` 和 `sort_order` 仍是数据库的层级和顺序依据，不新增编号存储字段。Agent 新节点填 `id:null`，程序在阶段交接时分配 ID 并写回会话；已有节点必须原样保留 ID，评分规划及叶子分配通过 `root_id` 引用稳定的根节点 ID，不再维护 `branch_id`。技术方案使用独立的 `TechnicalPlanOutlineItem` / `TechnicalPlanOutlineData` 类型，不改变可研目录身份协议。
- 正文编排、原方案还原、生成工具及结果清单使用稳定的 `id` / `node_id` / `section_id` 关联；提示词和页面显示使用 `number`。正文 HTML、还原底稿和业务目录内每小节 Word 均按稳定 ID 命名；转换失败后排序再重试不会改变输入输出归属。此次改造不兼容旧目录和产物，不迁移、不做升级重置或历史清理；用户自行执行现有重置操作。
- 目录结构和非 AI 节点正文的权威来源是 `technical_plan_outline_nodes`，Renderer 对应 `outlineData.outline[*].content`；`contentGenerationSections` 主要保存生成状态和错误。新正文 Agent 的受限 HTML 保存在持久会话工作区，整本 Word 导出直接读取这些文件，不额外保存 HTML 到数据库。

- `saveOutline()` 的 `reason` 是持久化协议：`replace` 清空全部旧正文；`edit` 只更新标题，保留正文和编排；`delete`、`add-root`、`add-child` 结合稳定节点 ID / `affectedNodeIds` 只清理受影响节点。叶子下添加子目录清空原叶子正文和编排；删完全部子目录后，父节点成为 AI 叶子并重新编排、生成。`sort` 只更新目录顺序，显示编号按树位置重新计算；节点 ID、正文、编排、图片关联、运行时及小节 Word 文件名保持不变，不执行 ID 重映射或 Word 换名。不要省略 `reason`，否则 Store 会按 `replace` 处理。
- 目录改名保留正文任务和运行时；局部增删清理本轮任务进度，但保留正文持久 Session 和工作区，按当前有效 AI 叶子 ID 保留未受影响小节的成功状态、编排、`section_words` 与 Word 转换记录。新增及重新成为叶子的节点加入待生成列表并跳过原方案还原；已删节点的 HTML、图片和 Word 允许留为孤儿文件，导出只按当前目录 ID 读取。叶子与父章节互换仍清空该节点的正文、状态和编排，同时清除对应 HTML、Word 及字数，不影响其他小节或共享图片。
- 新一轮局部生成在原正文 Session 中更新输入快照与 targets，重置上一轮字数调整和审计进度，保留其他正文及图片；本轮暂停/失败继续不重置输入和阶段。仅生成、调整、审计及转换本轮目标，成功后合并字数、状态及 Word 记录。局部目录保存不调用 AI；只有明确全文重新生成、整目录替换或重置才按原流程删除正文会话，不新增历史数据处理及后处理流程。

一至六级标题始终是正文顶层段落，保留 Word 导航、编号、`keepNext` 和一级标题另起页设置。`heading_border.include_headings` 对应“标题也放入页框”，只在章节页框开启时生效，默认 `true`；已有模板缺字段也按 `true` 读取，不迁移、不批量改写模板。关闭时仅取消标题边框，保留底纹、缩进和其他标题样式，正文表格在标题前后分别收口。模板预览、小节 Word 和整本导出共用 C# 转换。`exportService.cjs` 中仍在使用的 Markdown 导出保留段落页框结构，但同步遵循标题边框开关；不把受限 HTML 的融合逻辑复制到该路径。左题栏功能已移除，旧配置不读取、不迁移。

`npm run check:docx` 检查真实表格分页和 Markdown 标题开关，`node scripts/check-technical-plan-export.cjs` 检查受限 HTML 的平面融合、标题导航属性、开关以及预览与正式导出范围。

模板的纸张、方向、双栏及四向页边距始终应用于整个文件，其余标题、正文、列表、表格、图片、章节页框、页眉页脚和页码遵循项目范围。`ai-only` 按叶子目录的 `content_mode=ai-generate` 识别，全部后代均为 AI 生成时父标题也套模板；混合父标题保持基础样式，并跟随首个子目录所在的页面。非 AI 内容不得通过文档默认字体或标题样式间接继承模板。连续同范围目录正常接续，AI 与非 AI 范围交界使用 Word 原生下一页分节，不加表格包装；页框在章节或样式范围结束处收尾。`document` 模式下待填写提示同样接续页框，`ai-only` 模式下非 AI 提示不画框。范围外的节必须显式写入空页眉页脚，避免 Word 继承上一节；页码沿全文连续计数，只在文档起点设起始值，后续节不重启；“首页不同”为封面预留，整本导出尚未接入封面，因此暂时忽略该设置：不创建首页专用空白页眉页脚，第一页按所在范围的普通页面规则排版。用户设置仍保留，普通小节转换和模板样张继续遵循该设置。

页眉页脚的预定义样式只负责色条、边框、图标、分栏和固有高度等结构；模板设置中的页脚距底边距离、字体、字号、正文颜色和正文对齐方式对全部样式生效，预览与 Word 导出必须读取同一组设置。选择色带页脚或为其应用主题时，应根据强调色计算可读颜色并写入 `footer_color`；用户后续修改该设置时，渲染和导出不得再自动覆盖。页码徽标和图标的前景色可继续根据结构底色自动计算对比色。

正文间距使用 `spacing_before/spacing_after` 与各自的 `_unit`（`lines` / `pt`），行距使用 `line_spacing_mode` 与 `line_spacing_value`。旧正文间距字段不读取、不迁移，缺少新字段时默认为段前后 0 行、多倍行距 1.2。普通正文与列表逐段应用，表格只共享行距；基础样式不携带正文的行单位段间距，避免标题、图注和表格继承。模板预览、模板样张导出和投标文件导出都写入 Word 原生 `beforeLines/afterLines`、`line/lineRule`，不将导出文件中的行单位换算成磅。

DOCX 预览引擎固定使用 `@docx-editor.dev/core@2.15.0`，项目修复统一保存在 `patches/@docx-editor.dev+core+2.15.0.patch`，同时覆盖 ESM 与 CommonJS 两份构建。`postinstall` 通过 `patch-package --error-on-fail --error-on-warn` 自动应用；补丁失败或版本不匹配必须中止安装，不再维护另一套替换脚本。

该补丁包含两类修复：标准行段间距（标记 `yibiao: standard-line OOXML paragraph spacing`）补齐 `beforeLines/afterLines`，按一个标准行等于 240 twips（12pt）换算，并保留自动间距优先、属性分别继承的规则，限定项目生成的无 `docGrid` 文档，不支持自定义网格行高；表格分页（标记 `yibiao: flowing table rows and keepNext`）让可拆分的表格行先使用当前页剩余空间再续排，并让单元格内表题与表格、标题行与下一行首块保持同页。同页关联的容量判断必须扣除已启用的重复表头高度和单元格上下内边距；关联块超过该容量时按原拆行规则续排，不得为保留关联块而丢掉续页表头。表格流式排版对顶层业务表格和段落边框页框同样关键，不得删去。

补丁必须随代码纳入版本控制，`node_modules` 只保存应用后的结果，不作为修复的唯一来源。补丁以原始依赖包为基线；有局部手改或局部补丁的环境使用 `npm ci` 重建依赖，由 `postinstall` 完整重放，不兼容局部修改状态。升级依赖时同步更新补丁及版本，不能跳过补丁后继续声称预览支持对应排版行为。

Mermaid 以 Markdown `mermaid` 代码块持久化。Renderer 由 `MarkdownRenderer` 本地预览，Word 导出由 Main 的 `localImageRenderService.cjs` 本地转图，不依赖在线 Mermaid 服务。

### 正文格式自检

全文及局部正文生成在字数调整、一致性审计和可选去表格结束后，进入 `layout-checking`，随后执行原有逐节 Word 转换；单小节重新生成不增加此阶段。`contentGenerationLayout.cjs` 复用整本导出，按当前目录和模板将 Word 写入系统临时目录。`wordLayoutPreload.cjs` 在独立隐藏 Electron 窗口中调用 docx-editor 2.15.0 的导出布局 API，显式传入 Canvas 字体测量器，不使用近似测量、截图或 AI 读 Word。窗口和临时文件在完成、失败、暂停时清理，继续任务时重新创建。

检测只处理实际文流中图片或图片组放不下而进入下一页/栏的尾部留白，阈值为至少 3cm 且超过邻近正文 4 行；页边距、页眉页脚、图内和单元格内部留白不计入。双栏按左栏、右栏、下一页左栏分析，通栏标题分隔文流；章节另起页及文档末尾不补写。字数取邻近同栏宽的完整正文行估算，扣除段间距并预留一行，不按整页字数平均。布局只有 docx-editor 排版口径，不承诺与其他 Word 排版引擎逐页一致。

自检导出副本携带不可见书签，映射稳定小节 ID、顶层块下标及图片标识；不修改源 HTML，不向 Agent 工作区放 Word。任务集合及已成功小节保存在正文 Session 的 `state.layout_check`。主 Agent 复用原会话，调用 `supplement-layout-sections`；工具沿用 `editContentSections`、Pi 原生 edit 和图片写入前保护。同一小节的所有位置交给一个子任务，补写在目标图片/完整图组之前，不写入单元格、不改图片或既有正文。失败仅重试未成功小节，程序最多执行一轮补写和一次重新导出复查，残留问题写入日志；无合格留白时不调用模型。补写后不重复检查字数范围或一致性，仅刷新实际字数。局部生成分析全书但只补写本次 targets，成功和恢复继续沿用现有小节转换、统计与文件生命周期。

页面显示格式自检、补写、复查进度，暂停及失败继续原阶段。全文进度范围为正文至 70%、审计至 80%、去表格至 83%、自检至 88%、转换至 99%，任务成功才为 100%。运行 `node scripts/check-content-layout.cjs` 验证真实整本 Word、Canvas 分页、书签不影响版式、单/双栏及图文表格、章节页框、估算补写和一次复查；原会话工具和任务恢复分别由 `check-content-generation-agent.cjs`、`check-content-generation-output.cjs` 覆盖。

## UI 与样式复用

UI 使用全局 CSS + Radix primitives，不使用 Tailwind。优先从 `src/shared/ui/index.ts` 引入：

| 场景 | 复用入口 |
|---|---|
| 页面底部操作 | `FloatingToolbar` |
| 对话框、开关、提示 | `AppDialog`、`AppSwitch`、`useToast` |
| 上传区 | `UploadBoard`、`UploadRow`、`UploadFilePill`、`UploadEmpty` |
| 进度、加载、空态 | `ProgressBar`、`InlineSpinner`、`EmptyState` |
| Markdown | `MarkdownRenderer`、`MarkdownEditor`、`MarkdownFullscreenViewer` |
| 全局特殊交互 | `AgentQuestionDialogProvider`、`AiHttpErrorDialogProvider`、`DocumentParseNoticeProvider` |

- `AppProviders` 已挂载全局 Provider，feature 使用对应 Hook，不重复创建全局弹窗或提示状态。
- 成功、错误和普通提示使用 `useToast()` 的 `success`、`error`、`info`；不要使用 `alert`、`window.confirm` 或 `window.prompt`。需要确认或长文案时使用 `AppDialog`/Radix Dialog 和共享按钮类。
- 复用 `.primary-action`、`.secondary-action`、`.danger-action`、`.text-button`、`.panel`、`.section-kicker` 等基础类；颜色、圆角、阴影、焦点和动效优先使用 `styles/tokens.css` 的 `--yb-*` 变量。
- 新 feature 样式放 `styles/feature-<name>.css` 并在 `styles.css` 的 feature 区导入；共享样式才进入 `shared-*.css`。总入口的 `tokens → layout → shared → feature` 顺序参与 CSS 优先级，不随意重排，也不要照搬开发者测试页中的内联视觉样式。
- `body` 固定 `overflow: hidden`。页面根节点保持 `width/height: 100%`、`min-height: 0`，滚动放在页面内部；`FloatingToolbar` 是覆盖层，不为它预留大段底部空白。
- `MarkdownRenderer` 当前默认 `allowRawHtml=true`，调用方不要依赖默认值：远程公告、Agent/AI 文本及其他非本地可信内容显式传 `false`；只有确需保留本地解析 HTML 结构时才传 `true`。
- 所有用户可见文案使用中文，并给失败状态提供可操作信息。

## AI、Agent、文件与日志

- 业务模型请求统一经过 `electron/services/aiService.cjs`。它集中处理模型配置、文本/生图独立队列、并发、重试、取消、日志、Token 统计和埋点；Main 业务代码不要直接请求模型 HTTP。
- `taskService` 为任务绑定 `queueScopeId`、取消信号以及 scoped `aiService` / `agentService`。暂停或取消应沿该作用域传播，不在业务任务里复制队列。
- Pi SDK 模块和工具环境全局共享，`agentService.cjs` 为每个实际 Agent 调用创建独立 Runtime/Session，不限制活动 Session 数；模型请求仍由 `aiService` 文本队列统一控制并发、取消和统计。业务任务通过 `primary_session` 显式指定主 Session，执行监视器展示 `active_tasks`，桌宠插件只访问主 Session。`services/agent/` 和 `services/pi/` 只实现 Runtime、Proxy、Session、工具、诊断和持久任务，不引用业务 Store 或业务 Prompt。业务适配器通过 `agentService` 公共接口调用。
- 普通 Agent workspace 是临时目录；目录生成 V2 使用持久 task workspace/Session 才能在一级目录确认阶段恢复。结构化 Agent 输出的 Schema 定义在业务任务代码中，通过 `json_validation_schemas` 注入，Agent 调用 `json-validation` 时只传 `file_path`。
- 目录生成按阶段声明必需产物：一级目录、子目录和数量调整使用 `outline.json`；评分规划使用 `technical-score-groups.json` 与 `score-directory-plan.json`；多技术分支且有字数目标时由 Agent 填写 `leaf-allocation.json`；最终审核使用 `outline.json` 与 `outline-review.json`；模板提取使用 `投标模版字段分类.json`，最终 Word 和字段清单仍由 `openxml apply-template-fields` 生成。无评分流程跳过评分及分配文件，单分支或无字数目标的分配内容由程序直接写入。字段分类 Schema 由模板任务与 OpenXML 工具共用，零候选时两个分类数组可以为空。
- Runtime 接收任务或阶段交接的 `prepare_output_files`，在写入阶段输入后，以 UTF-8、仅新建方式在当前工作区准备空白文件；已存在文件保持原样，修复轮不清空或重新预建。提示词要求 Agent 用 `write` 首次填入空文件，准确使用工作区根目录文件名。目录和模板任务在 `validateOutput` 中检查当前阶段全部必需产物的非空、JSON 和结构要求，校验通过后才将 `validation_result` 交给循环外的 `continueTask` 推进流程。每阶段最多退回原 Session 修复一轮，失败仍中止；修复沿用已有内容与用户选择，不重复执行交接副作用。任务通过 `buildRetryPrompt(error, meta)` 指明实际待修复文件，普通执行错误返回 `null` 不触发产物修复；未提供回调的其他任务保留原重试行为。
- `agentService.runTask()` 的 `summary_enabled` 默认开启；仅显式传 `false` 时关闭结束总结。公共 Pi 层会让 Agent 在最后一批工具调用上附加 `task_complete=true`，整批成功后直接结束当前阶段；Main 业务任务也可通过 `is_final_tool_call` 回调声明结束工具，此时由程序判断，不向模型提供完成标记。工具失败继续处理，原有结果校验和多阶段续跑照常执行。该参数按调用生效，不写入全局配置，业务调用自行决定是否关闭。技术方案一级目录和完整目录生成、原方案还原、投标模版提取、全局事实生成已关闭结束总结；全局事实 AI 调整保留总结供界面展示。投标模版提取将完整分类写入 `投标模版字段分类.json`，`openxml` 的 `apply-template-fields` 只接收 `fields_file`；工具完成文件结构、候选分类、Word 校验和产物检查后自动结束该任务。
- Agent 提问由全局 `AgentQuestionDialogProvider` 和 Main 的问答/自动确认服务承接，feature 不实现第二套等待 Promise 或弹窗。
- `agentService.runTask()` 的 `auto_validate_json` 默认关闭，显式传 `true` 后，Pi 的 `write` / `edit` 会在同一次文件操作内校验 `json_validation_schemas` 中预置的目标文件，复用独立 `json-validation` 的解析、Ajv 和错误反馈；局部修改差异仍保留。失败文件保留在 Agent 工作区供修复，Session 内记录未修复错误，完成标记及阶段交接均禁止接受未通过的结果。未预置规则的文件、脚本写入和 Main 自身文件写入不自动拦截；独立校验工具继续处理已有文件。当前在技术方案一级目录、完整目录、原方案还原和全局事实生成中启用；投标模版提取继续使用 `openxml` 内置校验，其他业务保持原状。
- 新的文档导入优先复用 `fileService.cjs` / `parseDocumentWithConfig()`，保留配置中的本地或 MinerU 选择、格式 fallback、图片 scope 和统一错误文案。涉及 LibreOffice 缺失提示时复用 `DocumentParseNoticeProvider`。
- Word 导出统一走 `exportService.cjs` 和 `window.yibiao.export.onWordExportProgress()`；Mermaid/HTML 转图由 Main 本地完成。
- AI 返回的局部文本修改复用 `electron/utils/textEdit.cjs`：未知位置用 `applyTextEdit()` / `applyTextEdits()` 并保持唯一命中，已知范围用 `applyRangeEdit()` / `applyRangeEdits()`；未命中或多命中应返回错误，不把替换内容静默追加到末尾。
- 排查异常先记录可复现的阶段、输入摘要和错误链：开发者模式模块日志使用 `createDeveloperLogger()` 写到 `userData/logs/<module>/`，AI 请求日志在 `userData/logs/ai/`。可丢弃文件日志通过 `silentFileLog.cjs` 异步写入，日志失败不得影响主流程。

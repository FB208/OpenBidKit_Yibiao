# 易标投标工具箱开发说明

## 目标

本文面向参与 `client/` 独立客户端开发的成员。阅读后应能快速判断：代码放在哪里、Renderer 和 Electron Main 如何协作、哪些组件和样式应复用、改动后如何验证，以及需要查看哪些仓库级关联目录。

## 技术栈与命令

- Electron：桌面窗口、本地文件系统、配置、后台任务、导出和更新检查。
- Vite + React + TypeScript：Renderer 层 UI 与交互编排。
- Radix UI：Dialog、Tooltip、Switch 等无样式基础组件。
- CSS：全局 CSS，不使用 Tailwind，不复用旧 `frontend/` 样式。

常用命令：

```powershell
cd client
npm install
npm run dev
npm run build
npm audit
```

项目包含 Electron Main 侧 native 依赖，例如 `better-sqlite3`。`npm install` / `npm ci` 后会通过 `postinstall` 把 native 模块重建到当前 Electron 版本。Pi Agent 使用的 `rg`、`fd`、`jq` 已按支持的平台和架构保存在 `client/vendor/agent-tools/` 并进入 Git，日常开发和打包不下载工具。若出现 `NODE_MODULE_VERSION` 不匹配或 IPC 大面积未注册，先运行：

```powershell
cd client
npm run postinstall
```

## 架构边界

- `client/` 是独立桌面客户端，不依赖旧 `frontend/` 和 `backend/` 源码路径。
- 本项目是安装在客户本地计算机上的一体化客户端，Renderer 和 Electron Main 不是传统前后端网络边界；两侧传递的业务参数默认视为客户端内部可信数据，不要因为 IPC 往返而做多余、重复的校验或重复计算。
- Renderer 不直接访问 Node、`fs`、`path`、`ipcRenderer`，只通过 `window.yibiao` 调用 preload 暴露的安全 API。
- Electron Main 负责本地能力：配置、文件解析、AI 请求、SQLite Store、后台任务、导出、自动更新。
- IPC 文件只注册通道和转发参数；业务逻辑放 `electron/services/*.cjs`。
- Renderer 页面只做 UI 和交互编排，不承载耗时任务生命周期，也不保存业务权威状态。
- Prompt builder 只负责组装消息，不直接请求 AI；不要在组件内硬编码大段 Prompt。
- 所有用户可见文案使用中文。

## 目录职责

```text
client/
├── electron/                 # Electron Main / Preload / IPC / Node 服务
│   ├── ipc/                  # IPC 通道注册，只做参数转发
│   ├── services/             # 配置、AI、文件、Store、任务、导出等业务服务
│   └── utils/                # Main 侧工具函数
├── src/
│   ├── app/                  # 路由、菜单、全局 Provider
│   ├── components/           # 应用布局组件，例如 AppShell、Sidebar
│   ├── features/             # 业务功能模块
│   ├── shared/               # 跨功能共享能力
│   ├── main.tsx              # Renderer 入口
│   └── styles.css            # 全局样式
└── assets/                   # 客户端图标和静态资源
```

关联目录入口：

- `analytics/`：独立 Cloudflare Workers 埋点服务和统计看板。客户端只通过共享埋点入口上报；修改埋点字段、页面映射、公告读取或统计展示时才需要查看。
- `sql/workspace_schema.sql`：`workspace/yibiao.sqlite` 目标完整表结构说明。运行时不会执行该文件；实际建表和升级以 `client/electron/services/sqliteDatabase.cjs` 的 migration 为准。

新增主菜单页面时，通常同步修改：

- `src/shared/types/navigation.ts`
- `src/app/menuConfig.ts`
- `src/app/AppRouter.tsx`
- 如需页面级工具条，再按页面状态渲染 `FloatingToolbar`

如一级菜单需要承载多个子功能，在 `menuConfig.ts` 为该一级 `AppMenuItem` 配置 `children`，点击一级菜单后由 `shared/ui/SecondaryMenuPage.tsx` 在右侧主内容区渲染二级菜单页；不要在侧边栏做展开式或悬浮式二级菜单。二级入口仍需补充 `SectionId`、具体页面路由和埋点看板中文映射。

## Feature 与 Shared

业务功能放在 `src/features/<feature-name>/`：

```text
features/<feature-name>/
├── pages/        # 页面级组件
├── components/   # 本功能专用组件
├── hooks/        # 本功能专用 Hook
├── services/     # Renderer 侧轻量编排或兼容工具；长任务不要放这里
└── types.ts      # 本功能专用类型
```

当前功能模块：

- `technical-plan`：技术方案。
- `knowledge-base`：知识库。
- `duplicate-check`：标书查重。
- `rejection-check`：废标项检查。
- `settings`：设置页，管理文本模型、生图模型、组件设置（文件解析与本地转图并发）、Pi Agent 场景开关和关于信息。

技术方案流程页面复用约定：

- `src/features/technical-plan/pages/TechnicalPlanHome.tsx`、`DocumentAnalysisPage.tsx`、`BidAnalysisPage.tsx`、`OutlineEditPage.tsx`、`GlobalFactsPage.tsx`、`ContentEditPage.tsx` 是“生成技术方案”和“已有方案扩写”共用的流程页面；后续修改这些页面时必须同时考虑两个入口的展示、步骤 gating、任务状态、错误提示、导出和重置行为。
- “已有方案扩写”和“生成技术方案”的主步骤及页面骨架保持一致，差异主要由工作流类型、Step01 是否额外上传“已有方案”、Main 侧后台任务和 Prompt 决定。Renderer 侧不要为了其中一个功能复制整套页面，也不要把某个入口的业务假设硬编码进通用页面。
- 如需调整上述共用页面的 props、状态字段、IPC 调用或任务事件处理，必须确认另一个入口仍能正常启动、恢复、切换步骤、生成目录、设定全局事实、生成正文和导出 Word；不能为了修复一个入口导致另一个入口回归。

共享能力放在 `src/shared/`：

- `shared/ai/aiClient.ts`：Renderer 侧 AI 请求门面，仅用于仍在 Renderer 侧的轻量请求。
- `shared/prompts/`：仍由 Renderer 使用的 Prompt builder。已迁入 Main 后台服务的流程不要保留 Renderer 直连 AI 占位 Prompt。
- `shared/types/`：跨功能类型，包含 `ipc.ts` 中的 `window.yibiao` bridge 类型。
- `shared/ui/`：跨功能 UI，例如 `FloatingToolbar`、`SecondaryMenuPage`、`DetailHelpLink`、`MarkdownRenderer`、Toast。
- `shared/utils/`：跨功能纯工具，例如 ID、字数统计。

共享层规则：

- `shared/` 不引用任何 feature 模块，避免循环依赖。
- 类型优先使用 `interface`；联合类型和泛型工具类型使用 `type`。
- 新增 bridge API 时，同步 `electron/ipc/*`、`electron/preload.cjs` 和 `src/shared/types/ipc.ts`。

## Electron Main、IPC 与 Store

- `electron/` 使用 CommonJS，保持 `.cjs`。
- `electron/ipc/*.cjs` 只注册/转发 IPC，不写业务逻辑。
- `electron/services/*.cjs` 承载 Main 侧业务逻辑。
- Renderer bridge 以 `src/shared/types/ipc.ts` 为类型权威；不要在多个文件里各自手写不一致的返回类型。
- Main 侧文件读写显式使用 UTF-8，并把 Windows 中文路径作为默认场景处理。

核心服务分工：

- `configStore.cjs`：配置读写，保存到 Electron `userData/user_config.json`。
- `autoConfirmationService.cjs`：统一管理确认弹窗的自动提交开关、8 秒计时和业务提交回调，不解析选项内容。
- `aiService.cjs`：文本模型、生图模型、JSON 修复和模型请求统计。
- `fileService.cjs`：文档导入与解析，统一按配置选择本地或 MinerU 解析方式。
- `sqliteDatabase.cjs`：工作区 SQLite 初始化和 runtime migration。
- `technicalPlanStore.cjs`、`duplicateCheckStore.cjs`、`rejectionCheckStore.cjs`、`knowledgeBaseStore.cjs`：各功能 SQLite Store。
- `taskService.cjs`：通用后台长任务管理、任务组锁、active task、统一 checkpoint、事件推送和状态落盘。
- `agentService.cjs`：Pi Agent 协调服务，管理唯一的 Pi runtime 和全局串行队列，并统一返回输出文件、assistant 文本、diff、session 和 runtime 状态信息。
- `exportService.cjs`：Word 导出、Markdown 转 Word、图片和 Mermaid 导出。

新增文件上传、导入、转换功能时，优先复用 `fileService.cjs` 的 `parseDocumentWithConfig(app, filePath, config, { assetScope })`。删除业务资源时，同步调用 `electron/utils/importedImages.cjs` 的 `deleteImportedImageBatches(app, assetScopePrefix)` 清理导入图片资产。

Main 侧通用文本编辑：

- `electron/utils/textEdit.cjs` 是纯字符串 edit 引擎，不读写文件、不调用 AI、不访问 Store；业务服务传入完整文本和 edit 指令，拿返回的 `content/changed/edits/errors` 后自行决定是否保存。
- AI 返回局部替换时优先用 `applyTextEdit()` / `applyTextEdits()`，参数为 `oldText/newText`，默认必须唯一命中；多处命中时让 AI 补充更多上下文，不要静默替换第一处。
- 程序已经明确捕获范围时优先用 `applyRangeEdit()` / `applyRangeEdits()`，例如表格块、代码块、段落块替换；批量 range 会先校验不重叠，再倒序应用。
- 只搜索不修改时用 `findTextMatches()`；匹配策略按 exact、line-trimmed、whitespace-normalized、trimmed-boundary、block-anchor 逐级尝试，整体保持保守，避免误改正文中的参数、工期和承诺。

## 数据存储

- 配置保存到 Electron `userData/user_config.json`。
- 业务工作区保存到 Electron `userData/workspace/`。
- 结构化业务状态统一进入 `userData/workspace/yibiao.sqlite` 或功能专用 Store。
- SQLite 表结构调整时，同步更新 runtime migration 和仓库根目录 `sql/workspace_schema.sql`，后者只用于阅读、评审和排查问题。
- 大文本 Markdown、原始上传文件和图片资产保存为文件，SQLite 只保存路径、hash、计数和结构化状态。
- Renderer 只允许使用 `localStorage` 保存轻量 UI 偏好；大文本、草稿、API Key、流程状态都走 Main 侧 Store/IPC。
- 命令型数据库接口默认只写不读，返回 `void`、成功摘要或本次创建/修改的目标；SQLite 写入或事务成功即表示提交完成，不得再读取完整工作区进行二次确认。
- 查询必须通过显式 `load*`、`get*`、`list*`、`read*` 接口完成，且查询接口保持纯读取，不得隐式创建默认行、恢复任务、清理文件或修复状态；这些动作放在 Store/服务初始化或单独命令中。
- 写命令为了计算排序、检查目标存在、获取旧资源路径等业务依据，可以执行必要的定向前置查询；需要返回本次变更实体时优先使用已知输入或 SQL `RETURNING`，不得附带无关的完整状态。
- 导入、切换工作流、移动文件等复杂低频命令如确需刷新全局状态，由调用方在命令成功后显式读取；后台任务高频 checkpoint 必须直接用本次 patch 推送事件，禁止写后全量读取。
- Store 接收嵌套业务 patch 时，字段缺失表示保持原值，普通字段出现表示只更新该字段，结果数组出现才表示替换对应明细；空数组用于明确清空，禁止把未传入的结果数组当作空结果处理。
- 任务进度、业务结果和 Renderer 交互状态必须分开处理：普通进度与提示只更新 Main 内存并推送事件，有恢复价值的阶段 checkpoint 才写任务表；结果生成、文件处理完成或用户删除结果时才更新对应明细，展开、收起和选中操作只更新自身字段。
- SQLite 任务日志统一存入 `task_logs` 行表，每个当前任务最多保留 80 条；任务删除、换代或工作区重置时必须同步删除，禁止恢复 `logs_json` 整体数组和永久任务日志。
- 任务统计与正文运行状态只保存有恢复价值的有限 JSON checkpoint；全文图片计划使用计划头和图片项目表，单张图片状态变化只更新对应项目。权威设计见 `doc/数据库任务状态与日志持久化方案.md`。
- 技术方案正文展示和 Word 导出以 `outlineData.outline[*].content` 为权威来源。

技术方案流程状态约定：

- 主流程 Step 只表示页面级阶段，例如 `document-analysis`、`bid-analysis`、`outline-generation`、`global-facts`、`content-edit`。
- Step 内部如果存在可中断子流程，不新增主 Step；应在 Store 中落盘为该 Step 的子状态，页面加载后按子状态恢复 UI。
- 多标段识别属于 Step02 `bid-analysis` 子流程：用户选择多标段后由 Main 后台任务 AI 提取标段范围，结果写入 `bid_sections_json`，选择后生成当前投标范围工作副本 `tender.md`；Step01 只负责导入完整原文 `tender-original.md`。
- Step05 正文生成属于 `content-edit` 的后台任务子流程，运行态、章节状态、正文规划结果、全文图片计划和 runtime JSON 由 Main 持续写入 Store，用于异常关闭后的暂停恢复。
- Step03 是因字数目标调整目录结构和 `ai-generate` 叶子节点数量的唯一阶段；Step05 只能更新这类目录节点正文，不得新增、删除、拆分、合并或重新编号目录。
- Step03 当前字数设置与成功生成目录时的生效快照分别保存。修改当前设置只有重新生成目录后才影响正文任务；Step05 及其暂停恢复只读取目录生效快照。
- 小节或全文经过限定轮次仍未达到字数目标时保留有效正文并记录警告，不得仅因字数不达标把小节或任务标记为失败。
- 最终小节复核和全文字数调整位于原方案覆盖修复、一致性修复及表格清理之后，全文图片编排之前。
- 正文编排只决定写作重点、知识库引用、事实变量和表格，不再逐节决定或生成图片。正文生成、扩写、审计和表格清理全部完成后，Main 使用当前智能体运行时阅读 `technical-plan.md`、`outline-tree.json`、`illustration-config.json`，严格校验 `illustration-plan.json` 后一次性写入 `contentIllustrationPlan`。
- 全文图片计划保存 `kind/image_type/title/section_ids/placement/priority`，其中 `title` 是编排 Agent 基于全文统一设计的最终图注，最终计划内必须唯一。程序按 HTML、AI、Mermaid 的顺序处理类型上限和小节冲突，再进入图片生成阶段；三类生成提示词都直接注入计划标题，不得在生成阶段另行生成或拼接标题。
- 全文图片编排 Agent 失败或暂停时不保存半成品；从 `illustration-planning` 恢复时跳过已完成的正文和审计阶段，重新执行整轮图片编排。
- 所有正文小节请求结束后统一检查状态；存在未完成小节时必须在正文生成阶段停止。未完成是指状态既不是 `success` 也不是 `ignored`，包括生成失败的 `error`、保存空正文产生的 `idle` 和异常残留的运行状态。此时不得自动进入小节字数调整、原方案覆盖检查、全文一致性检查、表格清理、最终小节复核、全文字数调整或图片阶段。任务通过 `awaiting_content_decision` 持久化等待状态，页面同时提供“重试失败小节”和“继续后续流程”。
- “重试失败小节”重新生成所有未完成正文，仍有未完成小节则再次等待，全部成功后自动执行完整后续流程和全文图片编排；“继续后续流程”必须经用户确认，将剩余未完成小节改为 `ignored` 后直接执行后续流程。`ignored` 小节不参与字数调整、审计、表格清理、图片编排和图片生成，任务完成后不再提供失败重试入口。
- 图片编排始终是基于当前全部 `status = success` 正文执行的一次性全文编排，不存在局部图片计划合并、旧图片额度扣减或补生成小节单独配图。图片回填不得修改正文小节状态或清除正文错误，实际插入位置对应的小节不是成功状态时必须跳过该图片。
- 正文生成配置弹窗在开发者模式下显示“以随机失败模式开始”：Main 从本轮待生成小节中无放回随机选择约 20%（至少 1 个、最多 5 个，并至少保留 1 个正常小节），在正文请求前注入一次性失败。该模式只影响本次启动任务，后续“继续生成正文”不得再次模拟失败。
- 新增 Step 内子状态时，要同时定义异常关闭后的恢复、确认完成后的清空、取消后的清理和重置工作区时的清理规则。
- 重置技术方案时必须先取消并等待活动中的目录生成任务退出，再清空 Store，避免一级目录确认等待器和 Pi Session 长期占用任务组及 Agent 队列。

## 后台任务

- 所有耗时 AI、文件解析、批处理、生成、检查、导出转换都必须放在 Electron Main 后台任务中执行。
- Renderer 只负责启动任务、订阅事件、读取 Store 快照和展示状态。
- Main 任务启动后必须立即写入 running 状态，并在每个关键阶段持续写入对应 Store。
- 页面卸载不能取消任务，也不能作为任务失败信号。
- 页面重新挂载后必须先读取 Store，再订阅任务事件，并通过 `getActiveTasks()` 触发 active task 状态回放。
- 如果 Store 中存在 running/pausing 等运行态，但 Main 没有对应 active task，应标记为“上次任务未完成，请重新执行”或进入业务约定的可恢复状态，不能静默恢复为 idle。
- 任务状态由 `taskService.cjs` 统一管理。业务任务不得先把 `*Task` 字段写入 Store，再将已保存的工作区状态传给 `updateTask()` 重复落库。
- 同一个业务 checkpoint 同时包含任务进度和业务结果时，统一调用任务服务提供的 `checkpointTask(taskPatch, workspacePatch, eventPatch)`；任务服务必须把两部分合并为一个 Store patch，在同一个事务中只提交一次。
- `checkpointTask()` 只在 Store 提交成功后更新任务事件；Renderer 接收局部事件或完整快照只影响展示方式，不得触发第二次任务状态落库。
- `updateTask()` 只更新 Main 内存并推送 Renderer，禁止写 Store；纯百分比、重复提示和实时活动使用该入口。阶段切换、单项完成、等待用户、暂停、失败和成功使用 `checkpointTask()`。
- 技术方案重置必须先取消并等待全部 `technical-plan` 活动任务退出，再清空 Store；取消后的任务不得继续提交 checkpoint。

任务组约定：

| 任务组 | 锁策略 | 说明 |
| --- | --- | --- |
| `technical-plan` | `group-exclusive` | Step02/Step03/Step04 共用技术方案工作区，组内互斥。 |
| `duplicate-check` | `group-exclusive` | 标书查重外层是一轮分析任务，内部子流程可以并发。 |
| `rejection-check` | `group-exclusive` | 废标项解析和检查共用同一检查缓存，组内互斥。 |
| `knowledge-base` | `scope-exclusive` | 后续接入统一任务服务时按 `documentId` 加锁；当前仍由 `knowledgeBaseService.cjs` 独立管理文档级互斥。 |

清空规则原则：

- 重新生成某一步时，只清空该步骤旧结果和后续步骤结果，不清空前置输入。
- 清空动作应在 Main 侧任务确认启动后执行并落盘，Renderer 不要在 IPC 成功前清空持久化业务数据。
- 目录重新生成、编辑、添加或删除后，必须清空旧正文内容、正文生成缓存和全文图片计划；手工编辑正文或修改正文生成配置后也必须清空全文图片计划。

## UI 与组件复用

- 新页面优先复用现有卡片、胶囊 Tab、状态栏、工作区、列表/树 + 阅读器、`FloatingToolbar` 等模式，不另起一套视觉语言。

- 用户确认、长文案提示、危险操作优先使用项目内 Radix Dialog 和统一按钮样式；新增或重构时不要使用 `alert`，也尽量不要使用系统 `window.confirm` / `window.prompt`。

## AI、Prompt 与日志

- Prompt 放 `src/shared/prompts/` 或 Main 侧对应服务中，避免在组件内硬编码大段 Prompt。
- 已迁入 Electron Main 后台服务的流程，不保留 Renderer 直连 AI 占位 service 或 Prompt。
- 全局 AI 并发队列实现在 `electron/utils/aiRequestQueue.cjs`，由 `electron/services/aiService.cjs` 统一创建和使用；普通业务请求和 Agent 模型请求都不得绕过 `aiService` 直接发起 AI HTTP 请求。
- 文本模型和生图模型使用独立队列：文本请求队列读取文本模型 `concurrency_limit`，默认 `10`；生图请求队列读取生图模型 `image_model.concurrency_limit`，默认 `2`。
- `aiService.chat()`、`aiService.requestJson()`、`aiService.collectJsonResponse()`、`aiService.parseJsonResponseContent()` 进入文本队列；`aiService.generateImage()` 进入生图队列。
- 队列按 FIFO 调度；超过并发上限的请求进入队列等待，拿到并发 slot 后才真正发起 HTTP 请求。
- 排队时间不计入上游请求超时：父级取消信号从入队起持续生效，上游普通响应超时或流式空闲超时只在拿到并发 slot 后启动。Agent 排队期间通过不可见活动心跳维持任务 watchdog，并将实际排队耗时记录为 `queue_wait_ms`。
- 普通 AI 请求由队列统一识别网络异常、请求超时、`408`、`429` 和 `5xx` 等临时错误，单个请求最多尝试 3 次；Agent 模型请求在队列层固定只执行一次，不得与 Pi 原生回合重试叠加。
- `taskService.cjs` 启动后台任务时会生成 `queueScopeId`，并分别注入 scoped `aiService` 和绑定相同作用域的 `agentService`；普通 AI 请求和 Agent 模型请求必须共享该作用域及全局文本并发上限。
- scope 暂停是队列通用能力：已发出的请求继续执行，尚未发出的排队请求会被丢弃并抛出 `AI_QUEUE_SCOPE_PAUSED`。
- 业务层负责响应队列暂停错误，例如正文生成将 `AI_QUEUE_SCOPE_PAUSED` 转换为自身的暂停落盘流程；队列层不写具体业务状态、不修改 Store。
- 正文生成的文本并发不再单独配置，使用文本模型并发上限；正文任务末尾只生成全文图片计划，不调用 AI 生图或 Mermaid 渲染。
- Main 侧需要按文本模型上下文限制切割用户长文本时，使用 `electron/utils/userTextSplitter.cjs` 的 `splitUserTextByContextLimit(text, config)`；函数读取 `config.context_length_limit`，按 0.8 安全系数先均分段数，再优先在段落、换行、句末标点附近切分，返回文本数组。

Pi Agent 调用约定：

- 新版 Agent 严格分为功能层和业务层。`agentService.cjs`、`services/agent/`、`services/pi/` 属于功能层，只负责队列、Runtime、Proxy、模型请求、工作区、Session、持久任务、工具、重试、超时、监控和统计，不得引用技术方案 Store、目录任务、业务 Prompt、业务常量或业务状态。
- 目录生成 V2 是新版 Agent 的首个业务适配层，由 `outlineGenerationTaskV2.cjs` 和 `outlineGenerationAgentV2Config.cjs` 定义 Prompt、输入输出文件、Schema、阶段流程、用户确认、持久任务 key、进度和业务落库。业务层只能通过 `agentService` 公共接口调用 Agent 能力，不得导入 `services/pi/*` 或直接操作 Agent 持久任务文件。
- `agentService` 的公共任务协议统一提供 `runTask`、任务作用域、持久任务读取/更新/删除/Session 检查、单阶段执行、`validateOutput`、`continueTask`、`ask-user` 和检查点回调。以后新增新版 Agent 业务时只增加业务适配器及正常的任务/IPC/UI 注册，不得为业务复制 Runtime、Proxy、队列或持久化实现。
- 目录生成旧实现已删除，V2 是唯一正式目录生成链路；正文生成、全局事实等既有任务保持原执行设计，后续按业务需要单独适配新版 Agent 公共协议。
- Main 侧只运行 Pi Agent，运行时元数据固定为 `pi / Pi Agent`，不提供运行时选择或回退。
- Pi 使用本地 Agent AI Proxy 适配 SDK 所需的 OpenAI 接口和流式工具调用协议；Proxy 不直接访问外部模型，也不维护独立请求队列，所有 Agent 模型请求统一交给 `aiService` 文本出口，并复用其模型配置、全局并发、请求日志、Token 统计和 `ai_request` 埋点。
- Pi 的 `openai-completions` 下游协议固定使用 SSE，文本模型 `request_mode` 只决定 `aiService` 请求外部模型时采用普通还是流式响应。流式上游由 Proxy 原样转发；普通上游由 Proxy 将完整 Chat Completion 确定性编码为标准 SSE Chunk，完整保留正文、推理字段、工具调用、`finish_reason` 和 Token 用量。这是正式协议适配，不允许在两种模式间失败回退，也不得补造缺失的模型结果。
- Pi 自检按当前文本请求模式验证基础请求和工具调用，并始终执行真实 Pi 端到端任务；未选中的请求模式仅作为诊断探针，不得因其不可用阻止当前配置运行。
- Pi 全局开启 Agent 回合级原生重试，按 SDK 默认策略处理限流、服务端错误、网络中断和流提前结束等瞬时错误；Provider、SDK 和 Agent Proxy 请求级重试保持关闭。`model_retry_count` 按 `auto_retry_start` 事件累计原生模型重试，`retry_count` 仅表示业务输出修复，两者不得混用。
- Pi Agent 不设置任务总时长上限；默认无进展 watchdog 为 8 分钟，普通上游请求总超时为 15 分钟，流式首包及相邻数据块空闲超时为 5 分钟，Pi HTTP 空闲兜底为 15 分钟。持续产生模型、工具或工作流活动时任务可一直运行，等待用户操作期间暂停 watchdog。
- `TASK_CANCELLED`、`CONTENT_GENERATION_PAUSED`、`AI_QUEUE_SCOPE_PAUSED` 和 `AGENT_DISCONNECTED` 属于正常中断，不计入 `agent_runtime` 失败埋点；真实模型错误和上游超时仍按失败统计。
- 网关返回 Pi 尚未识别的明确瞬时错误时，通过 `DefaultResourceLoader.extensionFactories` 注册的内联 `message_end` 扩展规范化错误文案，再交给 Pi 原生重试；当前仅处理 `Upstream service temporarily unavailable`，外部扩展发现仍保持关闭，最终业务错误恢复网关原文。
- Renderer 或业务服务统一通过 `window.yibiao.agent.run(payload)` 调用，不直接启动具体运行时或访问运行时内部 API。
- `payload.files` 用于写入本次任务 workspace，只放本次任务需要的输入文件，例如 `tender.md`、`bid.md`、`current-result.json`。
- `payload.task` 是默认任务描述；如需要完全自定义提示词，使用 `payload.prompt`。
- `payload.output_file` 默认是 `agent-result.md`，业务侧读取结果时优先使用返回值中的 `output_content`。
- 业务层默认不要传 `task_id`，让 `agentService` 自动生成 UUID；如果确需传入，只能传内部生成的稳定 ID，不要使用用户输入、文件名、本地路径或包含 `/`、`\`、`..` 的字符串。
- 智能体只写入自身隔离 workspace，不直接修改业务 Store；正式业务由对应 Main 侧适配层严格校验输出，再一次性合并到业务 Store。
- `agentService` 为 Pi 维护全局 FIFO 队列，所有智能体任务按进入队列的顺序串行执行。
- 暂停或应用重启后的恢复任务继续使用 Pi，不保存运行时选择，也不做旧运行时任务兼容。
- Pi 不自动加载外部上下文、扩展、Skill、Prompt 模板或主题。普通 Agent 调用继续使用内存 Session；V2 目录生成使用任务专属文件型 Session，后续完整执行通过 `SessionManager.open()` 继续原聊天上下文。
- Pi 使用随应用打包的 `agent-tools` 中的 `rg`、`fd`、`jq`；本地开发如需指定工具目录，只使用 `YIBIAO_AGENT_TOOLS_BIN_DIR`。
- Pi 的全局工作区指令在 Session 创建时根据 `process.platform` 追加当前 Shell 规则：Windows 使用 PowerShell 5.1，macOS 使用 `/bin/sh`。业务 Prompt 不重复声明操作系统；文件操作和 JSON 校验优先使用专用工具，不得创建临时脚本重复执行结构、数量或字段校验。
- Pi 通过 SDK 注册 `json-validation` 专用工具；它不是 `agent-tools` 外部命令。所有新增业务的 Agent JSON 输出必须由程序预置 Schema，禁止要求 Agent 自行设计、复制或传入 Schema。
- Pi 全局注册 `ask-user` 专用工具。只有任务材料无法确定且不同选择会实质影响结果时才允许调用；Agent 每次提供一个问题和 2 至 5 个互斥选项，第一项为推荐选项且必须设置 `custom=false`。每个选项必须显式声明 `custom`；普通选项为 `false`，需要用户选中后输入具体要求时为 `true`，一次提问最多只能有一个 `custom=true` 的选项。程序不再自动追加“其他”，自定义选项必须由 Agent 使用明确的业务名称提供。
- `ask-user` 的问题、选项名称和选项说明必须面向不懂软件开发的普通用户，只使用简单自然的业务语言，明确推荐结果、实际影响和可选操作；禁止暴露变量名、字段名、文件名、JSON 属性、英文状态、内部编号和其他软件实现术语，内部规划必须转换为具体目录名称、数量、层级和调整效果后再询问。
- `ask-user` 不得在问题、选项名称或选项说明中复述、概括或改写当前任务 Prompt 的要求，只呈现 Agent 分析后确实需要用户确认的结论或不确定事项。存在多个实际确认事项时才使用简单 Markdown 按“简短说明、分行要点、最后确认”组织；弹窗通过 `MarkdownRenderer` 且关闭 raw HTML 后渲染问题内容。
- `ask-user` 在同一 Pi Session 内异步等待用户回答，回答后直接返回工具结果并继续当前执行。等待期间继续占用 Agent 全局队列，但不计入无进展超时；Renderer 刷新时可通过 `agent:get-pending-question` 恢复当前进程中的弹窗。应用退出后不恢复 `ask-user`、不修复工具结果分支，目录任务按执行中断处理。
- Agent 提问弹窗由 `AgentQuestionDialogProvider` 全局承接，业务页面不要重复实现提问 UI 或自行管理等待 Promise。弹窗不允许跳过回答；普通选项可直接提交，选择 `custom=true` 的选项后必须输入有效的具体要求。
- 自动回答授权保存为 `user_config.json` 的 `agent_auto_answer_enabled`，默认关闭；设置页、Agent 提问和程序确认弹窗通过 Main 侧 `autoConfirmationService` 即时联动。开启后 Main 为每个确认项创建 8 秒倒计时并调用业务预先注册的默认提交回调，不解析选项内容、不调用 AI。程序自动选中默认项不停止计时；用户手动修改任意选项后立即停止当前弹窗的倒计时，但不关闭全局配置。关闭开关会立即取消所有当前倒计时。
- 一个业务流程需要连续执行多个 Agent 阶段时，通过 `payload.continueTask` 在同一次完整 Agent 执行中继续发送 Prompt、追加文件。普通流程依赖 Pi 原生自动压缩管理上下文；只有业务明确要求立即压缩时才调用当前 `AgentSession.compact()`。普通 Agent 任务结束后归档 workspace；V2 目录任务直接保留任务专属 workspace、Session、`task-state.json` 和 `result.json`。
- Pi Agent 执行监视器只采集窗口打开后发生的事件。首轮或恢复 Session 的输入通过 `task_start` 采集，`payload.continueTask` 产生的后续 Prompt 和新增或更新文件通过 `task_input` 按轮次采集；中间阶段的主输出文件通过 `task_output` 采集，最后阶段由 `task_end` 提供最终输出，相同 `task_id` 的后续输入和输出都必须追加展示。监视内容只保存在监视器窗口内存中，关闭窗口后清空，主进程不缓存历史事件。
- Pi 原生 `auto_retry_start/auto_retry_end` 必须进入执行监视器并更新“模型重试”；业务输出校验触发的 `retry` 单独更新“结果修复”，两种机制不得合并统计。Agent AI Proxy 必须收集 SSE 流内 `error`、`finish_reason` 和 `[DONE]` 状态，流内错误或提前取消时要结束对应 pending 日志。
- Pi 交互模式的手动压缩命令是 `/compact`；客户端使用嵌入式 SDK，其等价正式入口是 `AgentSession.compact(customInstructions?)`，禁止把 `/compact` 作为普通 Prompt 发送。压缩返回 `Nothing to compact` 或 `Already compacted` 表示当前上下文无需处理，记录后可继续；取消任务或关闭服务时必须同时中止压缩。
- V2 一级目录生成是一次完整 Agent 执行；`outline.json` 写入并校验后释放 Agent 连接，由程序等待用户选择。用户确认后重新打开原 Session，再执行技术方案目录规划、叶子分配、子目录生成、数量差异处理和最终审核，因此聊天记录与工作文件保持连续。
- 一级目录程序确认使用 `autoConfirmationService` 注册生成阶段给出的默认目录、属性和处理模式；倒计时结束后直接调用既有 Main 侧确认逻辑。用户修改勾选、目录属性、处理模式或选择稍后处理时停止本次倒计时；应用重启恢复该确认状态时重新开始一轮倒计时。
- V2 目录任务根目录通过 `path.join(app.getPath('userData'), 'agent-runtime', 'pi', 'tasks', taskKey)` 动态计算，不保存任何用户绝对目录常量。`task-state.json` 只保存 Session 文件名，恢复时基于当前用户动态计算的 `sessions` 目录重新拼接，并以当前 `workspace` 覆盖 Session cwd。
- 普通 Pi 任务只在执行期间使用共享工作区，成功任务不创建归档；失败任务归档只保留到诊断进程读取和上报结束。V2 目录生成的持久任务目录不按普通归档清理，仍按重新生成、前置步骤失效和重置规则删除。
- 应用重启时只恢复 Agent 已完整退出后的一级目录程序确认状态；恢复弹窗时不连接 Agent，用户确认后才打开原 Session。模型请求、`ask-user` 或其他 Agent 执行阶段中断后标记为失败，用户必须重新生成目录。
- 完整目录后续执行中的各阶段共用重新打开的原 Session。`content_mode = ai-generate` 的实际叶子数与目标不一致时，Agent 必须通过 `ask-user` 固定提供“接受当前结果”“允许 Agent 自行调整”“自定义需求”三个选项。程序直接读取系统记录的真实选项；用户要求调整后仍未精确满足时再次询问，不使用决定文件，也不得通过重复、空泛或近义目录机械凑数。
- 子目录和数量差异处理结束后直接由同一 Agent 审核最终目录，不主动压缩 Session；`compaction.enabled` 保持开启，由 Pi 在接近上下文上限或发生溢出时自动压缩。宿主程序先把叶子数量、内容模式数量、最大层级、父节点数量、单子节点和评分节点机械映射写入 `outline-review-context.json`，Agent 直接采用这些确定性结果，只审核评分语义覆盖、重复或近义子目录及专业合理性。程序存在目标叶子数时，将 `targetLeafCount - 2` 至 `targetLeafCount + 2`（下限不低于 1）作为可接受范围写入审核上下文；没有目标时不得增加数量审核规则。
- 目录审核结果写入 `outline-review.json`，状态只能是 `passed`、`simple_fix`、`user_feedback` 或 `user_refuse`。`passed` 表示无问题；`simple_fix` 表示 Agent 自主完成了无需确认的静默目录调整；`user_feedback` 表示 Agent 已按用户回答修复；`user_refuse` 表示用户选择保留当前目录。宿主程序信任 Agent 的审核分类和处理结果，不再对审核状态、提问记录、用户反馈副本或审核前后改动执行二次语义判定。
- `buildFinalOutline()` 接受 Agent 的完整目录结果，仅统一整理层级编号和节点字段，不再根据早期 `allow_root_changes` 状态恢复或过滤一级目录。技术分支在 Agent 工作区内使用 `branch_id` 作为不随增删、重排和重新编号变化的稳定标识；统一编号后程序按 `branch_id` 同步 `score-directory-plan.json` 中的当前 `root_id/root_title`，写入正式业务目录前移除内部 `branch_id`。一级目录调整权限由评分规划和最终审核 Prompt 结合当前 Session 中全部 `ask-user` 回答判断。Agent 要求用户修改时使用 `user_feedback`，按回答完成最终修复后无需再次确认；用户拒绝时使用 `user_refuse` 并原样保留审核前目录。审核中的 `ask-user` 不跨进程恢复。
- 新生成或重新生成目录会先删除上一轮目录 Agent 工作区并从头开始。重置技术方案、重新导入招标文件或原方案、重新解析使目录失效的前置步骤、切换标段或工作流时，也必须同步删除该工作区；目录任务成功、失败或手工编辑现有目录时不删除。
- 设置字数目标且存在多个技术一级目录时，叶子分配必须作为 `payload.continueTask` 的独立阶段交给当前 Pi Session，读取同一 workspace 中的评分项、目录规划、知识库和原方案并写入 `leaf-allocation.json`；分配项使用稳定 `branch_id` 指向技术分支，不使用会因一级目录调整而变化的 `root_id`。禁止在 continuation 回调中使用 `aiService` 发起脱离当前 Session 的分配请求。
- V2 子目录生成前必须先将“技术评分项”结构化为 `technical-score-groups.json`，再生成 `score-directory-plan.json`。默认每个评分项对应一个独立目录节点，同一技术方案分支内这些节点处于相同层级，不同分支可使用不同层级；无论是否存在偏离，Agent 都必须通过一次 `ask-user` 确认分析得出的技术方案分支和评分项目标层级，存在合并、拆分、遗漏、增加同层级大项、改变目标层级或调整已确认一级目录时只追加实际偏离及影响，不复述默认规则。
- `score-directory-plan.json` 是评分项目录位置的生成阶段权威：规划生成时每个技术分支以当前一级目录的 `root_id/root_title` 绑定稳定 `branch_id`，完整目录重新编号后再按 `branch_id` 同步当前编号和标题；固定叶子统计、叶子分配和最终审核均以 `branch_id` 识别技术分支。评分项必须恰好映射一次。知识库和原方案只能完善映射节点的下级结构，叶子数量调整不得删除、移动映射节点或增加未经批准的同层级大项。最终审核前宿主程序按 `branch_id` 定位重新编号后的技术分支，只机械检查目标标题是否位于指定层级，并把结果写入审核上下文；Agent 仍需直接对照 `技术评分信息.md` 判断评分语义是否完整覆盖，并结合该规划自主审核和修复，宿主程序不执行二次语义判定。
- 最终目录每个叶子节点必须设置 `content_mode`：`ai-generate`、`template-fill`、`point-to-point` 或 `other`；父节点不保存该字段，`other` 可用 `content_mode_note` 说明。只有 `ai-generate` 参与目录叶子目标、正文生成、字数控制、审核和图片流程，其他模式当前标记为待处理且不阻止 Word 导出。
- 目录处理模式持久化在 `technical_plan_outline_nodes.content_mode/content_mode_note`。当前处于开发阶段，不推断或补齐缺少模式的旧目录；旧目录必须重新生成。手工调整目录形成新叶子时必须明确模式，模式变化按目录正文失效规则清空相关正文和缓存。
- `json-validation` 只执行 `JSON.parse` 和 Ajv 结构校验，不直接修改文件。业务侧仅在存在 JSON Schema 无法表达且业务明确需要的语义规则时使用 `validateOutput`，不要重复进行 JSON 格式校验。
- `vendor/agent-tools/` 同时保存 `win32-x64`、`darwin-x64`、`darwin-arm64`；`prepare-agent-tools.cjs` 只用于升级内置工具，且每次只替换指定平台目录。
- 开发者模式下，Proxy 日志写入 `userData/logs/pi-ai-proxy/*.jsonl`，Token 统计进入共享 `textTokenStatsStore`。

Pi Agent JSON 输出校验约定：

- Schema 在业务任务代码中与输出格式一起定义，并通过 `payload.json_validation_schemas` 按工作区相对文件名传入；一个任务输出多个 JSON 时，为每个文件分别配置 Schema。
- Schema 作为宿主程序配置保存在 Electron Main 内存中，经 Pi Runtime 和 Session 注入 `json-validation` 工具，不写入 Agent workspace，也不作为 Prompt 内容发送给模型。
- Prompt 必须明确说明目标文件已预置 Schema，并要求 Agent 调用 `json-validation` 时只传 `file_path`，不得传入 `schema`。
- 工具根据 `file_path` 自动选择对应的预置 Schema，读取工作区文件并执行 `JSON.parse` 和 Ajv 校验；Agent 无权查看或修改 Schema。
- 校验失败时，Agent 必须根据工具返回的错误使用 `edit` 或 `write` 修复输出文件，并重新调用工具，直至校验通过后才能结束任务。
- Schema 应完整声明根结构、对象 `type: object`、必填字段、字段类型、枚举、数组元素和额外字段限制，避免把明确的格式约束留给 Agent 自行判断。

调用示例：

```js
const OUTPUT_SCHEMA = {
  type: 'object',
  required: ['items'],
  additionalProperties: false,
  properties: {
    items: {
      type: 'array',
      items: {
        type: 'object',
        required: ['id', 'title'],
        additionalProperties: false,
        properties: {
          id: { type: 'string', minLength: 1 },
          title: { type: 'string', minLength: 1 },
        },
      },
    },
  },
};

const outputFile = 'agent-result.json';
const result = await agentService.runTask({
  title: '结构化结果生成',
  prompt: `请将结果写入 ${outputFile}。程序已预置校验 Schema；写入后调用 json-validation，只传 {"file_path":"${outputFile}"}。`,
  output_file: outputFile,
  files,
  json_validation_schemas: { [outputFile]: OUTPUT_SCHEMA },
});
```

Prompt 缓存优化原则：

| 原则 | 说明 |
| --- | --- |
| 大段共享上下文放最前面 | 服务商缓存通常命中 Prompt 前缀，所有相关请求要尽量共享同样开头。 |
| 不要在共享上下文前放不同 system prompt | 不同 system prompt 会改变请求前缀，降低后续请求的缓存命中率。 |
| 先跑一个能写入缓存的请求 | 先完成共享上下文较完整的请求，后续 fan-out 并发请求才更可能命中缓存。 |
| 独立子目录生成可以并发 | 一级目录确定后，各一级目录下的二三级目录互相独立，可以并发生成。 |
| 并发仍交给全局 AI 队列控制 | 业务层不再额外限制并发数量，只控制“先预热再并发”的执行顺序。 |

- JSON 主请求解析失败时复用现有 JSON 修复链路；修复请求只提交模型已返回内容片段、校验问题和目标格式，不重复提交完整大文本上下文。
- 后台任务不得按 token、chunk 或部分内容落盘；只在阶段开始、单次 AI 请求完整返回、失败、暂停或任务结束时写入 Store。
- Renderer 不展示 token 级增量结果；页面只展示任务阶段、进度、日志和完整结果。
- 开发者模式下 AI 请求日志保存到 Electron `userData/logs/ai/`；不要把日志路径或敏感内容暴露给普通用户。
- 所有可丢弃的本地诊断文件日志统一通过 `electron/utils/silentFileLog.cjs` 异步入队，按文件路径保持 FIFO，任何创建、序列化、写入或删除失败都必须静默且不能影响主流程；不得在日志失败后降级为同步写入。
- 开发者模式下的程序调试日志统一使用 `electron/utils/developerLog.cjs` 写入 `userData/logs/<module>/*.jsonl`；关闭开发者模式时必须是 no-op。任务数据库日志、Pi Session、自检报告和业务输出属于权威数据或用户结果，不使用静默日志写入器。
- 程序调试日志默认只保存在本机；Agent 最终执行失败是唯一例外：客户端会在 Analytics 后台开启接收且当前版本位于接收版本列表时，异步上传完整 gzip 诊断包。诊断包包含任务输入、Prompt、归档工作区、部分输出、错误链和运行环境，但必须清除文本/生图 API Key、MinerU Token、Authorization、Cookie、密码和 URL 凭据；工作区遍历、完整会话读取、脱敏、序列化、压缩和上传统一放在一次性 Electron Utility Process 中执行，主进程只做版本预检和轻量调度，任意环节失败不得影响主流程。
- 历史垃圾清理由独立清理版本控制，在新清理版本首次启动、数据库就绪且 Agent 预热前执行；只删除明确废弃的旧运行时、普通任务归档、旧安装包、废弃状态文件和未引用旧生图。任一目标删除失败时不阻止启动，也不写完成版本，下次启动继续处理。
- 技术方案图片文件随图片计划和正文引用清理：计划失效或图片被替换后，只删除不再被计划和正文引用的本地生图；新一轮图片编排移除旧图片块并落库后，再清理剩余未引用根目录生图。
- 排查文件解析、查重、废标检查、导出等模块问题时，优先使用模块级 JSONL 日志，不把详细调试过程塞进 SQLite 任务日志。

## 埋点统计

- 关联实现位于仓库根目录 `analytics/`：`analytics/worker/` 是上报与查询 API Worker，`analytics/dashboard/` 是统计看板。部署和密钥说明见 `analytics/README.md`。
- Renderer 埋点入口统一使用 `src/shared/analytics/analytics.ts`。
- AI 模型请求统计由 Main 侧 `electron/services/aiService.cjs` 统一上报。
- 禁止以清理、重构、简化为由删除或绕过现有埋点、统计字段、页面访问映射、模型使用统计和看板展示。
- 新增主菜单页面时，同步更新 `SectionId`、`menuConfig.ts`、`AppRouter.tsx`，并补 `analytics/dashboard/public/src/pages/traffic.js` 页面中文名映射。
- 埋点路由和值应稳定、可读、低基数，不包含用户输入、文件名、本地路径、文档 ID、任务 ID、随机 ID 或时间戳。
- 普通 `/track` 埋点禁止上传 `api_key`、`base_url`、`mineru_token`、Prompt、AI 响应、错误详情、文件名、本地路径、招标文件内容、正文草稿等敏感或大文本数据；Agent 最终失败诊断只能使用独立 `/agent-errors` 链路和专用 R2，不得写入 Analytics Engine。
- 埋点失败必须静默处理，不影响用户主流程。

## 发布与打包

- 打包配置位于 `client/package.json` 的 `build` 字段。
- Release workflow 位于 `.github/workflows/release.yml`，推送 `v*` tag 或手动输入 tag 触发。
- workflow 在 `client/` 下 `npm ci`，从 tag 同步 `package.json` 版本，再用 `electron-builder --publish never` 构建并通过 `gh release upload` 上传产物。
- 正式版 tag 使用 `vX.Y.Z`；带 SemVer 预发布后缀的 tag（例如 `v2.25.0-alpha.1`、`v2.25.0-beta.1`、`v2.25.0-rc.1`）会自动标记为测试版。
- 测试版只上传 GitHub 构建产物，不发布到 Cloudflare R2；AtomGit 维持现有同步和手工附件上传方式，Gitee 只同步预发布标记和更新说明，不生成 Cloudflare 下载链接。
- 客户端自动更新只检查正式版；测试版客户端可以升级到相同核心版本的正式版或更高正式版。
- 官方构建在打包前运行 `npm run generate-build-attestation`，读取 GitHub Actions Secret `YIBIAO_LICENSE_PRIVATE_KEY_JWK` 生成构建签名，并把公钥写入安装包；release workflow 缺少私钥会直接失败，本地脚本缺少私钥时才生成未签名开发构建。
- 当前未接入代码签名；Windows/macOS 未签名提示是已知发布约束，不要在普通功能改动里临时绕过。

本地打包命令：

```powershell
cd client
npm run dist:win
npm run dist:mac
```

## 开发约定

- 优先小步修改，不做无关重构。
- 保持 Windows 中文路径和中文编码兼容。
- 不新增全局状态库，除非实际复杂度需要。
- 不在 Renderer 存储 API Key。
- 不为新上传功能另写一套文档解析链路。
- 命名保持清晰：页面 `*Page.tsx`，服务 `*Service.ts` / `*.cjs`，Hook 以 `use` 开头。
- 用户可见文案、Toast、Dialog 标题和按钮文案保持中文、清晰、可操作。
- 新增主菜单入口时，必须按“埋点统计”章节完成埋点和看板映射自查。

# 统一公告系统改造执行方案

## 一、目标与范围

将原独立启动广告正式改为“图片公告”，接入现有公告系统。文字公告、图片公告共用发布流程、当前公告、历史时间线、已读规则和送达统计；图片公告内部支持图片或视频。

本次实现：
1. 看板新增／编辑公告可选择文字公告或图片公告。
2. 图片公告配置媒体类型、媒体地址、点击跳转链接、关闭倒计时、关闭时是否跳转。
3. 保留旧接口与 Markdown 正文，新客户端读取新增配置，旧客户端继续按文字公告展示。
4. 迁移已有文字公告，不改变其历史、版本、已读识别和送达计数。
5. 图片公告完整缓存媒体并确认可显示后才自动弹出；文字公告维持原展示流程。
6. 历史公告统一展示两类内容，不倒计时、不强制跳转。
7. 删除旧启动广告实现及不再使用的专属样式。

不包含：图片上传、图床建设、视频转码、视频网站嵌入、直播／分片播放、自定义按钮文字、增加广告展示频率规则、增加新的统计维度、通用弹窗排队系统、生产部署与客户端正式发布。

## 二、确定的产品行为

### 2.1 发布与互斥

- 每个项目继续只有一条 KV 当前公告，不为两类公告分别维护当前记录。
- 保存任意类型的公告，沿用现有“生成新客户端公告版本、同步当前 KV、重置本次版本送达数”的行为。
- 自动展示使用同一个公告状态和弹窗入口，按类型切换内容，不同时打开文字公告与图片公告两个自动弹窗。
- 继续沿用启动检查、每 30 分钟检查、按公告版本记录关闭状态的规则，不恢复旧广告“每次启动强制显示”的行为。
- “互斥”针对两类自动公告，不扩展成整个应用所有弹窗的协调系统。

### 2.2 各类型行为

| 项目 | 文字公告 | 图片公告：图片 | 图片公告：视频 |
|---|---|---|---|
| 展示内容 | 原 Markdown 正文 | 指定图片 | 指定视频直链 |
| 自动弹出前提 | 正文获取成功且按原规则需展示 | 完整缓存成功且图片解码成功 | 完整缓存成功且首帧可显示 |
| 倒计时 | 保留现有 5 秒 | 看板配置，0 立即可关闭 | 同左，与播放进度无关 |
| 关闭按钮 | 保留“知道了” | “关闭公告” | “关闭公告” |
| 倒计时按钮文字 | 保留现有文案 | “N 秒后可关闭” | 同左 |
| 点击内容 | 保留现有 Markdown 图片预览／链接交互 | 有链接则打开系统浏览器，无链接不跳转 | 视频区域用于播放器操作；有链接另显示“查看详情” |
| 视频播放 | 不增加视频播放器支持 | 不适用 | 自动静音播放，保留原生控件，不新增循环播放 |
| 关闭时跳转 | 不改变 | 按配置执行 | 按配置执行 |

自动公告统一只通过关闭按钮关闭，禁止 Esc 与点击遮罩关闭。倒计时结束只解除按钮禁用，不自动关闭。图片点击或“查看详情”只打开链接，不关闭公告；关闭跳转开启时，关闭按钮按顺序调用现有外部链接能力，再关闭弹窗、记录关闭和已读。关闭期间禁用重复点击，避免重复打开链接。外部链接打开沿用现有应用行为，不新建浏览器窗口管理机制。

### 2.3 失败行为

- 图片公告下载失败、写盘失败、图片解码失败或视频无法显示首帧：本次不自动弹出、不记录关闭／已读、不上报送达，不退回在线显示，不弹出报错打扰用户；保留诊断日志，下一次现有检查再尝试。
- 文字公告不受媒体缓存约束：正文请求成功就按原规则弹出；正文图片加载失败不能阻断公告。
- 清理旧缓存失败静默忽略，不作为本次媒体下载和公告弹出的前置成功条件。

## 三、统一数据结构与旧客户端兼容

### 3.1 对外字段

保留已有字段及其含义，新增以下字段：

```ts
// 公告的公共展示内容；用于当前公告与历史公告。
type NoticePresentation = {
  title: string;
  content: string;       // 始终是旧客户端可显示的 Markdown
  noticeType: 'text' | 'image';
  media: null | {
    kind: 'image' | 'video';
    url: string;
    linkUrl: string;     // 空字符串表示没有跳转
    closeDelaySeconds: number;
    openLinkOnClose: boolean;
  };
};
```

- 文字公告：`noticeType`（类型）为 `text`，`media`（媒体配置）为 `null`，正文保持原值。
- 图片公告：`noticeType` 为 `image`，`media` 包含完整媒体配置；`kind`（媒体类型）区分图片和视频。
- 缺少新类型标记的旧记录、旧 KV 内容，按文字公告读取。这是本次明确要求的兼容逻辑。
- 当前公告继续以原 `id` 表示客户端公告版本。
- 历史列表继续以原 `id` 表示稳定记录 ID；可新增 `clientNoticeId`（客户端版本号）用于区分内容版本，但不替换既有 `id` 含义。
- 新增字段同时贯通管理端查询、保存、KV 写入、当前公告与历史公告响应；不修改红点接口和送达接口的既有字段含义。

### 3.2 自动生成兼容 Markdown

由 Worker 保存服务统一生成图片公告的 `content`（兼容正文），不让看板和客户端各自维护一份权威生成逻辑：

- 图片：生成 Markdown 图片；有跳转链接时在后面附“查看详情”普通链接。
- 视频：生成“打开视频”的普通链接；有跳转链接时另附“查看详情”。
- 正确处理标题、URL 中影响 Markdown 的字符，保证生成结果可被既有渲染器解析。
- 图片公告不要求管理员填写 Markdown，也不接受手填正文覆盖自动生成内容。
- 切回文字公告后，以管理员确认的文字正文保存，清除已保存的媒体配置，避免隐藏字段继续生效。

旧客户端忽略新增字段，仍能读取非空 `content`：图片以正文图片展示，视频通过链接在浏览器打开。旧客户端继续使用自己的关闭倒计时、图片预览和关闭规则，不尝试在旧版上实现强制跳转或媒体缓存。

### 3.3 数据库迁移

新增 `analytics/worker/migrations/0014_add_notice_media.sql`（公告媒体配置迁移），实施前再次确认编号未被其他改动占用。

在资源数据库 `RESOURCE_DB` 的 `notices`（公告表）新增：

- `notice_type TEXT NOT NULL DEFAULT 'text'`：公告类型。
- `media_json TEXT`：媒体配置 JSON；文字公告为 NULL。

原 `content` 列继续存储文字正文或生成的兼容正文。媒体字段不参与查询筛选，统一存为 JSON，避免给表增加不必要的独立列。

迁移要求：
- 不修改旧迁移文件。
- 不修改既有 ID、客户端版本号、正文、时间、启用状态、送达数。
- 不通过“重新保存全部公告”进行迁移，避免生成新版本和重置送达数。
- 旧 KV 不强制重发：读取时补齐文字类型；下次正常发布时写入新结构。
- 沿用资源数据库现有迁移执行机制，不误用统计数据库，不改客户端业务 SQLite schema。

## 四、统计看板改造

### 4.1 表单

在现有公告表单中增加“公告类型”：文字公告／图片公告，新增默认选文字公告。

文字公告保留标题、状态、Markdown 编辑与预览。

图片公告保留标题、状态，并展示：

| 字段 | 默认与约束 |
|---|---|
| 媒体类型 | 默认图片，可切换视频 |
| 图片／视频地址 | 必填，HTTP(S) 直链；标签随媒体类型变化 |
| 点击跳转链接 | 可空，填写时为 HTTP(S) 链接 |
| 关闭倒计时（秒） | 默认 0，非负安全整数；说明“0 表示随时可关闭” |
| 关闭时强制跳转 | 默认否；选是必须填写跳转链接 |

表单切换类型只显示对应字段，不使另一类隐藏必填字段阻止提交。未保存的切换可保留表单内输入；实际提交只保存当前选中类型对应的数据。

新增和编辑使用同一套表单逻辑，刷新、重置、选中历史记录均能正确回填类型及媒体配置。

### 4.2 预览与列表

- 沿用现有预览入口，按类型预览 Markdown、图片或静音视频。
- 媒体预览限制在面板内部，不撑开页面；切换记录／类型时停止上一段视频。
- 看板预览不执行关闭强制跳转，也不计客户端送达。
- 列表标明“文字公告／图片公告”，视频可附“视频”说明；保留当前公告标记、启用状态、送达数、更新时间与编辑删除操作。
- 不新增上传、播放参数面板或独立广告管理页。

### 4.3 输入校验

看板给出中文输入错误；Worker 管理端保存入口做对应外部输入校验。仅按所选类型检查必需内容、URL、倒计时和跳转依赖，不在客户端内部 IPC 层重复堆叠业务校验。URL 类型不按扩展名猜测，媒体类型由管理员明确选择。

## 五、客户端缓存设计

### 5.1 职责与存储

新增 Main 服务 `client/electron/services/noticeMediaCacheService.cjs`（公告媒体缓存服务），负责当前版本同步、文件下载、缓存复用和旧缓存清理。

新增薄 IPC 模块 `client/electron/ipc/noticeIpc.cjs`（公告缓存通道），通过 preload 暴露给 Renderer；同步 bridge 类型定义。此服务不依赖业务 SQLite，装配在非数据库服务部分。

缓存放在 `userData/notice-cache/`，由统一路径工具提供位置，不写入业务工作区，不使用 localStorage 保存文件或公告正文。

目录按项目与客户端公告版本隔离。每个有效版本保存必要的公告快照／媒体来源清单和已完整下载的文件，不能只有文件存在就认定下载完成。下载采用临时文件，完成后提交正式文件和完成记录；未完成文件不供渲染器使用。

缓存不作为公告权威来源：仍先向原接口获取当前公告，不增加离线自动推送逻辑。

### 5.2 下载与版本控制

1. 当前公告检查成功后，同步服务端当前版本。版本同步与是否展示判断分开，避免已关闭的新版本使旧缓存永远无法清理。
2. 文字公告只触发必要的版本切换／清理，不等待这些工作完成，直接走原展示流程。
3. 需要展示的图片公告请求媒体准备；相同版本及相同媒体来源已有完整文件时复用。
4. 用流式写盘完整下载图片或视频，不把大视频整体堆入 Renderer 内存，不把浏览器预加载提示视为完整缓存。
5. 同一版本并发准备共用进行中的请求；不并发重复下载相同文件。
6. 发现更新版本后，使旧准备结果失效，并取消不再需要的旧下载；异步返回前再次检查目标版本，旧结果不得触发弹窗或覆盖新缓存状态。
7. 下载失败释放进行中状态并清理本次临时文件；清理失败不覆盖原始失败原因，下一轮原有检查可重试。
8. 不新增轮询频率、不无限即时重试、不增加“每次启动强制展示”判断。

### 5.3 清理规则

- 新当前版本到达后清理旧版本缓存，文字公告替换图片公告时也清理旧媒体。
- 清理与新媒体准备隔离，不等待清理成功再下载。
- 清理必须跳过新版本目录，避免旧异步任务误删新文件。
- 已打开的旧媒体在关闭或切换前不主动破坏其正在使用的文件；待释放后执行清理，删除失败静默忽略。
- 服务端明确返回无当前公告时，可释放旧当前缓存；网络请求失败不等同于“没有公告”，不得因此切换当前版本。
- 不预下载历史列表，不增加历史媒体永久缓存集合。

### 5.4 本地媒体读取

扩展现有 `yibiao-asset`（本地资源协议），增加只指向公告缓存目录的资源入口，Renderer 获取本地资源 URL，不接触磁盘路径。

媒体展示使用缓存 URL，不再次请求远程媒体。为视频启用协议流式媒体支持，并让缓存视频读取正确处理媒体类型、Range／部分内容请求，保证播放控件能正常拖动；改动限定在公告媒体资源分支，其他本地图片资源行为不变。Electron 官方协议说明明确提供流式媒体支持设置。citeturn214549search0

### 5.5 就绪与弹出

- 下载完成并不等于可显示：Renderer 对本地图片完成加载／解码，对视频等到至少首帧可用后才进入可展示状态。
- 准备阶段不创建可见模态遮罩、不抢焦点、不开始倒计时、不上报送达。
- 正式打开时使用已准备好的本地媒体；视频从开头自动静音播放，不让预加载阶段提前播放完内容。
- 图像／视频准备失败走本次不弹出的规则，且不能留下阻止下一轮重试的活动公告标记。
- 关闭、切换公告或卸载时释放媒体预加载对象、事件监听和定时器，停止视频播放。

## 六、客户端统一展示与历史公告

### 6.1 自动公告入口

改造现有 `UpdateNotifier.tsx`（更新与公告控制）：

- 软件更新和插件更新分支保持不变。
- 接收扩展后的公告类型，由同一个当前公告状态控制展示分支。
- 将“检查中／媒体准备中”与“已经展示”区分，避免缓存阶段被当作已送达。
- 文字公告取得正文后直接展示；图片公告走缓存与媒体就绪步骤。
- 倒计时从可见时刻开始：文字 5 秒，图片读取配置；0 秒不创建倒计时任务。
- 送达计数保持现有按项目与客户端版本上报、同一运行期间防重复的口径，不改为媒体下载次数或历史浏览次数。
- 关闭继续调用原关闭记录与侧栏已读逻辑，不变更存储键或额外建立已读系统。

可将图片／视频内容提取为 `client/src/features/notice/components/NoticeMediaContent.tsx`（公告媒体内容组件），由自动公告与历史公告复用。媒体组件只负责展示、播放、显式点击跳转及就绪通知，不负责公告轮询、送达或已读。

### 6.2 历史公告

改造 `NoticeBoardDialog.tsx`（历史公告弹窗）：

- 使用同一条按更新时间倒序排列的历史列表，保留原启用过滤与上下条导航。
- 按类型展示 Markdown 或图片／视频，标题可显示类型说明。
- 图片可按配置打开跳转地址；视频保留控件及“查看详情”，自动静音播放。
- 关闭历史弹窗随时允许，不运行倒计时、不执行关闭强制跳转。
- 不预下载整份历史列表：仅当前选中的媒体按需加载，显示加载／失败状态；切换条目停止上一段视频并清理监听。
- 历史媒体读取不替换自动公告的当前版本缓存标记，不触发旧当前缓存淘汰。
- 保留历史打开埋点与现有已读红点规则，不将历史浏览额外计为自动送达。

### 6.3 旧广告清理

删除 `StartupAdvertisementDialog.tsx`（旧启动广告组件），去掉固定图片 URL、固定跳转 URL、8 秒倒计时及相关旧回调逻辑。删除已无使用者的 `startup-advertisement-*`（旧广告样式）规则，不恢复其高层级独立弹窗。

统一公告样式复用现有基础组件与 Radix，不引入 UI 依赖。文字公告渲染遵守远程内容的现有项目约束，显式关闭原始 HTML；Markdown 图片、链接等兼容内容不依赖 HTML 视频标签。

## 八、执行顺序

1. **实施前检查**：查看工作区改动，确认文件当前内容和迁移编号；保留无关用户改动。
2. **数据契约与迁移**：确定共同字段，新增 SQL；修改 Worker 存储、类型映射、兼容 Markdown 和路由输入校验。
3. **看板**：新增表单字段、类型切换、回填与预览，贯通保存和列表。
4. **客户端缓存基础**：新增 Main 服务、薄 IPC、preload 类型、缓存路径、本地媒体资源入口。
5. **自动公告**：扩展客户端类型与请求，接入单一公告展示、图片缓存门槛、媒体就绪、倒计时和关闭跳转。
6. **历史公告及清理**：接入媒体复用组件，保持时间线与统计，删除旧广告组件及死样式。
7. **聚焦验证与修复**：完成下节必要检查，仅修复本次范围内发现的问题。
8. **交付**：汇报改动、已执行检查、未完成环境验证及生产上线顺序，不擅自部署。

### 9.2 必要界面／链路检查

因涉及 IPC、媒体协议和弹窗，在本地开发环境验证以下目标行为；仅使用隔离的本地公告数据，不发布生产公告：

| 场景 | 验收要求 |
|---|---|
| 已有文字公告 | 可读可编辑；迁移不改版本、正文、送达数 |
| 看板类型切换 | 只显示当前类型配置，正确回填与保存；强制跳转必须有链接 |
| 旧客户端兼容 | 响应中保留非空 Markdown；使用旧渲染路径能显示图片及视频链接 |
| 新客户端文字公告 | 正常弹出；正文中的坏图片不能阻断；原倒计时与关闭记录有效 |
| 图片公告、倒计时 0 | 完整缓存并解码后才出现，立即可关，无先出现的空白遮罩 |
| 图片公告、倒计时大于 0 | 可见后才开始计时，期间按钮禁用，Esc／遮罩不能关闭 |
| 视频公告 | 从本地缓存自动静音播放，首帧准备前不弹，控件播放及拖动正常 |
| 点击与关闭跳转 | 空链接无跳转；图片／详情点击只打开链接；关闭强制跳转开关生效且不重复触发 |
| 下载／解码失败 | 图片公告不弹、不记已读、不送达；后续检查可重试；不影响文字公告 |
| 缓存复用与更新 | 同版本不重复下载；新版本淘汰旧缓存；失败清理不阻断新公告；旧异步结果不抢占新版本 |
| 历史时间线 | 混合展示两类公告，按原顺序浏览；关闭无倒计时及强制跳转；切换停止旧视频 |
| 统计 | 仅实际自动展示后按原口径上报，缓存、预览和历史浏览不增加自动送达 |

验证以必要编译、语法和手动链路检查为限，不额外建设自动化测试框架。若本地服务、权限或媒体样本限制导致某项不能验证，交付时明确标注，不将其写为已通过。

## 十、上线顺序与权限边界

上线时按以下顺序：

1. 对资源数据库执行新增迁移。
2. 部署支持新旧结构的 Worker。
3. 部署新看板。
4. 发布支持媒体公告的新客户端。

新 Worker 在新客户端发布前即可继续服务旧客户端：文字公告照常显示，图片／视频公告提供兼容 Markdown。旧 KV 会被当作文字公告，不需要批量重新发布。

本次批准只授权实现代码、生成迁移文件和执行本地必要验证。远程迁移、Cloudflare 部署、上传公告、推送版本标签及正式发布不在本次执行范围，需要另行授权。

## 十一、完成标准

- 新旧客户端共享原公告接口且各自能按约定展示。
- 文字和图片公告在同一时间线、同一自动公告入口中运行。
- 图片公告的媒体、跳转和倒计时全部由看板配置，不再存在固定广告地址和旧独立广告逻辑。
- 自动图片公告在媒体缓存及就绪前不出现；失败不影响文字公告。
- 原有公告统计、已读、红点和历史浏览能力保留。
- 所有实际改动完成必要语法／编译与可执行的本地链路验证；未验证项和部署待办如实列出。

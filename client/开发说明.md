# 易标投标工具箱开发说明

本文面向参与 `client/` 开发的成员。具体功能行为以当前代码为准；本文只保留能帮助定位代码、跨进程协作、复用 UI、维护持久状态和完成验证的稳定规则。

补充本文时只写跨功能约束、权威来源和易错点；功能交互、文案、阈值、进度区间、Prompt 措辞和改造过程留在代码与提交记录中。

## 快速开始

仓库根目录没有客户端 `package.json`，所有客户端命令先进入 `client/`：

```powershell
cd client
npm ci             # 安装依赖；postinstall 会应用 patches/ 并按当前 Electron 重建 native 模块
npm run dev        # Vite 127.0.0.1:5173 启动后打开 Electron
npm run build      # tsc --noEmit && vite build
```

- CI 使用 Node 22，排查本地与发布构建差异时优先对齐该版本。
- `better-sqlite3` 是 Electron native 依赖。出现 `NODE_MODULE_VERSION` 不匹配时运行 `npm run postinstall`；验证 ABI 用 `npm run smoke:electron-native`，不要用普通 Node 进程加载 Store 代替。
- 项目没有统一 lint 脚本，也没有 test 脚本；定向检查脚本见“验证清单”。

## 运行结构

```text
src/main.tsx
├─ 开发者独立窗口（由 ?window=... 选择）
└─ AppProviders
   └─ WorkspaceDatabaseGate
      └─ App
         └─ AppShell + AppRouter

Renderer
  └─ window.yibiao
      └─ electron/preload.cjs
          └─ electron/ipc/*.cjs
              └─ electron/services/*.cjs
                  ├─ SQLite Store / 配置
                  ├─ 文件与导出
                  └─ AI / Agent / 后台任务
```

- Renderer 是 Vite + React + TypeScript ESM；Electron Main、preload、IPC 和 Main 服务是 CommonJS，保持 `.cjs`。
- 主窗口启用 `contextIsolation`、关闭 `nodeIntegration`。Renderer 不导入 `electron`、`fs`、`path`，也不直接使用 `ipcRenderer`，本地能力统一通过 `window.yibiao`。
- Renderer 负责页面状态和交互编排；Main 负责配置、SQLite、文件解析、AI、Agent、后台任务、导出、插件和更新。
- `WorkspaceDatabaseGate` 在数据库检查、迁移和历史清理完成前阻止业务页面挂载；数据库相关 IPC 也会先注册为 pending/unavailable handler。
- `AppRouter` 是基于 `SectionId` 的组件分发，不是 URL 路由。不要按 React Router 的约定添加页面。

## 代码放在哪里

| 位置 | 职责 |
|---|---|
| `src/app/` | 应用级路由、菜单、全局 Provider、数据库 Gate、启动提示与状态条 |
| `src/components/` | 应用壳层组件，目前主要是 `AppShell`、`Sidebar` |
| `src/features/<feature>/` | 功能页面及其专用组件、Hook、类型和 Renderer 轻量编排；目录按实际复杂度创建，不补空层级 |
| `src/shared/ui/` | 跨功能 UI 组件和全局交互 Provider |
| `src/shared/types/` | 跨功能类型、导航类型和 `window.yibiao` bridge 类型 |
| `src/shared/prompts/` | 仍在 Renderer 使用的 Prompt builder |
| `src/shared/utils/`、`src/shared/markdown/` | 跨功能纯工具和 Markdown 渲染辅助 |
| `src/styles/` | token、壳层、共享组件和各 feature 样式；`src/styles.css` 是唯一总入口 |
| `electron/main.cjs` | 窗口、协议、应用生命周期和 Main 入口 |
| `electron/preload.cjs` | 主窗口 bridge；拖拽文件路径也在这里通过 `webUtils` 暴露；插件配置窗另用 `preload-plugin-config.cjs` |
| `electron/ipc/` | IPC 注册与参数转发；`index.cjs` 负责服务装配和数据库生命周期 |
| `electron/services/` | Main 业务服务、Store、任务实现；`agent/`、`pi/`、`doc2markdown/` 是专用子层 |
| `electron/shared/` | Main 与 Renderer 共用的纯计算模块（如 `imageLayout/index.mjs`） |
| `electron/utils/` | Main 纯工具、路径、日志、队列、文本编辑和导入图片清理 |
| `electron/resources/` | 打包进入客户端的 Agent 指令、正文样张与规范、许可证公钥和构建证明 |
| `vendor/agent-tools/`、`scripts/` | 随包 Agent 命令工具及构建/校验脚本 |

放置原则：

- 只被一个功能使用的代码留在该 feature；出现真实跨功能复用后再上移 `shared/`。
- `shared/` 的运行时代码不要依赖 feature。现有 `shared/types/ipc.ts`、`shared/types/index.ts` 会组合或转出部分 feature 类型，这是 bridge/type 边界的现状，不应扩展成 shared 引用 feature 组件或服务。
- Renderer 的 `services/` 只做 bridge 调用或轻量编排；耗时流程和权威持久化放 Main。
- 新业务 IPC 默认保持薄。`ipc/index.cjs` 的生命周期装配以及 `pluginIpc.cjs` 的现有插件市场/配置编排是例外，不要把它们复制成普通功能模板。
- Prompt 不写进组件：Renderer Prompt 放 `src/shared/prompts/`，Main 后台任务的 Prompt 与对应任务服务放在一起。

### 新增菜单页面

至少同步检查以下位置：

1. `src/shared/types/navigation.ts`：增加 `SectionId`。
2. `src/app/menuConfig.ts`：配置一级或二级菜单。
3. `src/app/AppRouter.tsx`：注册页面分发。
4. `src/components/Sidebar.tsx`：为 `navigationIcons` 补齐图标映射。
5. `analytics/dashboard/public/src/pages/traffic.js`：为新增埋点路由补中文显示名。

一级菜单有 `children` 时，`AppRouter` 会使用 `shared/ui/SecondaryMenuPage.tsx` 显示二级入口，不在侧边栏实现展开菜单。设置页是侧边栏底部的独立入口。

## Renderer 与 Main 协作

新增或修改 bridge API 时按完整链路更新：

1. 在 `electron/services/` 实现业务能力或 Store 操作。
2. 在对应 `electron/ipc/*Ipc.cjs` 注册通道，并在 `electron/ipc/index.cjs` 装配依赖。
3. 若通道依赖工作区数据库，同时加入 `index.cjs` 的 `workspaceDatabaseChannels`，确保数据库就绪前不会漏注册或重复注册。
4. 在 `electron/preload.cjs` 暴露方法或事件。
5. 在 `src/shared/types/ipc.ts` 同步参数、返回值和事件类型；全局声明由 `src/vite-env.d.ts` 引用该类型。

其他约定：

- `onXxx` 事件 API 必须返回取消订阅函数，React effect 卸载时调用。
- 受管任务页面先读取 Store 快照，再订阅 `tasks.onTaskEvent()`，随后调用 `tasks.getActiveTasks()`；后一步会再次订阅并回放活动任务，避免首次事件早于 listener 注册。
- IPC patch 以“字段是否存在”为语义：字段缺失表示保留，字段出现表示应用该值；`undefined`、`null` 或空集合通常用于显式清理，具体由对应 Store 定义。Renderer 合并 patch 时使用 `hasOwnProperty`，不要用 truthy 判断。
- 命令接口可能返回 `void`、实体或局部 patch，不假定每次写入都会返回完整工作区；需要全量状态时显式调用 `load*` / `get*` / `list*`。
- 拖拽得到的浏览器 `File` 通过 `window.yibiao.file.getPathForFile(file)` 转为本地路径，不读取非标准 `file.path`。
- 外部链接通过 `window.yibiao.openExternal()`；本地导入图和生成图使用 Main 注册的 `yibiao-asset://imported-images/...`、`yibiao-asset://generated-images/...`，不要向 Renderer 暴露 `file://` 路径。
- 只在用户输入和外部响应边界做必要校验；Renderer、preload、IPC、service 之间不重复堆叠同一套内部参数校验。

## 数据与后台任务

### 持久化位置

| 数据 | 位置 / 权威实现 |
|---|---|
| 用户配置与 API Key | `userData/user_config.json`，由 `configStore.cjs` 管理 |
| 结构化业务状态 | `userData/workspace/yibiao.sqlite` |
| 导入/解析源 Markdown、图片及文件型产物 | `userData/workspace/<feature>/`、`imported-images/`、`generated-images/` |
| Pi 运行环境和持久任务 | `userData/agent-runtime/pi/` |
| 开发诊断日志 | `userData/logs/` |
| 插件与插件配置 | `userData/plugins/`、`userData/plugin-configs/`、`userData/plugin-states.json` |

- 核心工作区、配置、日志和 Agent 路径集中在 `electron/utils/paths.cjs`；新增核心路径优先补在这里。插件自身路径目前由插件服务管理。
- Main 文件读写显式使用 UTF-8，并以 Windows 中文路径为常规场景。
- SQLite 建表、升级、健康检查和备份逻辑以 `electron/services/sqliteDatabase.cjs` 为运行时权威。改表时增加 migration，并同步仓库根目录 `sql/workspace_schema.sql` 的目标结构；历史迁移编号保持不变。
- 数据放 SQLite 还是文件系统由对应 Store 定义。不要按文本大小另建平行 JSON 缓存；删除文件型资源时同步清理其导入图片 scope。
- 不在 Renderer 保存业务状态、草稿或密钥。`localStorage` 只用于公告、更新日志已读标记等轻量 UI 偏好。

### 受管后台任务

`taskService.cjs` 统一管理技术方案、标书查重、废标检查和暗标合规检查任务；各业务组当前均为组内互斥。知识库是明确例外：`knowledgeBaseService.cjs` 按文档维护 preparation/matching 活动集合，并通过 `knowledge-base:event` 推送。Word 导出也有独立的进度事件。

受管任务遵循以下流程：

1. Main 创建 running 任务并持久化初始状态。
2. 无恢复价值的高频进度调用 `updateTask()`，只更新 Main 内存并推送事件。
3. 阶段结果调用 `checkpointTask(taskPatch, workspacePatch, eventPatch)`，在 Store 事务中一次提交任务和业务 patch，成功后再推送同一份局部事件。
4. 页面卸载不取消任务；重新挂载从 Store 和活动任务回放恢复展示。
5. 应用重启后的恢复策略由 `taskService.cjs` 按任务类型决定（如正文任务可转为 paused，其余中断任务通常转为 error）。Renderer 不自行把残留 running 状态改成 idle。

会清空任务或下游结果的 Main 命令，必须先取消相关活动任务并等待 runner settled，再提交 Store；取消后的 runner 不得继续 checkpoint。技术方案和废标检查的导入、删除、重置已经通过 `taskService` 的 `beforeCommit` 链路处理，新入口应复用该模式。

## 技术方案

技术方案统一使用 `technical-plan` 入口：标书分析、目录、全局事实、正文等耗时流程都在 Main 后台任务中运行并持续写入 SQLite Store。是否启用原方案扩写由 `originalPlanFile` 是否存在决定，不再维护独立扩写入口或工作流开关。

### 权威数据与状态规则

- **生成配置**：项目级配置保存在 `technical_plan_generation_config` 及其 `_bid_tasks`、`_reference_docs` 子表，Main 通过 `technicalPlanStore.loadGenerationConfig()` / `saveGenerationConfig()` 读写，Renderer 使用同名 API。只有 Step02 维护生成设置（页签集中在 `generationSettingsTabs.ts`），目录、全局事实和正文页直接使用已保存配置。正文任务一旦启动，Step02 除导出模板和模板样式范围外锁定，锁定状态复用正文运行时保存，只在页面层校验；明确重置正文或清空正文后解锁。模型、API、文件解析器和 Word 导出样式属于全局 `user_config.json`。
- **字数快照**：`outlineWordControlOptions` 是可编辑配置，目录成功时固化为 `outlineWordControlSnapshot`；正文只使用生效快照。
- **招标文件**：`technical-plan/tender-original.md` 是完整合并原文，`tender.md` 是当前投标范围工作副本，`tender-files/` 是单份来源 Markdown，`tender-originals/` 是 Word 原件。切换标段从原文重建工作副本并清空下游。
- **目录身份**：节点 `id` 是程序分配的稳定 UUID（Agent 新节点填 `id:null`，由程序在阶段交接时分配），`number` 按树位置计算、仅供显示；数据库以 `node_id`、`parent_node_id`、`sort_order` 表达关联、层级和顺序，不从 ID 推算编号。正文 HTML、还原底稿和小节 Word 均按稳定 ID 命名。技术方案使用独立的 `TechnicalPlanOutlineItem` / `TechnicalPlanOutlineData` 类型，不改变可研目录协议。
- **目录与正文权威**：目录结构和非 AI 节点正文以 `technical_plan_outline_nodes` 为准（Renderer 对应 `outlineData.outline[*].content`）；AI 小节正文是正文持久会话工作区中的受限 HTML，数据库只保存生成状态、错误和 `section_words`，不保存 HTML 副本。
- **`saveOutline()` 的 `reason` 是持久化协议**：`replace` 清空全部旧正文；`edit` 只更新标题和描述；`delete`、`add-root`、`add-child` 结合 `affectedNodeIds` 只清理受影响节点；`sort` 只改变顺序和显示编号，节点 ID、正文、编排、运行时及 Word 文件名保持不变。不要省略 `reason`，否则 Store 按 `replace` 处理；不要在 Renderer 复制清理规则。
- **局部目录变更**保留正文持久 Session 和工作区，新增及重新成为叶子的节点进入 `pending_item_ids`；已删节点的 HTML、图片和 Word 允许成为孤儿文件，导出只按当前目录 ID 读取。只有全文重新生成、整目录替换或重置才删除正文会话。
- **全局事实**保存、增删、重新解析在已有正文时必须先确认清空；确认后 Main 清空正文、编排、任务和运行时。
- 正文任务处于 running、pausing 或 paused 时，Store 禁止目录变更和手工正文保存。技术方案任一后台任务运行中、正在暂停或正文任务已暂停时，页面禁用整本导出，避免读到未完成的 HTML。
- **全流程重置**先经 `taskService` 取消并等待后台任务、关闭 OpenXmlHelper，再由 Store 删除 `workspace/technical-plan/` 及该流程专属的生成图片、导入图片和持久 Agent 会话；用户原始文件、知识库、模板库和全局配置不清理。Renderer 对重置、全局事实保存和目录保存在 `finally` 中重新读取完整状态。

### 目录生成与投标模版提取

- 目录生成 V2（`outlineGenerationTaskV2.cjs`）使用持久 task workspace/Session，才能在一级目录确认后恢复。各阶段声明必需产物（`outline.json`、评分规划文件、`leaf-allocation.json`、`outline-review.json` 等），由 `validateOutput` 检查。
- 一级目录来源分两条路径：技术文件独立成册按技术评分项生成；完整投标文件和商务标独立成册由 `outlineFormatExtraction.cjs` 处理。程序先准备覆盖全部导入文件的原文结构：Word 原件用 `readTenderBlockOutline()` 生成 `招标原文结构.txt`（块号）；没有 Word 原件的文件（如 PDF）合并后加行号写入 `招标原文（带行号）.md`，全部没有 Word 原件时对 `tender.md` 加行号。Agent 按内容判断招标文件的格式章节（不依赖章节名称），逐条照抄提取，格式章节本身分层时带出子目录，只在中标后使用的条目标 `post_award`；找不到格式章节时才按响应文件要求生成平铺一级目录（`basis` 区分两种依据）。按格式章节提取时 `format_scope` 是范围数组（格式分在几份文件时逐段填写），每个节点带原文位置 `source`（`start` 含、`end` 不含，多份来源时 `source.source` 为原件路径或带行号原文文件名），程序校验位置顺序、嵌套范围和标题与原文一致。`source`、`post_award` 只存在于确认阶段，进入后续阶段前去掉，不写数据库。
- 一级目录确认弹窗是树形勾选：勾子目录自动勾上级，取消上级取消整棵子树，子目录全部取消时上级一并取消。完整投标文件默认勾选除中标后使用外的全部节点，商务标独立成册默认勾选模板填写、目录生成和人工填写叶子。
- 技术分支挂载在已确认的叶子节点上：评分规划和叶子分配用 `node_id` 指向挂载节点，`score_item_level` 以挂载节点为第 1 层；无评分项模式以已确认的 AI 叶子为挂载点。未批准一级目录调整时，子目录生成、数量调整和审核阶段由程序核对全部已确认节点不变，只允许在挂载节点下扩展。目录不要求父节点至少有两个子节点。
- 叶子处理模式为 `ai-generate`、`template-fill`、`directory-generate`、`manual-fill`、`other`。`directory-generate` 是投标文件目录，全目录最多一个（提示词约束；目录页“下一步”多于一个时报错拦截，允许没有），由整本导出生成目录，不进商务模版、不填写、不计入正文页待处理。商务模版按选中目录完整抽取：除目录生成外，带 Word 原文位置的已确认叶子不论处理方式都交给投标模版提取，处理方式只决定字段是否自动填写（`auto_fill`）；没有原文位置时只按标题抽取 `template-fill` 叶子，位于带行号原文（无 Word 原件）的节点不抽取。有可抽取的叶子且有招标 Word 原件时，才从目录会话分叉普通 Session 执行提取（`templateExtractionTask.cjs`），产出 `bid-template.docx` 与 version 2 字段清单 `bid-template-fields.json`。提取直接按确认时的原文位置抽章；`openxml` 工具的 `extract-chapters` 按 id 核对每个已确认目录恰好抽一章、按目录顺序排列并注入 `auto_fill`，助手写入字段时把非自动填写章节的字段改为人工（同名字段在自动填写章节由程序填写时沿用程序填写）。
- 目录变更后的重新提取（`bidTemplateExtractionTask.cjs`，任务类型 `bid-template-extraction`）：
  - 目录页“下一步”经 `inspectBidTemplate()` 核对当前非 AI 叶子与字段清单 `chapters`。按上述规则应进入模版却没有对应章节（新增），或 `auto_fill` 与当前处理方式不符（变化）时，询问是否重新提取。原文位置按 ID 取自目录任务的 `outline_selection.items`；比对只看 ID 和处理方式，改标题、描述、排序不会触发。技术文件独立成册、没有招标 Word 原件或正文已开始时不检查。
  - 重新提取先确认目录会话存在，再清空旧模版（旧产物会让提取校验误判完成），然后从目录会话分叉，按当前目录整本提取。失败后没有模版，下次“下一步”再次提示。
- 模版提取经 `openxml` 工具操作 Word；字段语义、`subject`/`section`/`kind` 与表格逐行规则、Open XML 动作细则见 `openxmlhelper/开发说明.md`。

### 正文生成

正文由一个持久 Pi 主会话（task key `technical-plan-content-generation`）连续执行：基础编排 →（按需等待原方案还原）→ 正文与配图 → 可选字数校正 → 一致性审计 → 可选去表格 → 可选格式自检 → 程序逐节转换 Word。阶段经 `continueTask` 在同一 Session 续接，不以多次打开 Session 代替。

| 模块 | 职责 |
|---|---|

易遗漏约束：

- **固定工具列表**：主会话以 `fixed_tool_list: true` 运行，首次创建即启用全部工具，阶段切换只更新门禁，保持 system prompt 与 tools 不变以复用前缀缓存。
- **续跑提示**：暂停继续、失败重试时，若当前阶段要求已发出（持久状态的 `prompted_stage`，见 `wasStagePrompted()`）只发送 `CONTINUE_PROMPT`，否则发送完整阶段要求。新一轮任务、新一次单节修改和导出修复都要先把 `prompted_stage`、`compaction_pending` 清为 null。
- **任务文件与程序清单**：批量工具不接收数组参数，统一读取 `任务/` 下的固定任务文件；随小节数增长的结果写入 `程序清单/`，工具只向模型返回统计和未成功项，逐项结果放在 details。新一轮清空两者，暂停继续和失败重试保留；单节修改使用各自的 `单节修改/` 子目录。
- **单工具阶段**（字数校正、去表格、格式补写）由程序逐项调用 `aiService`，不启动 Pi 子会话，进度和失败状态保存在持久任务 state 中，续跑跳过已完成项。
- **HTML 结构**：AI 响应先经 `electron/utils/aiSourceExtraction.cjs` 的 `extractAiSource()` 提取源码，结构由 `electron/utils/htmlStructure.cjs` 统一检查；生成保存、提交和整本导出前开启 `checkSourceCompleteness`。Word 转换和预览遇到旧正文结构问题只用 `repairHtmlStructure()` 在内存副本修复，不回写源 HTML。
- **图片**：生成方式规则集中在 `contentImageKinds.cjs`，关闭的方式从规范、提示词、工具和 Schema 中整体移除；`受限HTML生成规范.md` 用 `<!-- @if ai -->…<!-- @endif -->` 条件段和占位符在写入工作区时渲染。AI 画面形式以 `AI_IMAGE_STYLES` 为唯一来源，增删时同步规范中的 style 列表。原方案图片始终复用、不重新生成，也不占新增布局名额。
- **图片保护**在提交时比对而非写入时拦截，基线由 `pi/piWorkspaceBaseline.cjs` 管理。
- **并发编辑**按小节互斥；批次结束后对本批以外被改动的目标小节做越界还原，这依赖派发工具为 `executionMode: 'sequential'`。若放开 `sequential` 或改为后台派发，须先记录各小节被批次接管的次数，只还原次数未变的小节。
- **请求前缀**：并发写作请求经 `promptPrefixCache.cjs` 的 `sharedPrefixMessages()` 拼装，system 整轮相同，公共材料单独成消息排在本节内容之前（规则见“AI 请求”）。
- **产物位置**：HTML、图片和源码留在 Agent 会话工作区（`正文/<稳定ID>.html`、`图片/`）；正式小节 Word 输出到 `userData/workspace/technical-plan/<小节ID>.docx`，先写临时文件再替换，失败保留原 Word。小节预览（`previewContentWord`）只在系统临时目录独立转换，不覆盖正式 Word。正文页只读，不提供手写编辑：AI 小节显示 Word 只读预览，其他处理方式的小节显示处理说明。
- 业务进度复用 `onActivity` 的结构化 progress 事件，不经过模型；进度只用于展示，不作为执行成功或跳过任务的依据。
- 小节 Word 与正文同生命周期：正文重置、全局事实清空、整目录替换同步清理全部；局部失效只处理受影响节点 ID，数据库提交失败时逆序恢复暂存文件。
- 正文、配图、审计、去表格都在主会话完成；旧的独立配图、多轮审计、内容矫正、“忽略失败小节”等流程已移除，不要恢复相关存储或入口。

### 原方案还原

- 独立持久 Session（task key `technical-plan-original-restoration`，`primary_session=false`），实现在 `originalPlanRestoration.cjs`；仅当 `technical_plan_meta.original_plan_markdown_path` 非空时执行。
- Agent 只输出各小节对应的原文行号范围、标题处理和未还原范围，不输出正文；程序用 `restoredAssignmentContent()` 按范围逐字重建，避免模型改写原文。结果先经 `assertOriginalRestorationSchema` 校验，再检查覆盖范围、表格和图片。
- 原方案 Word 导入使用 `preserveImages: true` 和独立 `technical-plan-original` 图片批次；原图在正文初始化时复制到工作区 `原图/`，后续各阶段不得丢失、重复、跨节搬运或改写原图引用。
- 还原率按来源行范围并集、`countReadableWords` 统计，保存在 `stats.content.original_restoration`。

### 商务模版填写

- 正文任务在初始 checkpoint 后并行启动 `businessTemplateFillTask.cjs` 副流程（task key `technical-plan-business-template-fill`）；没有 AI 小节时只执行副流程。主流程成功前须等待副流程，两者都成功才提交 success。
- 填写范围跟随当前目录：`loadBusinessFillScope()` 只取 ID 为当前非 AI、非目录生成叶子的模版章节，字段按空白底稿版式的块号归属章节。填写 Agent、确认弹窗和填写统计都使用这一范围；回填 Word 仍按全部字段，范围外字段保留占位，也不会被导出。
- 填写单元由 `groupFieldUnits()` / `buildFillUnits()` 按字段清单 v2 生成，`manual` 字段不交给 Agent；确认阶段 `reviewing` 复用自动确认机制（`taskControl.waitForBusinessFillReview()`），确认与后续编辑共用 `buildConfirmedEntries()`。
- 确认弹窗（`BusinessFillReviewDialog.tsx` + `BusinessFillDocument.tsx`）按模版版式还原表单：`loadBusinessFillReview()` 经助手 `read-template-layout` 读取空白底稿的版式，按字段清单的 `chapters` 分章，字段在原段落、原表格位置就地编辑，同名字段的多处位置共用一个值。左侧章节栏显示各章已填和待处理数量；待处理为未填写、不是未使用空行、也不是签章位置（字段 `signature`）的填写项，签章位置显示为线下签章、不可编辑。
- 逐行清单表（同一表格内同名字段出现在多行）按行判断：有任一格已填的行（签章不算）空格待处理；一行都没填时只有第一行待处理，其余行为未使用的空行，不计入待处理和总数，输入内容即转为已用行。弹窗按当前输入实时计算（`BusinessFillDocument.tsx` 的 `findIdleListUnitKeys()`），导出按已确认值计算（`businessTemplateFillTask.cjs` 的 `findIdleListUnits()`），两份实现同一规则、改动时同步；AI 写入的留空标记由该规则取代，字段清单中的值不改。
- 正文页选中在字段清单 `chapters` 中有对应章节的非 AI 小节时，经助手 `slice-template-chapter` 按块号从当前 `bid-template.docx` 现截单章并以 Word 只读显示（`previewBusinessChapter()`，不落盘）；结果文档重新回填后旧预览撤下，再次打开时重新截取。没有对应章节的小节显示处理说明。
- Word 始终以空白底稿 `bid-template-blank.docx` 重新回填（`ensureBidTemplateBlank()` 在首次填写前复制），因此用户在 Word 中对 `bid-template.docx` 的手工修改会被覆盖。
- 回填值由 `renderBusinessTemplate()` 组装：纯空白的文字值（AI 用空格表示“不符合则留空”）按留空写入，助手 `fill-template-fields` 不接受空白文字；确认弹窗仍把纯空白视为未填写。
- 已填值随正文一起失效，在 `createContentWordTransaction` 中处理；Word 被占用时报 `BID_TEMPLATE_IN_USE`。正文任务运行中编辑填写值须经 `taskControl.businessFillEditor` 同步任务内存，避免被后续 checkpoint 覆盖。

### 整本导出、模板与格式自检

- 投标文件整本导出走 `export:word` 并携带 `source: 'technical-plan'`，由 `technicalPlanExport.cjs` 按当前目录读取正文会话工作区的 HTML，不读数据库 AI 正文或已有小节 Word。导出前 `inspect()` 检查源码完整性，不通过时转入正文会话的 `export-repair` 阶段，本次不保存文件。AI 小节未完成或单张图片无法写入时保留标题、原位文字标出并返回 warnings；格式自检复用导出时保持严格校验。
- 整本导出按目录导出正本，各叶子按处理方式取内容：AI 生成只用 AI 正文；目录生成在该处生成 Word 目录；其他处理方式并入商务模版中 `id` 等于该节点的章节，没有时保留占位提示。
- 目录每次导出重新生成，不入库、不判断过期：
  - `technicalPlanExport.cjs` 在第一个目录生成小节写 `YIBIAOTOC` 标记，助手换成 Word 原生目录域（文档里有几级大纲就收几级，规则见 `openxmlhelper/开发说明.md` 的“整本目录”）；老项目多出的目录生成小节保留占位并提示删除，已抽进模版的目录章节不并入、不填写。
  - 页码由 `technicalPlanToc.cjs` 测量回填：条目已写满、页码为等宽占位，先用 `readWordPageAnchors()`（隐藏窗口 docx-editor 布局，只回传页数、各页显示页码和 `_Toc` 书签所在页）测整本；回填只会让条目变窄，再用助手另存的只含目录小文档复测页数，少了 Δ 页就把目录之后的条目统一减 Δ（目录前后都是硬分页），最多 3 轮，最后对整本只回填一次。
  - 测量失败不阻断导出，页码留空并提示在 Word 中更新域；清空页码也失败时导出报错，不把占位交给用户。生成的文档保留 `UpdateFieldsOnOpen`，Word 打开时会提示更新域，以 Word 排版为准。
  - 格式自检复用整本导出但不测量页码，目录保留占位。
- 商务模版章节按模版原样并入（细则见 `openxmlhelper/开发说明.md` 的“客户端接入”）：
  - 不写程序标题，与目录标题同名的段落加大纲级别；字体、表格、编号和图片保持模版格式，纸张、页边距和字符网格用模版自己的，页眉页脚沿用样式范围规则。
  - 每次导出由 `renderBusinessTemplateForExport()` 以空白底稿和已确认值临时生成一份已填模版（`technical-plan/bid-template-export-*.docx`，导出后删除），签章位置留白，用户在 Word 中对 `bid-template.docx` 的手工修改不带入。
  - 未填写项保留占位，清单表未使用的行留空（`applyListRowMarks()`，规则同确认弹窗），数量按确认弹窗的待处理口径由 `countPendingUnits()` 统计后写入导出提示，与 Word 中商务部分的标记数一致；格式自检和“从投标文件导出”复用同一导出，同样带上商务章节。
- 需要用户补充的位置在程序内外统一为“【待填写】”或“【待填写：说明】”，导出后搜索一个关键词即可逐项处理：
  - AI 正文和全局事实沿用提示词中的【待填写】，商务模版的 AI 与人工字段都写“【待填写：字段名】”（确认弹窗仍按 `fill_by` 显示“待填写/待人工填写”状态），导出时原样保留、不再转换；无正文小节（说明由 `getPendingContentModeMessage()` 给出）、未完成的 AI 小节和无法导出的图片由 `formatPendingMark()` / 助手写成“【待填写：说明】”。
  - 签章位置和未使用的空行留白，不加标记；助手返回的 `pendingMarkCount` 写入导出提示“文档中共有 N 处“待填写””，暗标检查的占位符规则按“待填”识别。
- 模板设置页“从投标文件导出”复用同一整本导出，只替换模板配置。
- 统一正文样张 `electron/resources/content-generation/正文模板.html` 是唯一来源，模板设置页经 `src/shared/bodyHtml/documentTemplate.ts` 读取；规范为同目录 `受限HTML生成规范.md`，配图类型为 `配图类型对照表.md`。
- 模板样式范围 `exportTemplateScope` 取 `ai-only` 或 `document`；纸张、方向、双栏和页边距始终作用于整个文件，其余样式按范围生效。范围外的节显式写入空页眉页脚，页码只在文档起点设起始值。
- 页眉页脚预定义样式只负责结构；距离、字体、颜色、对齐等设置对全部样式生效，预览与导出读取同一组设置。正文间距写 Word 原生 `beforeLines/afterLines`、`line/lineRule`，不换算成磅。
- 受限 HTML 的章节页框由 `RestrictedHtmlDocumentRenderer` 融合为真实表格，模板预览、小节 Word 和整本导出共用 C# 转换，细则见 `openxmlhelper/开发说明.md`。`exportService.cjs` 的 Markdown 导出保留段落页框结构，不复制融合逻辑；`node electron/services/exportService.cjs` 运行其自检。
- 格式自检可选：`contentGenerationLayout.cjs` 复用整本导出写入临时目录，`wordLayoutPreload.cjs` 在隐藏窗口调用 docx-editor 的导出布局 API 测量，不使用截图或 AI 读 Word；状态保存在正文 Session 的 `state.layout_check`，最多一轮补写和一次复查。

### DOCX 预览补丁

- DOCX 预览引擎固定 `@docx-editor.dev/core@2.15.0`，修复统一保存在 `patches/@docx-editor.dev+core+2.15.0.patch`，同时覆盖 ESM 与 CommonJS 构建，由 `postinstall` 的 `patch-package --error-on-fail --error-on-warn` 应用；补丁失败或版本不匹配必须中止安装，不维护另一套替换脚本。

## UI 与样式复用

UI 使用全局 CSS + Radix primitives，不使用 Tailwind。优先从 `src/shared/ui/index.ts` 引入：

| 场景 | 复用入口 |
|---|---|
| 页面底部操作 | `FloatingToolbar` |
| 对话框、开关、提示 | `AppDialog`、`AppSwitch`、`useToast` |
| 弹窗内选一种方式并立即开始 | `OptionCardList`（整张卡片可点击，可置灰并写明原因，`highlightedValue` 标出推荐或上次的选择；底部只留“取消”） |
| 上传区 | `UploadBoard`、`UploadRow`、`UploadFilePill`、`UploadEmpty` |
| 进度、加载、空态 | `ProgressBar`、`InlineSpinner`、`EmptyState` |
| Markdown | `MarkdownRenderer`、`MarkdownEditor`、`MarkdownFullscreenViewer` |
| 全局特殊交互 | `AgentQuestionDialogProvider`、`AiHttpErrorDialogProvider`、`DocumentParseNoticeProvider` |

- `AppProviders` 已挂载全局 Provider，feature 使用对应 Hook，不重复创建全局弹窗或提示状态。
- 成功、错误和普通提示使用 `useToast()` 的 `success`、`error`、`info`；不要使用 `alert`、`window.confirm` 或 `window.prompt`。需要确认或长文案时使用 `AppDialog`/Radix Dialog 和共享按钮类。
- 复用 `.primary-action`、`.secondary-action`、`.danger-action`、`.text-button`、`.panel`、`.section-kicker` 等基础类；颜色、圆角、阴影、焦点和动效优先使用 `styles/tokens.css` 的 `--yb-*` 变量。
- 新 feature 样式放 `styles/feature-<name>.css` 并在 `styles.css` 的 feature 区导入；共享样式才进入 `shared-*.css`。总入口的 `tokens → layout → shared → feature` 顺序参与 CSS 优先级，不随意重排，也不要照搬开发者测试页中的内联视觉样式。
- `body` 固定 `overflow: hidden`。页面根节点保持 `width/height: 100%`、`min-height: 0`，滚动放在页面内部；`FloatingToolbar` 是覆盖层，不为它预留大段底部空白。
- `MarkdownRenderer` 当前默认 `allowRawHtml=true`，调用方不要依赖默认值：远程公告、Agent/AI 文本及其他非本地可信内容显式传 `false`；只有确需保留本地解析 HTML 结构时才传 `true`。
- 所有用户可见文案使用中文，并给失败状态提供可操作信息。

## AI、Agent、文件与日志

### AI 请求

- 业务模型请求统一经过 `electron/services/aiService.cjs`，集中处理模型配置、文本/生图独立队列、并发、重试、取消、日志、Token 统计和埋点；Main 业务代码不要直接请求模型 HTTP。
- `taskService` 为任务绑定 `queueScopeId`、取消信号以及 scoped `aiService` / `agentService`。暂停或取消沿该作用域传播，不在业务任务里复制队列。
- Agent 的空闲计时归属由 `electron/utils/aiRequestActivity.cjs` 的异步上下文维护：实际请求成功、失败或收到流式数据时刷新所属 Agent 及父链的 `last_activity_at`，不广播给同队列其他 Agent，也不增加定时心跳。
- 易标官方 API 余额不足（HTTP 402，`error.code=INSUFFICIENT_BALANCE`）不重试，由 `emitAiHttpErrorToWindows()` 广播 `ai:balance-insufficient`；主窗口统一由 `src/app/useTextModelSetupRedirect.ts` 跳转设置页，功能页面不单独处理余额不足或未配置跳转。
- 批量程序步骤用 `electron/utils/aiBatchGuard.cjs` 识别服务端故障：同一批连续多次 AI 请求本身失败（`isAiRequestError`）且期间无成功时，以 `AI_UPSTREAM_UNAVAILABLE` 停止派发，已完成结果保留；暂停和取消不计入。
- **提示词前缀缓存**：模型服务只在消息边界复用前缀，同一条消息内的相同前缀、`cache_control` 和 `prompt_cache_key` 都不起作用。多个请求共用的材料单独作为消息排在变化内容之前；并发或连续发出两次及以上时，先用 `promptPrefixCache.cjs` 的 `warmPromptPrefix()` 预热，预热与正式请求用同一函数构造前缀，预热失败不影响后续请求。
- AI 返回的局部文本修改复用 `electron/utils/textEdit.cjs`：未知位置用 `applyTextEdit()` / `applyTextEdits()` 并保持唯一命中，已知范围用 `applyRangeEdit()` / `applyRangeEdits()`；未命中或多命中返回错误，不静默追加。

### Agent 运行时

- `agentService.cjs` 为每个实际 Agent 调用创建独立 Runtime/Session，模型请求仍走 `aiService` 文本队列。`services/agent/` 和 `services/pi/` 只实现 Runtime、Proxy、Session、工具、诊断和持久任务，不引用业务 Store 或业务 Prompt；业务适配器通过 `agentService` 公共接口调用，业务工具经 `create_tools` 注入。
- 在某个 Agent 执行过程中发起的调用即为子代理：按父 Agent 分池限流，每条提示词后最多执行有限轮数（超限 `AGENT_TURN_LIMIT`，错误交给调用方）；主任务不设轮数上限。失败诊断上报只由 `failure_handled_by_parent` 决定。
- 业务任务通过 `primary_session` 显式指定主 Session；执行监视器展示 `active_tasks`，桌宠插件只访问主 Session。
- 普通 Agent workspace 是临时目录；需要跨确认或暂停恢复的流程使用持久 task workspace/Session。结构化输出的 Schema 定义在业务任务代码中，通过 `json_validation_schemas` 注入，仅供 Agent 自查。
- 各阶段均开放原生工具 `read/write/edit/bash/grep/find/ls`，公共层保证阶段切换和恢复时不缩减；业务工具按阶段权限开放。会话工厂先注册全部工具，再用 `setActiveToolsByName()` 切换阶段工具；`fixed_tool_list: true` 时改为只切换执行前门禁。
- Runtime 接收 `prepare_output_files` 预建空白产物文件（已存在不覆盖）；阶段交接可返回 `await_before_prompt`，与上下文压缩并行执行程序步骤，结束后才发送下一阶段提示词。
- `summary_enabled` 默认开启，仅显式传 `false` 时关闭结束总结；Agent 在最后一批工具调用上附加 `task_complete=true` 结束当前阶段，业务也可通过 `is_final_tool_call` 由程序判断结束。
- 开发者 Pi Agent 链路测试可按本次任务启用 Parallel 公开网页搜索，默认关闭；Main 调用使用 `parallel_search: true`，工具仍遵循当前阶段权限。使用范围、匿名 MCP 连接和定向检查见 [Parallel 网页搜索](doc/Parallel网页搜索.md)。
- Agent 提问由全局 `AgentQuestionDialogProvider` 和 Main 的问答/自动确认服务承接，feature 不实现第二套等待 Promise 或弹窗。
- Agent 不得自行终止任务：`report-failure` 由 `pi/piTaskFailureTool.cjs` 统一改为向用户确认，用户确认终止才以 `AGENT_REPORTED_FAILURE` 结束；`failure_handled_by_parent=true` 的子会话及没有提问通道的会话仍直接报告失败。业务提示词无需改写。

### 提交校验

- 文件写入不在 write/edit 层校验或拦截，任何写入方式的结果统一在 Agent 结束一轮后校验：Runtime 先还原受保护文件（`pi/piWorkspaceBaseline.cjs`），再由业务 `validateOutput` 返回统一报告 `{ value, issues, progress?, minimumGoal? }`，`issues` 每项以 `severity=blocking|quality` 区分。
- 业务校验问题正常返回报告；文件读取、模型中断及程序异常才抛出，按 `max_retries` 处理，不消耗提交修复预算。
- `pi/piSubmissionPolicy.cjs` 统一按相邻两轮的进展决定继续修复、要求换方法、接受质量遗留或终止；接受时 `report.value` 作为 `validation_result` 传给循环外的 `continueTask`，放行问题记入 `accepted_issues`，不把遗留伪称为修复成功。
- 退回提示由公共层拼接修复模式说明，业务通过 `buildRetryPrompt(request, meta)` 只补充文件和工具信息（`kind=execution` / `kind=submission`）。
- 目录、全局事实、正文各阶段、原方案还原、模版提取和商务模版填写均使用相同报告协议，不兼容旧返回结构。

### 文件、导出与日志

- 新的文档导入优先复用 `fileService.cjs` / `parseDocumentWithConfig()`，保留配置中的本地或 MinerU 选择、格式 fallback、图片 scope 和统一错误文案。涉及 LibreOffice 缺失提示时复用 `DocumentParseNoticeProvider`。
- Word 导出统一走 `exportService.cjs` 和 `window.yibiao.export.onWordExportProgress()`；Mermaid/HTML 转图由 Main 的 `localImageRenderService.cjs` 本地完成。Mermaid 只用于技术方案正文生成，Markdown 中的 `mermaid` 代码块按普通代码块处理。
- 生成图片落盘前统一经 `electron/utils/imageCompression.cjs` 压缩，后续引用、预览和导出直接使用压缩后的文件。
- 排查异常先记录可复现的阶段、输入摘要和错误链：开发者模式模块日志使用 `createDeveloperLogger()` 写到 `userData/logs/<module>/`，AI 请求日志在 `userData/logs/ai/`。可丢弃文件日志通过 `silentFileLog.cjs` 异步写入，日志失败不得影响主流程。

Renderer 埋点入口是 `src/shared/analytics/analytics.ts`，AI 与 Agent 统计分别在 Main 的 `aiService.cjs`、`services/agent/`。埋点失败必须静默，不影响主流程，也不得删除或绕过现有统计。普通 `/track` 埋点不得上传 API Key、Prompt、模型响应、文件内容、文件名或本地路径；Agent 最终失败诊断是独立 `/agent-errors` 链路，由专用进程采集并脱敏诊断包，不得并入普通埋点或随意弱化。

## 已知缺口（无需修复）

以下问题已确认存在，影响很小，当前不修复；代码评审或排查再遇到时不必重新提出，确需处理时先与维护者确认。

- **未填写的勾选项没有【待填写】标记**：商务模版的勾选项（字段 `kind: choice`）只用内容控件包住招标文件原有的“□是 □否”等选项文字，不写占位。未勾选时，导出 Word 中该处没有“待填写”，用户按导出提示搜索找不到；但确认弹窗仍把它列为待处理，`countPendingUnits()` 也计入导出提示“商务模版有 N 项未填写”，因此该数字可能比 Word 中商务部分的“待填写”标记多。勾选项在商务表单中少见，原有方框也能看出是否已勾选，不为此补写标记。
